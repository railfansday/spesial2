Moving Postgres in Docker to 19: the parts that break

Tanggal: 2026-11-22

PostgreSQL 19 came out on November 19. I maintain a small tool that runs Postgres in Docker, so I spent the last few days moving it to 19. Most of it was boring, which is good. Some of it wasn't.

Everything below was run against the official postgres:17, postgres:18 and postgres:19 images. The output is from my terminal, with timestamps and noise trimmed.

This changed in 18, but if you're going from 17 straight to 19, it's the first thing that will stop you.

Your old compose file almost certainly has - pgdata:/var/lib/postgresql/data. With 19 the container won't start:

I got that with a brand new, empty volume too. The entrypoint refuses any mount at the old path, not just one with data in it.

For an existing volume, changing the path isn't enough: the data inside is still 17's and 19 can't read it. You need a dump/restore or pg_upgrade (section 4). The new layout exists so both majors can live under one mount (/var/lib/postgresql/17/docker, /var/lib/postgresql/19/docker) and pg_upgrade --link works without crossing a mount boundary.

18 added async I/O, with io_method = worker by default and io_workers to size the pool. If you tuned 18, you might have set it. 19 removed it and replaced it with io_min_workers (default 2), io_max_workers (default 8), io_worker_idle_timeout and io_worker_launch_interval. The pool scales itself now.

An unknown setting is FATAL at startup, and the official image passes your -c flags to the temporary server it starts during init. So on a fresh volume, initdb succeeds and then:

In compose with restart: unless-stopped, that's a restart loop.

On a fresh install this is harmless. What got my attention is when the error shows up during an upgrade: on the new major's first start, after the old cluster has been dumped, moved or deleted. My tool's major upgrade did exactly that: dump, remove the old volume, start the new cluster with the instance's settings, restore. With io_workers in the settings, the new cluster wouldn't start and the only way back was the pre-upgrade backup. It worked as designed, but it's not a fun place to end up.

postgres -C prints one setting and exits without starting a server. It still parses everything you pass, so it works as a validator. You don't need a data directory with a cluster in it:

If you use a postgresql.conf file instead of -c flags, mount it and point config_file at it. You even get the line number:

It also catches bad values (wrong units, out of range), not just unknown names. It won't catch a shared_preload_libraries entry the image doesn't have, rules that involve two settings at once, or not having enough shared memory. Those still only show up on a real start.

Settings you applied with ALTER SYSTEM live in postgresql.auto.conf in the data directory. pg_upgrade doesn't carry them over, but if you copy that file across by hand, check it too.

These don't stop anything from starting. They just behave differently.

max_locks_per_transaction went from 64 to 128, and the number means something different. The lock table is allocated differently in 19. The release notes say settings "must now be doubled to match their capacity in previous releases". If you never set it, you're fine, since the default was doubled for you. If you raised it to 256 for a schema with thousands of partitions, set 512 on 19 or you'll get roughly half the capacity you had.

JIT is off by default. The release notes say the costing that decided when to JIT turned out to be unreliable. For OLTP this is probably a small win. If you run big analytical queries and they got slower after the upgrade, try jit = on first.

MD5 password logins now log a warning. MD5 was deprecated in 18. In 19 every successful MD5 login warns (md5_password_warnings = off silences it). The real fix is to move those roles to SCRAM. Find them:

then reset their passwords while password_encryption = scram-sha-256 (the default since 14). You'll usually find them in old images and old pg_hba.conf files.

standard_conforming_strings is always on. A dump made by an older pg_dump with it off won't load correctly into 19.

When you move data across majors, use the new version's pg_dump/pg_dumpall. That was always the advice, and with the change above it's now required. In Docker it's easy, because you can run 19's client against the old server without installing anything:

I ran this 17 -> 19 with a test database and got all rows back on PostgreSQL 19.0 (Debian 19.0-1.pgdg13+1). Expect a harmless role "postgres" already exists error. For anything big, use pg_dump -Fc per database and pg_restore -j instead of one big SQL stream.

If you'd rather use pg_upgrade, 19 refuses to upgrade a cluster that has any of these, so check before you schedule downtime:

After pg_upgrade, the notes also recommend reindexing full-text-search and pg_trgm indexes on ICU/builtin-locale databases, and anything that uses the fuzzystrmatch functions, since their character handling changed.

The tool I mentioned is oddk. It runs Postgres containers on a single Linux host and handles snapshots to S3, alerts, and major upgrades. As of v0.1.97 it supports 19, and its major upgrade runs the postgres -C check above before it touches anything. MIT licensed. If you self-host Postgres on one box and don't want to write the cron jobs yourself, take a look.
