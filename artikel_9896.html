Actualiza tu dashboard cuando cambia un recurso Azure: Event Grid, caché y reindexación segura

Tanggal: 2026-11-20

Posted on Nov 20 • Originally published at danieljsaldana.dev on Nov 20

Un dashboard de infraestructura que consulta Azure cada pocos minutos tiene un intervalo incómodo: puede enseñar un recurso que ya no existe, no mostrar uno recién creado o conservar unas tags que acabamos de cambiar.

En Goliat Dashboard quería mantener el inventario en caché para no pedir a Azure Resource Manager los mismos datos en cada navegación, pero sin aceptar que el usuario tuviese que esperar al siguiente polling. Azure Event Grid encaja muy bien como señal de cambio.

La idea de este post es pequeña y reutilizable:

Event Grid no es la fuente de verdad del inventario. Sólo avisa de que debemos volver a consultar Azure de forma controlada desde el servidor.

Un despliegue de Terraform puede crear, modificar o borrar muchos recursos en pocos segundos. Lanzar una reindexación completa por cada evento sería tan ineficiente como consultar Azure constantemente desde el navegador.

Así el dashboard deja de servir datos viejos, pero tampoco se satura cuando una operación genera decenas de notificaciones.

El código mantiene un segundo filtro. Es importante: la configuración de Azure reduce tráfico y coste; la validación en la API protege el comportamiento si alguien modifica esa configuración más adelante.

No uses subject para construir una URL, ejecutar un comando o elegir una ruta interna. En esta integración todos los eventos aceptados provocan la misma acción fija: refrescar el ámbito de inventario.

En Goliat, Event Grid entrega una cabecera estática que sólo conoce Azure y el servidor:

El secreto se almacena en variables de servidor o en Key Vault. No se publica en React, no se registra y no se envía mediante la URL.

Una cabecera no reemplaza a Microsoft Entra ID en escenarios de máxima exigencia, pero es un punto de partida claro y válido para un webhook. Event Grid también puede usar entrega protegida con Entra ID cuando tu plataforma está preparada para validar tokens. Aquí tienes la guía oficial.

Comprobar Content-Length ayuda, pero una petición puede no incluir esa cabecera. El endpoint debe contar bytes mientras lee el stream.

Esta protección es útil en cualquier webhook externo, no sólo con Event Grid. Primero se comprueba el secreto; después se limita la lectura; sólo entonces se intenta convertir el contenido a JSON.

El siguiente ejemplo está reducido del endpoint de Goliat. Sustituye invalidateCacheScope y scheduleResourceReindex por Redis, una tabla de trabajos, una cola o la abstracción que ya tengas.

La reindexación no debe ejecutarse antes de responder. Event Grid recibe un 202 pronto y el trabajo costoso ocurre de manera controlada fuera del ciclo de entrega.

Una ventana de dos minutos evita que diez eventos de Terraform activen diez inventarios completos. Con Redis, NX garantiza que sólo la primera petición reserva el trabajo.

En un servidor Node persistente puedes retrasar el trabajo con un temporizador. En un entorno serverless, usa una cola, Azure Service Bus, Storage Queue o un trabajo duradero: el proceso puede terminar después de devolver el 202.

La caché debe ser consciente de carreras. Goliat incrementa una generación al invalidar un ámbito para impedir que una petición lenta, iniciada antes del evento, sobrescriba con datos antiguos la caché recién invalidada.

Con esta pieza, el dashboard conserva la velocidad de una caché sin obligar al equipo a esperar al siguiente intervalo de polling. Event Grid señala el cambio; tu backend decide cómo reaccionar; la interfaz sólo recibe un inventario reciente y autorizado.
