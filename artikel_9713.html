A local model can manage a brief question without any issues, but it may have difficulty when dealing with a complete document. The model's internal settings stay the same, but the effort needed and the memory required to process the request increase a lot.

In Part 1, I explained how to run a quantized model on a smaller GPU.

The next step is to choose a task, measure how long it takes, and find a setup that works within the GPU's limits.

This guide uses Qwen2.5-7B-Instruct along with llama.cpp.

It includes memory calculations, a fixed starting configuration, and a Python-based benchmark that you can run on your own computer. The numerical memory estimates are calculated values, and this article does not claim to have measured improvements in GPU performance.

To understand the actual delay you experience, there are two main waiting periods in a conversation. The first occurs when the model processes the initial prompt, often called the prefill phase. The second happens when the model generates the answer one word at a time, known as the decode phase.

If a document takes several seconds to process, fast decoding won't eliminate that initial delay. However, if the first words appear quickly but the rest of the response is slow, then the decoding phase is the area that needs optimization.

A target such as "start a short answer within two seconds" can guide your own experiments. It is a product requirement you choose, not a promised result for every 8GB card.

The model file is only part of the memory requirement. During generation, the runtime also stores attention keys and values for tokens already processed. This KV cache avoids recomputing those states, but it needs memory of its own. Working buffers and other GPU applications need space too. [1]

For a conventional full-attention transformer, an approximate KV-cache payload is:

KV bytes = 2 x layers x stored tokens x KV heads x head dimension

The initial 2 accounts for keys and values. Use the number of KV heads, which can differ from the number of query heads.

Qwen2.5-7B-Instruct has 28 layers, 4 KV heads, and a head dimension of 128, obtained from its hidden size of 3,584 divided by 28 query heads. With FP16 cache elements, the calculation becomes 2 x 28 x tokens x 4 x 128 x 2. [2]

These figures describe one sequence and exclude allocation padding, runtime buffers, and model weights. They are not measurements of total VRAM usage. Other architectures, cache layouts, and attention types need different calculations.

This is why a large advertised context window needs its own memory budget. On this model, moving from 4K to 32K tokens adds about 1.53 GiB of calculated FP16 cache payload. Whether that increase fits depends on everything else already occupying the GPU.

Weight quantization and cache quantization are separate choices. A Q4_K_M model can still use an FP16 KV cache. Reducing cache precision may free up space, but it needs a quality check and a latency measurement. Hugging Face's cache documentation also cautions that cache quantization can hurt latency in some short-context situations. [1]

The shell commands below target Linux or WSL2 with an NVIDIA GPU. Install a working NVIDIA driver, a compatible CUDA Toolkit, Git, CMake, and a C++ compiler first. The benchmark itself requires Python 3.10 or newer and no third-party Python packages.

Save the following script as bench_local.py. It formats the prompt using the server's chat template, checks a declared token budget, performs a warm-up, and records five measured requests by default.

In a second terminal, run it from the folder containing the script and input:

Its ttft_s is a client-side approximation of time to first token: timing starts before the generation HTTP request and stops at the first nonempty content chunk. That chunk may contain more than one token. Template formatting, token counting, model loading, and any document retrieval happen outside this timer.

The script uses the server's token statistics for decoding speed. Counting streaming events would measure chunks, whose boundaries are not reliable token boundaries. The native completion endpoint and its timing fields are documented in llama.cpp. [5]

Prefix reuse is disabled for these comparisons. The model still uses a KV cache within each generation; the setting prevents an identical prompt from being accelerated by a previous request's prefix. The separate warm-up is excluded from the median. Failed or truncated requests stop the experiment instead of producing a successful-looking score.

The --context value is a declared budget, not a command that reconfigures the server. Match it to the server's effective context. The script allows an additional 32-token reserve and records the formatted input token count.

Repeat the test with a realistic document saved in another input file. Keep that file unchanged across configurations. A short fixture helps check the pipeline, but it cannot establish long-document performance.

Restart the server for each configuration, adjusting only the settings listed here. Everything else, including weights, prompt files, output cap, and GPU placement, stays fixed.

Flash Attention is designed to reduce memory traffic during attention computation. It does not remove the persistent KV-cache requirement. [6] A larger physical batch may help prompt processing but can require more temporary memory, so treat E as an experiment rather than a recommended default.

There are two different comparisons to make. Use the same input across A through E to compare configuration overhead. Separately, increase the actual input length to study longer requests. Changing an 8K capacity setting while keeping a 200-token prompt does not simulate an 8K prompt.

Monitor GPU usage in a third terminal: [7]

Stop sampling with Ctrl+C when the experiment ends. These are device-wide samples, including other processes; one-second sampling can miss brief peaks. Use them alongside the server's allocation logs, not as an exact per-request peak measurement.

Compare median first-text delay, decoding rate, total time, and the observed range. Also inspect output lengths and stop_type: an answer that hit the output limit may be incomplete. Five repetitions are an initial check, not enough evidence for a dependable p95 latency claim.

For the Cedar fixture, check that the answer preserves Mira, the date, and duplicate IDs. It should also distinguish an unapproved budget from a known budget amount. A faster configuration that invents an amount fails this task.

Build a small fixed test set from the work you intend to do. Include a question answered by a detail near the end of a document, an extraction task with a required format, and a question whose answer is absent. Save the generated text before changing cache precision or switching to a smaller model.

A useful score is the number of tasks that meet your written acceptance rules. Keep those rules unchanged while comparing settings. Temperature zero reduces sampling variation, but numerical differences across backends and builds can still affect output.

Once the runtime is measured, inspect what the application sends it. A chat assistant can accumulate old turns, repeated instructions, and irrelevant document chunks until most of its context carries little useful evidence.

Once a configuration meets your latency target and quality checks, save its launch command, engine revision, model hashes, prompts, raw responses, and GPU logs together. That gives you a working profile you can revisit when a model update or a new workload changes the results.
