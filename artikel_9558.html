Catching Focus Hidden Under a Sticky Header: A Console Check, and Why elementFromPoint Lies

Tanggal: 2026-11-25

Posted on Nov 25 • Originally published at wasexamprep.com

In the Broken Case 1 of the Focus Not Obscured lab, keyboard focus lands on a link that sits completely under a header pinned across the top of a scroll region. That header is an absolutely positioned overlay, not position: sticky, but it behaves like a sticky header: it stays put while the content scrolls underneath. The lab's VoiceOver on Mac capture for that step (29 June 2026, taken in Arc) reads link, Chapter 3: Focus management checklist. Role and name are right. Nothing on screen shows focus.

The companion blog post explains the rule, WCAG 2.2 SC 2.4.11 Focus Not Obscured (Minimum), and which line of CSS fixes the lab. This article is about testing for it: a manual routine, a console check you can paste into DevTools, a trap I hit on the way, and the mistakes that bring the bug back.

All runs below are one browser (headless Chrome 156), one lab, one day (21 November 2026). The results are real; the conclusions are scoped to them.

2.4.11 says: "When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content." Turned into checks:

The criterion checks the component, not the ring. AA allows partial cover. AAA (2.4.12) allows none.

My first idea for automating this was hit-testing: take the centre of the focused element, call document.elementFromPoint(x, y), and see whether the focused element comes back. If something covers it, the cover should come back instead.

On the broken lab case, with the link fully under the header, elementFromPoint at the link's centre returned the link itself. The header has pointer-events: none, and hit-testing skips elements with pointer-events: none. Visually the header covers the link; to the hit test, the header is not there.

That is not an exotic setup. Overlay headers, gradient fades and decorative bars often get pointer-events: none so clicks pass through them. Any check built on elementFromPoint will report those as not covering anything.

This version ignores hit-testing and compares rectangles. On every focusin it waits two animation frames for the browser to finish scrolling, then samples a 5 by 5 grid of points inside the focused element. A point counts as visible if it is inside the viewport and every scrolling or clipping ancestor, and not inside any fixed, sticky or absolutely positioned element that is not an ancestor of the focused element.

On the lab, with the same steps (scroll to the bottom, focus Continue reading, Shift+Tab), it logged a warning for Broken Case 1 naming the header as the cover, and nothing for Fixed Case 1.

Fixed Case 1 adds scroll-padding-top on the scroll region (scroll-pt-14) and scroll-margin-top on the link (scroll-mt-14), and changes the content's top padding from pt-0 to pt-14. The lab says which one does the work: "pt-14 on the content area offsets the link below the header and is what keeps it visible in this demo." In the 21 November run, removing the padding brought the hidden link back, and removing both scroll offsets did not.

The link is the first item in the region. Shift+Tab scrolls the region to the top, and a scroll container cannot scroll above zero, so no scroll offset can move the first item down. Reserved space can. The lab calls scroll-padding-top "a complementary technique for in-page anchors further down the page". For any item the browser scrolls up to the top edge, it is exactly the right tool. For a page header, put it on the root:

How far a browser scrolls a newly focused element into view is the browser's choice. A layout that hides focus in one browser can pass in another. So test in the browsers your users have, and report what you saw, with the browser and version.
