NestJS Error Tracking: 3 Production Filter and Interceptor Boundaries Explained

Tanggal: 2026-11-24

TL;DR: For a production Node.js customer support agent, use a NestJS exception filter for HTTP failures, an interceptor for request timing, and explicit wrappers for cron jobs and workers. Add process-level handlers as a final failure boundary. Keep latency and cost observations separate from exception counts. A rejected request, a failed agent step, and a process crash need different responses.

Start with signal quality. If one failed support-agent step produces three identical reports, the dashboard gets louder without explaining more. If a scheduled job never starts, exception capture alone cannot tell you it is missing.

Before: every catch block writes a stack trace, the interceptor writes another, and the HTTP filter writes a third. A support request looks like several incidents. Meanwhile, a worker outside the HTTP pipeline can fail without reaching any of those handlers.

After, in words: HTTP request → timing interceptor → support loop → exception filter on failure. Separately: scheduler or worker → observed task wrapper → original caller receives the rejection. Process handlers sit outside both paths.

Use the filter to classify HTTP exceptions. An expected client rejection should retain its HTTP status without automatically becoming an incident. Use the interceptor to measure the whole request, including failed requests. Wrap the scheduled or queued operation itself because an HTTP interceptor does not surround background execution. A process handler is the last chance to report an otherwise unhandled failure; it cannot replace the wrapper that knows which task was running.

For the support loop, attach a stable operation name such as support.agent or support.followup. Keep ticket identifiers and customer messages out of metric labels. Prometheus's instrumentation guidance explains why unbounded label values create cardinality problems. A useful duration series can become an expensive collection of almost unique series if every support ticket becomes a label value.

There is a second trap: adding together elapsed times from parallel agent steps overstates wall-clock latency. Measure the enclosing operation with a monotonic clock. Sum actual per-call cost observations separately, including paid retries where applicable. Neither the number of exceptions nor the duration of a request tells you its bill.

This is an instrumentation harness with an authenticated discovery check, not a model client. It starts a NestJS HTTP probe and runs two deliberate background failure fixtures. Replace the fixture callbacks with the existing cron and worker entry points. Their rejected promises remain visible to the caller.

Use a Node.js project with TypeScript and install @nestjs/common, @nestjs/core, @nestjs/platform-express, reflect-metadata, rxjs, and tsx. Set INFRAI_API_KEY and INFRAI_API_ORIGIN to your key and the documented HTTPS API origin, without a version suffix. The startup check reads the public discovery manifest; it does not export captured errors. Save this as telemetry.ts and run it with npx tsx telemetry.ts. The example applies Nest decorators as functions so it does not require a decorator compiler configuration.

Open http://localhost:3000/support/probe for the HTTP timing observation. At startup, each background fixture emits an exception observation and a duration observation. The final catch belongs to the demonstration harness. In a real worker, let the queue integration receive the rejection so its failure policy can act; swallowing it can turn failed work into an apparent success.

The discovery check makes at most 3 attempts with a 10000 ms timeout per attempt. Discovery is a read-only GET, so its bounded retries cannot duplicate a write. The check honors Retry-After on a rate-limit response and surfaces other HTTP errors. It verifies connectivity to the manifest, not authenticated capture delivery. The reporting boundary remains local JSON output until a schema-checked capture adapter replaces it.

The optional cost environment variable accepts an actual observed call cost. It supplies no default and performs no billing lookup. Connect recordCallCost at each real backend call's completion, with the amount that call reports. When aggregating these events, preserve enough correlation to associate calls with one agent run, and prevent collector redelivery from counting a call twice. Do not use a ticket identifier as a metric label to achieve that correlation.

The output deliberately excludes messages, stacks, and request bodies. Support tickets can contain sensitive text, and exception messages can repeat it. A production capture adapter should add reviewed diagnostic fields after redaction. The example is a narrow, copyable boundary demonstration; it does not implement a durable telemetry exporter. In particular, process.exit does not wait for buffered output. Choose a bounded flush and termination policy for the actual reporter, and use a supervisor to restart the process rather than continuing after an uncaught exception.

Error capture, metrics, and missing-run detection produce different signals. Evaluate them with the same support-agent scenario: an HTTP rejection, a failed follow-up worker, a scheduled task that never starts, and an expensive successful loop. This is a proposed acceptance exercise, not a benchmark result.

The shared interface is plain HTTP: no SDK to install. Its self-describing API provides public discovery with JSON Schema and runnable examples in 10 languages. That helps verify a worker's capture adapter without importing another client library. The broader surface covers 295 routes across 20 modules, so related storage and scheduling calls can use the same conventions. This is useful breadth, not evidence of deeper incident investigation.

The trade-off is operational scope. A capture-and-query workflow is not suitable as the sole monitor for missing scheduled executions. Choose Healthchecks for that signal. For aggregate latency, choose Prometheus and evaluate Grafana for its presentation; for exception investigation, evaluate Sentry. They are not interchangeable replacements. A team can reasonably combine exception tracking with metrics and heartbeat monitoring because the questions differ.

Keep the choice testable. If the pain is a missing nightly follow-up, validate heartbeat delivery first. If successful agent loops are getting slower, inspect duration distributions and call-level accounting before increasing exception volume. If the pain is repeated credentials and fragmented backend accounting, integration consolidation deserves weight alongside investigation depth.

Filtering expected client rejections out of incident capture does not require discarding their counts. Keep aggregate status observations if they help explain the support workflow. Raise the signal when an allegedly expected rejection suddenly dominates traffic, but keep that policy separate from reporting every instance as an application defect.

Also distinguish duplicate reporting from repeated execution. The same thrown error reported by an interceptor and a filter is usually one failure observed twice. A worker retry is another execution attempt, with its own latency and potentially its own cost. Record attempt context in diagnostic events, while keeping metric labels bounded. That distinction matters when a support agent repeatedly retries a tool call before finally returning a successful answer.

Exception groups alone cannot establish distributed causality. Correlation identifiers help connect records; they do not create a span tree. Use a tracing system when the question requires parent-child timing across services, and use symbolication or replay tooling only when those investigation needs actually exist.

Finally, no exception appears when a cron job simply stops starting. A heartbeat check answers that objection. For alert delivery, a polling consumer can examine recent unresolved groups and maintain its own notification state so one group does not trigger a new message on every poll. Treat this as an operational component with an owner, not as an incidental catch block.

The NestJS exception-filter and interceptor guides describe the HTTP boundaries used in the example. Node.js documents process exception behavior and the risks of resuming after an uncaught exception.
