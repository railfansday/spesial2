TC39 `using` Declarations Land in V8 13: What Node.js 24 Developers Get for Free Without TypeScript

Tanggal: 2026-11-14

Posted on Nov 14 • Originally published at jsmanifest.com

This article was written with the assistance of AI, under human supervision and review.

Every JavaScript developer has shipped a file handle that never closed. A database connection that stayed open. A timer that kept the event loop alive.

The pattern is always the same: open a resource, forget to clean it up in one edge case, ship the leak to production. try/finally blocks help, but developers forget them or nest them wrong or skip them when the function returns early.

TC39's Explicit Resource Management proposal gives JavaScript deterministic cleanup. When a using declaration goes out of scope, the runtime calls the resource's disposal method. No try/finally. No manual tracking. No leaks.

V8 13 ships this feature unflagged. Node.js 24 gets it for free. TypeScript developers have been using the syntax since TypeScript 5.2, but the language-level guarantee is newer. Now the runtime enforces it.

The TC39 Explicit Resource Management proposal adds two keywords to using and await using. A resource declared with using must implement a Symbol.dispose method. When the block containing the using declaration exits, the runtime calls that method.

The disposal happens at the end of the containing block, not the function. Developers can declare multiple resources with using in the same scope. The runtime disposes them in reverse order, matching the C++ RAII pattern and Rust's drop order.

The disposal call happens even when exceptions occur. Developers do not need to wrap using declarations in try/finally. The runtime guarantees the cleanup.

Resources that need asynchronous cleanup implement Symbol.asyncDispose instead. Developers declare them with await using. The runtime awaits the disposal before continuing.

The proposal reached Stage 3 in TC39 in March 2023. V8 shipped the implementation in version 13.0, released October 2024. Node.js 24 (the current LTS as of March 2026) includes V8 13.4.

Node.js file handles already implement Symbol.dispose and Symbol.asyncDispose. Developers using Node.js 24 can replace try/finally patterns immediately.

The using version removes the try/finally block and the null check. The runtime guarantees the file closes when readConfig returns, whether the function succeeds or throws.

Multiple file operations in the same function become clearer. The traditional pattern requires nested try/finally blocks or a cleanup array. The using declaration handles both cases.

The disposal order matches the declaration order reversed. Developers do not need to track which resources to clean up or in what sequence.

The try/finally pattern requires explicit cleanup logic. Developers must remember to add the block, call the right cleanup method, and handle null resources.

The using declaration moves the cleanup guarantee to the language. The runtime handles null checks, disposal calls, and error propagation.

Early returns expose the difference. A function with multiple exit points needs cleanup in every path. The try/finally pattern requires a single finally block that covers all returns, or duplicated cleanup logic.

The using version guarantees cleanup without extra code. Developers add new early returns without updating cleanup logic.

Any object with a Symbol.dispose method works with using declarations. The method receives no arguments and returns nothing. The runtime calls it when the scope exits.

The disposal method runs even when the main code throws. Transactions that fail to commit get rolled back. Locks get released. Temporary files get deleted.

Resources that perform synchronous cleanup use Symbol.dispose instead of Symbol.asyncDispose. The runtime calls the method synchronously when the scope exits.

A resource can implement both Symbol.dispose and Symbol.asyncDispose. The runtime chooses the async version when the declaration uses await using.

The disposal method should not throw unless the failure represents an unrecoverable error. When disposal throws, the runtime propagates the error. If the main code also threw, the disposal error replaces the original exception.

The pattern matches how Node.js file handles implement disposal. The Symbol.dispose method calls closeSync() internally. Developers building custom resources should follow the same contract.

Resources that perform asynchronous cleanup need Symbol.asyncDispose. The method returns a Promise. The runtime awaits the Promise before continuing.

Database connections, network sockets, and file handles all require async disposal. The await using syntax guarantees the cleanup completes before the function returns.

Comparison of sync vs async resource disposal patterns

The await using declaration ensures the connection returns to the pool. Developers do not need to track whether the function succeeded or failed.

Multiple async resources dispose in reverse order. The runtime awaits each disposal before starting the next.

The disposal order prevents race conditions. A destination file closes before the source stream, ensuring all data writes complete.

Mixing sync and async disposal in the same scope works. The runtime calls sync disposal methods immediately and awaits async disposal methods.

The runtime disposes resources in reverse declaration order regardless of disposal type. Async disposal awaits completion before moving to the next resource.

V8 13 shipped using declarations unflagged in October 2024. Chrome 131 (stable November 2024) includes the feature. Safari 18.2 (shipped December 2024) supports it. Firefox 135 (planned February 2025) will include it.

Node.js 24 (LTS since March 2026) includes V8 13.4. Developers targeting Node.js 24 can use using declarations without transpilation. Deno 2.1 (shipped January 2025) supports the feature. Bun 1.2 (shipped December 2024) implements it.

Browser support lags server runtimes. Developers shipping client-side code should check caniuse.com for current browser coverage. Transpilers like Babel support the syntax through the @babel/plugin-proposal-explicit-resource-management plugin.

TypeScript 5.2 added support for using declarations in August 2023. Developers using TypeScript get type checking for Symbol.dispose and Symbol.asyncDispose methods. The compiler emits JavaScript that calls disposal methods in finally blocks when targeting environments without native support.

The Node.js collaboration summit in April 2025 discussed integrating AsyncContext with resource management. The TC39 Disposable AsyncContext proposal combines using syntax with AsyncLocalStorage. That feature remains in Stage 1.

Production readiness depends on the target environment. Node.js 24 projects can adopt using declarations immediately. Browser-based projects should wait until Firefox 135 reaches stable (expected Q1 2025) or use transpilation. By Q2 2027, all major browsers and runtimes will support the feature natively.

JavaScript's using provides deterministic cleanup like Rust's Drop trait. The disposal happens at the end of the block, not the function. Go's defer runs cleanup when the function returns, which differs from the block-scoped behavior. The reverse-order disposal matches both languages.

TypeScript compiles using declarations to try/finally blocks when targeting runtimes without native support. The cleanup happens, but the TypeScript compiler generates the code. Developers targeting older runtimes still ship transpiled JavaScript.

V8's native implementation moves the cleanup guarantee to the runtime. The disposal call happens regardless of transpilation. Developers targeting Node.js 24 skip the build step entirely. No TypeScript compiler. No Babel plugin. The runtime enforces cleanup.

The feature eliminates a class of bugs that try/finally blocks fail to prevent. Developers forget to add cleanup code. They nest blocks wrong. They return early without cleanup. The using declaration removes those failure modes.

Database connections stay open. File handles leak. Network sockets time out. These failures happen in production because cleanup logic lives in application code. The runtime guarantee moves cleanup from developer discipline to language semantics.

Node.js 24 makes this guarantee available without TypeScript. Developers running plain JavaScript get deterministic cleanup. The runtime handles disposal.
