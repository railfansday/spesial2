Real records rarely have five fields. Products, trips, and configurations can carry hundreds of attributes, and every user or service filters by a different handful. A key-value lookup is fast when you already know the key. But what is the key when it's whatever combination of attributes someone picked a moment ago?

I first ran into this problem at a global travel company, and again at a global e-commerce company. Different domains, identical shape:

That last point matters. When data is read far more often than written, you can afford to organize it once and reuse that work on every query.

A key-value store answers get(key) in roughly constant time. To search by city, you add a lookup keyed by city. To search by city and stars, you add a lookup keyed by both. If every combination should be a direct lookup, n attributes produce 2^n - 1 of them:

Even if queries never combine more than three of 100 attributes, that is 166,750 lookups, each storing references to the records again and each rebuilt whenever data changes. And each must exist before anyone asks.

Ordered composite indexes soften this, but they work best when a query matches their leading columns. An index on (city, stars, price) does not naturally serve a query on price alone.

You already know the standard answer: build one index per attribute and intersect the results. That is n indexes instead of 2^n.

The catch is that intersection cost follows the size of each matched list, not the size of the answer. Imagine a million hotels, city = Paris matching 40% of them and stars >= 4 matching 60%. To return a handful of results, you still materialize and compare hundreds of thousands of record IDs.

I wanted per-attribute indexes that could be combined without building large ID sets: any combination, chosen at query time, answered in memory.

That search became KiaraDB, first in Java and later in TypeScript.

KiaraDB stores records as paths in a tree, so records that share values share nodes: near the top of the tree, all Paris hotels sit under one Paris node, not a list of a million IDs. Every node also carries a pair of numbers that tells you, with two quick comparisons, whether one node sits underneath another. That is all you need to combine conditions.

You never declare which combinations you'll ask. You declare the fields.

NATIVE keeps decimals such as 4.5 intact. Both libraries also support multi-value fields, dates, stored ranges, typo-tolerant keyword search, and prefix completion.

I described the core algorithm in a 2020 paper, Efficient Storage and Retrieval of In-Memory Static Data. Think of a book's table of contents: chapter 3 spans pages 40-60, so a section on page 45 must belong to chapter 3. KiaraDB numbers its tree the same way.

Here is "Paris hotels with free cancellation," on a tree simplified to two levels:

The city index returns one node, [1, 6]. The cancellation index returns two, [2, 3] and [8, 9]. Only [2, 3] fits inside [1, 6], so h1 and h2 are returned, and Rome's path is never read. No index for "city + cancellation" exists, and none is needed.

Per the paper, preparation is linear in records times attributes, and a query's cost tracks how many nodes its conditions match, not how many combinations are possible. Numeric bands and stored ranges use the same idea, with binary search over sorted keys and interval trees.

I can answer that within one library. An earlier TypeScript engine kept one index per attribute, but merged results as record-ID sets, rechecked the candidates, and scanned numeric and range entries linearly. The current engine, released as kiara-ts 1.2.0, uses the tree and its numbers. Both ran on the same synthetic 100,000-record, four-attribute dataset under Node 24, with five isolated runs per engine:

Selective queries dropped well below a millisecond. Broad queries improved less, because the matching records still have to be assembled. Preparing the data took 0.87 seconds instead of 1.31, with about 14% less memory before text-search caches.

This compares two versions of one library on synthetic data, not every possible index implementation or your production workload. The full benchmark report includes the method and raw results.

It fits read-mostly data that fits in memory, with many attributes and unpredictable combinations: catalogs, inventories, reference data, and layered configuration, queried inside your application process.

It is not durable storage or a transactional database. Updates work by preparing a replacement snapshot and switching to it, which suits data that refreshes every few minutes or hours, not thousands of writes per second. Everything lives in RAM, so measure memory with your own records.

Start with the query your current indexes make awkward: the one combining attributes nobody planned for.
