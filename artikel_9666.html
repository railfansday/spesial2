My scheduler runs on a PC in Pakistan and sends for Toronto office hours. One function keeps the weekday straight

Tanggal: 2026-11-22

The same instant can be a Sunday afternoon in one city and a Monday just after midnight in another. My outreach tool lives on a PC set to Pakistan time and sends email for Toronto business hours, so it has to know which clock is the real one.

If the scheduler had asked the host machine, it would have seen Monday, a weekday, and sent into a Sunday afternoon. This is how I keep it honest.

The send window belongs to the recipient's zone and is written in config, not read from the machine. The config holds a zone name, a start, an end, and a weekdays-only flag:

One function turns an instant into the local weekday and minutes since midnight in the configured zone. Everything else reads from it.

Three details are worth the lines they take.

Because the function takes the instant as an argument, a test passes fixed instants and checks the answer for a fixed zone. No fake clocks, no waiting:

On 2026-11-03 I told the owner a wrong Toronto time. I had read the clock label printed by a shell date command on a Windows machine and trusted it, when the label did not match the zone. The fix was to stop reading any host-side label and ask Intl for the zone I mean. Since then every time shown in a report comes from the same function the scheduler uses.
