From Git Commit to Production: Building a Secure Cloud-Native Platform with AWS, Cloudflare, EKS, and Istio Ambient

Tanggal: 2026-11-24

The image describes Atlas Commerce, a fictional e-commerce platform deployed on AWS. It follows two connected journeys: how engineers deliver a new application version, and how a customer request reaches the application.

The design uses Cloudflare for public DNS, WAF, CDN and tunnel connectivity. AWS hosts the application and supporting services. Amazon EKS runs the workloads, while Istio ambient mode provides workload identity, service-to-service mTLS and selected Layer 7 traffic controls.

The architecture is a proposed design, not evidence of an existing deployment. The traffic weights, identities and connectivity shown are examples that would need to be configured and validated.

The image digest identifies the exact built artifact. Referencing the digest makes it possible to promote the same image from staging to production without rebuilding it at each stage.

The diagram simplifies the pipeline. The actual checks, approval policies, image signing and credential configuration would need to be defined in the workflows.

After a successful build, the delivery process opens a separate change to the GitOps repository, updating the desired image reference.

Once the GitOps change is approved, Argo CD compares the desired configuration in Git with the live state in EKS and reconciles the application according to its sync configuration.

If Helm is used, Argo CD can render the Helm chart into Kubernetes manifests and manage the application lifecycle. Helm and Argo CD therefore serve different purposes: Helm packages and templates the manifests; Argo CD reconciles the desired state.

Terraform appears in a separate lane because it manages infrastructure, not the customer request.

Terraform uses authenticated AWS API calls to create or update resources such as VPCs, subnets, IAM roles, EKS components and supporting infrastructure.

The remote Terraform state must be protected because it contains information about managed infrastructure and can contain sensitive values. The image does not establish the actual state-backend security settings; those must be configured and reviewed.

A customer enters the Atlas Commerce hostname in a browser.

The browser first performs a DNS lookup. DNS tells the client where to connect; it is not itself the path through which the application request is proxied.

The browser then sends an HTTPS request to Cloudflare Edge, where the configured services can provide:

For example, a cacheable product image may be served from Cloudflare without reaching the application. A personalized checkout request should normally be forwarded to the application rather than stored in a shared cache, unless a carefully reviewed caching policy says otherwise.

For a request that needs the application, Cloudflare forwards the request through Cloudflare Tunnel.

The connector, cloudflared, runs inside the AWS environment. It initiates outbound connections to Cloudflare and keeps them available for requests and responses.

The response follows the reverse logical path:

The customer does not connect directly to the private NLB. Cloudflare uses the connections already established by cloudflared to reach the private origin.

The diagram separately shows how cloudflared establishes its outbound tunnel connection:

The NAT Gateway is in a public subnet. The Internet Gateway is attached to the VPC boundary. The private subnet needs a route to the NAT Gateway, and the public subnet needs a route to the Internet Gateway.

The established connection carries tunnel traffic in both directions. NAT is not an application hop between the NLB and the Kubernetes pod.

After receiving the request from the tunnel, cloudflared connects to internal NLB A.

Despite being associated with the customer-facing route, the NLB is private. “Public route” describes where the request originated; it does not mean the NLB has to be internet-facing.

In the selected design, the NLB forwards TCP traffic to the Istio ingress gateway. The gateway handles the configured TLS and application routing.

Not every caller needs to enter through the public Cloudflare path.

An approved internal service or on-premises system can use a separate private route:

NLB B and the private ingress gateway are separate entry points. This allows the platform team to apply different access policies, scale the gateways independently and reduce the impact of a change to one ingress path.

The private route does not pass through Cloudflare WAF. It therefore needs its own network restrictions, authentication, authorization and monitoring. Private connectivity alone does not prove that a caller is authorized.

Separate gateways also do not make the two paths fully independent: they still depend on shared application workloads and data services.

The design separates workloads by purpose:

This separation helps establish different network boundaries and access policies. It does not automatically make the workloads secure: routes, security groups, Kubernetes policies and service authorization still need to be configured.

An AWS Transit Gateway connects the VPCs through separate attachments.

For example, an application workload may need to reach a monitoring endpoint in the Observability VPC. Its subnet route table must send the relevant destination CIDR to the Transit Gateway. The Transit Gateway must then have a suitable route to the destination attachment, and the destination must have a valid return path.

A route establishes a possible network path. Security controls determine which connections are allowed to use that path.

The diagram is a high-level view. Transit Gateway route-table associations, propagation, subnet routes and return routes must be designed and tested explicitly.

The application runs in Kubernetes pods on EKS worker nodes in private subnets.

The Frontend, Order Service and other application components are workloads within the cluster. Amazon RDS is a separate managed database service in the Application VPC’s data subnets; it is not an EKS pod.

Atlas Commerce needs services to communicate securely without requiring every application team to build its own certificate and mTLS implementation.

For a destination enrolled to use a waypoint, the conceptual path is:

The ambient proxies use HBONE with mTLS for the relevant proxy-to-proxy connections. The waypoint applies configured Layer 7 rules for the traffic it receives.

The application-to-local-ztunnel redirection should not be described as a separate remote HBONE mTLS session. The protected connections are between the relevant ambient proxies.

That matters when writing authorization policies. A policy that expects the destination ztunnel to see the original Frontend identity may behave differently from what the engineer intended.

Suppose the team releases a new Frontend version.

Rather than immediately sending all traffic to the new version, an HTTP routing rule could specify:

For traffic that actually reaches the waypoint, the waypoint applies the configured Layer 7 split and forwards requests to the appropriate version-specific backend.

The waypoint does not build the image, create the pods or decide by itself whether the release is successful. A human or a properly configured progressive-delivery controller must assess the release and coordinate changes to the routing weights.

There is an important configuration condition: ingress traffic does not automatically traverse the destination waypoint. If the public or private ingress path must use the waypoint’s canary rules, that path must be explicitly enabled and verified for the selected Istio version.

A waypoint also needs an appropriate authorization policy if bypassing it would bypass a mandatory Layer 7 security control.

The diagram shows workload identity alongside ambient mTLS.

A SPIFFE ID is an identity URI associated with a workload identity. An example for the Frontend is:

An X.509-SVID is a certificate that carries the SPIFFE ID in its URI Subject Alternative Name. The associated key and certificate allow the proxy to prove the identity during mTLS.

For example, stable and canary pods can share the same workload identity if they use the same Kubernetes ServiceAccount. A new version does not automatically receive a new SPIFFE identity.

When the Order Service needs database information, it connects to Amazon RDS for PostgreSQL:

The database is in isolated data subnets, separate from the EKS cluster.

Database TLS must be configured separately. Istio ambient mTLS between meshed application workloads should not be assumed to automatically provide PostgreSQL TLS to RDS.

A Multi-AZ database configuration can improve resilience, but it does not by itself guarantee zero downtime or zero data loss for every failure scenario.

The application may also need AWS services—for example, a secret from Secrets Manager or an invoice from S3.

The proposed design uses EKS Pod Identity:

The Pod Identity Agent and EKS Auth service supply temporary credentials for the associated role. The application uses a supported AWS SDK to obtain and use those credentials.

The customer does not inherit this IAM role. The application must first decide whether that customer is allowed to perform the business action, then use its own workload permissions to access AWS.

Suppose the customer requests an invoice stored in a private S3 bucket using SSE-KMS.

The application needs the applicable s3:GetObject and KMS permissions. For SSE-KMS, S3 performs the server-side decryption; the application does not receive the KMS key and manually decrypt the stored object.

The diagram also shows Secrets Manager and private endpoint concepts. Their endpoint, IAM, resource-policy and KMS configurations are implementation details that still need to be defined.

The image includes monitoring and operational controls because building the request path is only part of operating the platform.

A production implementation should be able to answer questions such as:

Useful signals include application request rate, latency, error rate, gateway and proxy resource usage, database health, queue depth and certificate expiry.

The image shows a target for resilience; it does not prove that replica placement, HPA, PodDisruptionBudgets, alerts, failover or recovery tests have been implemented.

A new Order Service version starts as a pull request. GitHub Actions tests and builds it, then publishes an image to ECR. An approved GitOps change references that image, and Argo CD reconciles the desired state into EKS.

The customer opens Atlas Commerce. Cloudflare receives the request, applies the configured edge controls and forwards the request through the established tunnel to the private AWS origin. The internal NLB and Istio ingress gateway lead the request to the application.

When the Frontend calls Order, Istio ambient uses workload identity and mTLS for the enrolled service path. A waypoint can apply the configured HTTP routing rule, including a canary split, if the relevant traffic is routed through it.

The Order Service reads or writes PostgreSQL data, returns a response, and the response travels back through the gateway, tunnel and Cloudflare to the customer.
