Getting the LiteLLM proxy and MCP gateway running: the steps that work today

Tanggal: 2026-11-28

I installed LiteLLM 1.110.1 on the day it came out and followed the CLI quickstart and the MCP gateway page exactly as written. The proxy had changed faster than the docs. A master key is now required, a few sample requests predate that, and the example model is gone upstream. I hit nine walls before everything worked.

This post is the version of the quickstart I wish I'd had. Each step is the one that works today. Where the docs say something different, there's a note on what you'll see if you follow them, so you can recognise the error when you hit it.

Tested on: LiteLLM 1.110.1 (19 Nov 2026) and again on 1.111.0 (28 Nov 2026). macOS, Python 3.12. Every command below was run on 1.111.0.

You'll end up with: the LiteLLM proxy on port 4000, a working chat request, and the MCP gateway serving tools from an HTTP server, an SSE server and a stdio server.

The proxy now refuses to start without one. The CLI quickstart doesn't mention it, so the first command on the page exits with:

The error itself is good. It tells you exactly what to run.

Don't use sk-1234. It's the sample key in a lot of older LiteLLM examples, and the proxy rejects it on purpose as "a publicly known default". Generate a real one.

The quickstart uses huggingface/bigcode/starcoder. Hugging Face's router doesn't serve that model any more, so the request comes back as:

followed by about 300 lines of HTML. That HTML is the huggingface.co home page. It's labelled as an auth error, so you'll probably start checking your Hugging Face token, like I did. The token is fine. The model is gone.

(Use "model": "ollama/llama3.2:3b" if you started with Ollama.)

The curl on the quickstart page has no Authorization header, and the OpenAI Python sample passes api_key="anything". Both were written before the master key was required, and both now return:

Skip litellm --test. The page tells you to run it in a second shell. Without an argument it crashes with ValueError: Invalid test value. --help says it takes a URL, but litellm --test http://0.0.0.0:4000 gives Unknown command: http://0.0.0.0:4000, because click reads the URL as a command instead of the option's value. The curl above does the same job.

I used three kinds of MCP server: DeepWiki over streamable HTTP (the one the docs use), the official filesystem server over stdio, and a small SSE server I wrote with the mcp SDK, so I could check the SSE path against something I controlled.

Without this, stdio servers are disabled. The proxy logs one warning at startup:

After that, nothing else tells you. The server is missing from the tool list, and GET /v1/mcp/server shows "status": null for it, the same as for the servers that work. The docs say a disabled stdio server is reported as unhealthy. It isn't. If a stdio server's tools are missing, check this flag before you debug the server.

Two lines in that file are there because of the docs.

transport: "sse". The Zapier example on the MCP page is a URL ending in /sse, with the comment # SSE Server and no transport key. The same page says transport "defaults to http in config.yaml". Both are true, and together they break. With no transport, the proxy talks HTTP to the SSE server and logs:

The server's tools never show up, and calling one returns Tool ping not found. Adding transport: "sse" fixes it.

The alias target. The page's mcp_aliases example maps deepwiki to deepwiki_mcp_server, but the DeepWiki server defined on the same page is called deepwiki_mcp. If you copy both, requests using the alias fail with a 403:

That reads like a permissions problem, so I went through key settings first. The real problem is that the alias points at a server that doesn't exist, and nothing warns you at startup. If you see this error, put the alias target and the server name side by side.

With the config above this returns 20 tools: 3 from DeepWiki, 1 from the SSE server and 16 from the filesystem server. The Bearer prefix is optional on this header. Both forms work.

To get one server's tools over REST, add ?server_id=deepwiki_mcp. The x-mcp-servers header doesn't filter this endpoint. It does filter the MCP endpoint at /mcp, where x-mcp-servers: deepwiki (the alias) returns only DeepWiki's three tools. There the tool names are prefixed with the alias, as in deepwiki-read_wiki_structure.

This returns the table of contents of LiteLLM's own DeepWiki. server_id takes the server name or the alias, and it's required on this endpoint, even if you use a prefixed tool name.

I tested the gateway directly, over REST and the /mcp endpoint, because that's where the config and docs problems were. I didn't put a model in the loop with /v1/responses and server_url: "litellm_proxy". Doing that with the Ollama model from step 2 is next.

Found on 1.110.1 and re-checked on 1.111.0 against the docs as of 28 Nov 2026. Each is a small docs change, and a few have a product fix that would have saved me the most time.

Already fixed: on 19 Nov, the REST docs said server_id was optional with a prefixed tool name, but the endpoint required it. The REST page now lists server_id as required, so the docs and the endpoint agree.

Once I got past these, the gateway was solid. Most of the fixes are one line each.
