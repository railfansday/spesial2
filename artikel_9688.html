Go Module Verification Has a Private-Module Blind Spot

Tanggal: 2026-11-18

Go's module system uses go.sum files and the public checksum database to make repeated downloads of a module version reproducible. A downloaded module can be checked against a recorded hash, and the checksum database supplies a signed, append-only record for public modules. The model is strong for public dependencies. It becomes more nuanced when an organization introduces private module paths and internal proxies.

The Go modules reference states that when a module is matched by GOPRIVATE or GONOSUMDB, or when the checksum database is disabled with GOSUMDB=off, the go command accepts the hash and adds the file to the module cache without verifying it against the public database. The build can still be reproducible if go.sum already contains the expected hash. The first download of a private module depends on the private source and the organization's controls around it.

For a public module, the default GOPROXY points to the Go module mirror and then to direct. The checksum database verifies newly added sums, and the module cache records downloaded content. If a proxy mirrors the checksum database, the go command may use that mirrored data instead of connecting to the public service. The proxy becomes part of the trust path and should have its own integrity, availability and access controls.

For a private module, GOPRIVATE acts as a default for GONOPROXY and GONOSUMDB. A private module can be fetched through an internal proxy, directly from a version-control server or from a local replacement. The checksum database cannot compute hashes for content it cannot see. The organization needs a private source of truth for the expected commit or artifact, plus a review process for the first version that enters the build.

Do not use GOSUMDB=off as a convenient fix for a proxy problem. It disables checksum verification for every module that is not already recorded in go.sum, which is broader than the private path that caused the failure. GOINSECURE is also not a general integrity bypass: the documentation says it permits insecure fetching for direct dependencies, but it does not by itself disable checksum database validation.

A replace directive can point a module to a local directory, a fork or a different version. That is useful during development and dangerous when it enters a release build without review. The release pipeline should inspect the effective module list, including replacements, and reject a path that is outside the approved source set.

The same review should cover pseudo-versions and local module cache state. A pseudo-version identifies a commit, but the build still needs a trusted mapping from that commit to the source repository and the expected content. A cache check is useful evidence, but it is not a substitute for a policy about which source is allowed.

go mod verify checks that cached module files and extracted directories have not changed since they were added to the cache. The Go reference warns that it does not download missing modules and does not use go.sum to verify module content. A clean cache after a build can therefore be consistent with a bad first download. Record the source, version and hash that the build actually used.

Configure a private proxy with authenticated access, immutable version storage and audit logs. Protect the credentials used by CI so that a compromised job cannot publish a new private version. Require review for module path changes, new replacements and first-time private dependencies. Run the same configuration in developer and CI environments so that a local GOPRIVATE setting does not hide a production path.

Go's checksum design does not claim to decide whether a dependency is appropriate. It protects the identity of a module version against later substitution. The operator still needs dependency review, source authorization and a policy for modules outside the public transparency log.
