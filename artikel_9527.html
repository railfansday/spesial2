Digger puts pull-request orchestration in front of Terraform execution

Tanggal: 2026-11-25

Digger is an infrastructure-as-code orchestration tool that runs Terraform or OpenTofu inside an existing CI pipeline. A pull-request comment can trigger a plan or apply workflow. The orchestrator handles webhooks, job state, plans, locks, and the link between a repository event and a CI run. That control plane can influence cloud infrastructure even when the actual Terraform process runs elsewhere.

The ZoomEye fixed sample on November 26, 2026 used page 1, page size 1, and sub_type=all. app="Digger" returned 1 match. title="Digger" returned 2,988. The title is a common word and may describe construction equipment, projects, or unrelated pages. The application result is narrow but still requires product-context verification.

Terraform applies are risky because they can change IAM, network, storage, and compute resources. Digger's design takes a plan generated in CI and coordinates the approval and apply steps. The orchestrator needs to know which repository, pull request, commit, project, and environment the plan belongs to. If an attacker can alter that mapping, a plan for one change can be applied in the wrong context or approved by the wrong actor.

The project's self-hosting architecture separates the orchestrator from the CI workflow and uses a token service for Terraform authentication in newer designs. A self-hosted instance also involves GitHub or GitLab webhooks, cloud state backends, and provider credentials. Each of those connections carries identity and authorization decisions.

Confirm that webhook requests are authenticated and tied to the intended repository. Validate the event type, installation or organization, pull-request number, commit, and workflow identifier. Reject duplicate or stale events. Do not treat a comment as authorization unless the commenter's repository role has been checked.

Review the CI workflow that Digger launches. A plan and apply should use separate credentials or separate trust conditions. Production applies should require an approval that is independent of the user who requested the plan. Limit the cloud role, state backend, and secret scope available to each project.

Inspect the page for a Digger UI, API, or documentation endpoint and confirm the owner. The title count is too broad for a product conclusion. The application value may be a genuine match, a coincidence, or a product page that is not an active orchestrator. ZoomEye's count-only evidence cannot decide that field.

For a confirmed deployment, record the version, webhook source, CI provider, repository scope, token-service design, state backends, lock storage, and administrator accounts. Check whether the orchestrator can be reached from the internet and whether the webhook path has a secret or signature check.

Terraform plans can contain sensitive values. Lock records can block or redirect a deployment. Review who can read a plan, who can cancel a run, and who can release a stale lock. Do not place plan artifacts in a broadly readable bucket or artifact repository. Use short retention and encrypt at rest.

Separate the Digger administration interface from the webhook receiver. Give each a network policy and an owner. Monitor failed signature checks, repeated webhook deliveries, unusual repository identifiers, and applies outside the expected branch or environment.

The paired result is a useful caution: one exact application match cannot be treated as one confirmed orchestrator, and 2,988 title matches cannot be treated as a population of Terraform managers. ZoomEye can find a candidate endpoint. The security decision depends on the repository binding, the webhook identity, and the cloud role behind the run.

Digger is valuable because it moves infrastructure decisions into a review workflow. That workflow becomes the control plane. The exposure review should make sure the plan, approval, and apply are bound to the same trusted context.
