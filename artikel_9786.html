vLLM production metrics: running an OpenAI-compatible server with Prometheus and GPU monitoring

Tanggal: 2026-11-23

Posted on Nov 23 • Originally published at span.observer

Putting vLLM into production means moving from an LLM that « works on my machine » to an inference service able to absorb hundreds of concurrent requests on datacentre GPUs. Born in a lab at the University of California, Berkeley and now hosted by the PyTorch Foundation, vLLM is one of the most followed open source projects on GitHub for serving language models. This guide covers the vLLM production metrics that matter, alongside the OpenAI-compatible server and GPU monitoring.

Its strength rests on two ideas: PagedAttention, which manages the key-value cache (KV cache) memory in pages, the way an operating system manages virtual memory, and continuous batching, which inserts new requests into the running batch instead of waiting for it to finish. The result: much better utilisation of GPUs, which are expensive.

For an SRE, vLLM has another quality: it natively exposes a rich Prometheus endpoint and can emit OpenTelemetry traces. Let us see how to install it, run it as an OpenAI-compatible server, then monitor it all the way into Dynatrace.

Its limits: it assumes a serious GPU, its startup time is long (loading weights, compilation, memory pre-allocation) and its many settings require some experience. For a developer workstation, Ollama locally or llama.cpp are lighter.

The vllm serve command starts the OpenAI-compatible server, on port 8000 by default. For a gated model on Hugging Face, first export a token in HF_TOKEN:

--gpu-memory-utilization sets the fraction of GPU memory vLLM allows itself, --max-model-len limits the context length (and therefore the KV cache size), and --tensor-parallel-size spreads the model across several GPUs. The full list of options is available with vllm serve --help.

In production, replace latest with a specific version. On Kubernetes, the documentation offers deployment examples and community charts; allow a generous startup probe, as loading a large model takes several minutes.

The server publishes its metrics in Prometheus format on /metrics, prefixed with vllm:. The exact names changed with the move to the « V1 » engine: check them by querying your own instance (curl localhost:8000/metrics) and the « Metrics » page of the documentation. The families to track:

These application metrics are read alongside GPU metrics: utilisation, memory, power and temperature, provided by NVIDIA’s DCGM exporter (deployed by the GPU Operator on Kubernetes) or by a host agent.

vLLM logs to standard output the model loading, the memory allocated to the KV cache and, periodically, a summary of throughput and cache usage. On Kubernetes, these logs are collected like those of any other pod.

For traces, the server accepts an --otlp-traces-endpoint option that sends one span per request to an OTLP collector, with attributes inspired by the GenAI semantic conventions (model, tokens, time in queue, TTFT). The required OpenTelemetry packages must be installed separately; the documentation provides a complete example. If the calling application propagates W3C context, the vLLM span attaches to the end-to-end trace.

The simplest route is an OpenTelemetry Collector that scrapes /metrics, receives OTLP traces and exports everything. Dynatrace expects OTLP metrics with delta temporality: the cumulativetodelta processor converts cumulative Prometheus counters.

The token must carry metrics and traces ingest permissions. On Kubernetes, Dynatrace can also scrape annotated Prometheus endpoints directly; check its documentation to choose between the two approaches. Once the data is in Grail, a few dashboards are enough: p95 TTFT, waiting requests, KV cache usage, tokens per second and GPU utilisation per node. The principles of histogram-based SLOs, detailed in our article on histogram metrics with OpenPipeline, apply directly to TTFT.

A CPU mode exists for some platforms, but vLLM is designed for accelerators. Without a GPU, llama.cpp or Ollama are better suited.

vLLM provides the throughput needed to serve open LLMs at scale, and it has the good sense to be observable straight after installation. By bringing its Prometheus metrics, its OTLP traces and GPU metrics together in a single backend, you can run inference like any other critical service.
