Context-Generic Programming (CGP) v0.8.0 - cargo-cgp, new documentation, and namespaces

Tanggal: 2026-11-18

Context-Generic Programming (CGP) v0.8.0 is out! This release is about making CGP easier to learn and maintain. It introduces cargo-cgp, a new tool for one of CGP's longest-standing problems: compile errors that describe the code the macros generated rather than the code you wrote. cargo-cgp explains those errors in your terms. When a provider needs a field your type lacks, for example, it can tell you which field to add, and the expanded documentation explains why the provider needs it. Later, as your application grows, the new namespaces let you choose the providers for a whole group of components in one wiring entry.

CGP is a language extension for Rust, with pluggable trait implementations at compile-time. It is an ordinary library on stable Rust: applications select providers through wiring that resolves to static calls, and you can adopt it one component at a time. The Overview explains the model.

I'll start with cargo-cgp and the new documentation, then work through namespaces using a social-media application. The namespace walkthrough is the longest part, so you can read the tooling and documentation news on their own if you prefer. Allow about 35 minutes for the full post, including the code, or jump to the section you need:

Since CGP began, verbose and confusing compiler errors have been one of the largest obstacles to adopting it. Leave out a field or a component binding, and the error message can name a generated trait or show a field name encoded as a Rust type. The compiler checks the Rust produced by macro expansion, so its explanation can be far removed from the code where we made the mistake.

For a newcomer, that can mean learning advanced Rust traits and generics, along with CGP's internals, just to diagnose a small mistake. You might understand the program you are trying to write and still have little idea why it does not compile. Because the difficulty lies in how the compiler reports the expanded code, better syntax alone cannot address it.

So I built cargo-cgp v0.1.0, CGP's new error toolchain, to report those errors in terms of the code you wrote. cargo cgp check checks CGP code and explains a missing dependency through the fields, components, and providers involved, leading with the root cause. It does not yet reshape every class of error, though, so some still reach you in the compiler's own words. When you want to look deeper, cargo cgp expand shows the Rust that the macros generated.

Let's try it on a small mistake from the area-calculation tutorial. We have an area provider that multiplies width by height, and a Rectangle that supplies only width. Here, the rectangle itself is the context: it is the value the operation acts on, and its fields supply the provider's inputs.

To produce this explanation, cargo-cgp wraps a nightly compiler and uses the Rust compiler's API to inspect the failed dependencies. It can follow their chain using information that would be difficult to recover from the printed diagnostic alone. That access is why the tool has its own compiler-linked driver.

With cargo and rustup available, you can install the tool and set up its compiler-linked driver, then check your own project. The install needs Rust 1.96 or newer, and the tool is tested on Linux only so far:

cargo cgp setup installs the tool's pinned nightly and builds the matching driver. That nightly runs only cargo-cgp's checks, so your application keeps its normal toolchain for ordinary cargo builds. CGP itself still compiles on stable Rust, and you can use it without installing cargo-cgp at all.

Use plain cargo to build, run, and test applications. cargo-cgp supplies check for diagnostics and expand for reading the Rust generated by macros, with CGP's type-level constructs restored to readable notation. The installation guide covers setup, updates, and the Nix alternative, and the cargo-cgp v0.1.0 release notes list what this first release supports.

The release also introduces namespaces, for grouping components as an application grows.

When an application has only a few components, writing out its delegate_components! table is straightforward. Each time we split behavior into another component, though, we add a routing entry. Eventually, someone opening the application has to sort through a long list of bindings before they can see which ones belong together. The implementations have become more reusable, but the configuration has become harder to follow.

I have tried a few ways to address this difficulty. Provider bundles collect implementations, but applications still have to list the components they forward to each bundle. The earlier preset system reduced some repetition too, with limitations I will return to below.

With namespaces, we can now give those groups names and select their implementations together. I'll work through a social-media application whose production and test configurations share a PostgreSQL-backed core but use different content filters. By the end, that difference will be visible in one wiring entry.

If you have already maintained a large wiring table, you may prefer to jump to the namespace syntax or the migration guide. Otherwise, let's start with the small application and see how its wiring grows.

Suppose we are building a social-media service that manages users and posts. We need a database handle and a place to choose the implementations the service uses, so our context will represent the application. The wiring has grown along with the dependency tree. Each context now has four entries, so the two contexts together already have eight to keep in step, even in this small service.

Adding CanCensorUsername to the user manager looked straightforward. But that bound belongs to the whole PostgresUserManager implementation, so even get_user now requires a context with a censor. Retrieving a user never runs the filter. The dependency arrives because retrieval and creation share a provider. The post manager has the same problem with spam detection, and every unrelated dependency we add makes the managers harder to maintain and test.

As we add operations, the domain boundaries become less obvious too. get_user_profile_picture might fit in the user manager, but it could need an entirely different set of dependencies. get_user_posts concerns both users and posts. Naming a manager after an entity does not settle which operations are useful to group together.

There is also a reason to keep the caller's interface narrow. Deleting a user is destructive, and we may not want every piece of code that works with users to be able to do it. Yet if we added delete_user to the manager, even generic code that only retrieves users would gain access to deletion. Giving retrieval its own trait lets that code ask for exactly the operation it needs, and nothing more.

Splitting the managers took our wiring table from four entries to nine, and a real application might have dozens or hundreds. Imagine opening that table for the first time. To learn how the application handles users, you have to pick the user bindings out of the list, and everything else reads as noise that hides what ProductionApp actually does. The application then looks far more complex than it is, which is one reason long wiring tables have made CGP harder to adopt.

The ??? keys are the hard part. Each entry in the table becomes a trait implementation for one key, so UserCreatorComponent: … gives the application one implementation that answers lookups for user creation. A key that stood for all user components would need to produce one implementation per component in the group, and Rust's trait system has no way to expand a single entry like that. So CGP needs another way to recognize a group: either its own lookup rules, or a macro that expands the group into its keys. Namespaces take the first route, but the macro route is worth a look first.

One possibility would be a helper macro that supplied the list of keys for each group. That would let us write a hypothetical table like this:

Here, all_user_components!() would expand to [UserCreatorComponent, UserGetterComponent, UserUpdaterComponent], with corresponding lists for posts and filters. Like the ??? keys above, these helpers are pseudocode rather than supported syntax.

Unfortunately, this runs into the order in which Rust expands macros. Rust expands them lazily, from the outside in, so delegate_components! runs first and receives all_user_components!() as literal tokens. At that point the helper has not expanded, and the component list does not exist yet. The table would need eager expansion, where a macro expands the macros inside its input before reading it, and stable Rust offers no way for a macro to do that. Even if it did, CGP would still have to generate helpers like all_user_components! and export them so that their names and imports keep working in other crates, and Rust's macro system has limited support for that.

My earlier preset system tried to solve the same problem, but it supported only a hierarchy like single inheritance. A context could inherit one preset, such as a user preset, and Rust's coherence restrictions then stopped it from also inheriting an independent post preset. I also experimented with combining several presets through macros, but the lack of eager macro expansion, together with the way imports and aliases resolve inside macro output, made that approach tedious to use.

Those attempts helped clarify what I wanted from the feature: an application should be able to name a group and choose its implementation bundle without enumerating every key. In v0.8.0, namespaces express that choice through trait resolution and paths. Existing preset users can find the conversion in the migration section.

The namespace DefaultNamespace; statement connects these paths to our components. Each component registers a route in the built-in DefaultNamespace, as we will do in a moment with #[prefix], and the statement tells the table to follow those routes. Namespaces are opt-in, so without this statement the table ignores the registered routes. A lookup for UserCreatorComponent, for example, follows a route that begins with @app.core.user, so it reaches the entry that selects PostgresUserComponents. Adding another user operation to the user group therefore leaves this table unchanged. The individual bindings still live in the bundles, while the application chooses only which groups it uses. The selected providers still need their dependencies. Each context must supply the required fields and other traits, and the hypothetical SQLite core would need its corresponding database handle.

Will these providers work together? A delegate_components! block can compile before Rust has checked the providers' dependencies. We can ask Rust to check them now with check_components!, naming the components we need on the concrete application.

Apply the same nine-component check to TestApp and any local variant. Earlier stages need checks matching their components: before splitting the managers, for example, check UserManagerComponent and PostManagerComponent.

The check lists the individual operations, even though the wiring now routes them in groups. A group entry only says where a lookup goes, so the check confirms that every operation we rely on actually resolves. Run it on the real application context, which supplies the database field and the other dependencies. An aggregate provider is only a bundle of implementations, so checking a bundle as if it were the application would ask it for dependencies that only the context can supply.

The namespace documentation explains the lookup model, and the delegate_components! reference covers the path syntax.

So far, we have organized the wiring around choices we might want to change: PostgreSQL or SQLite, production or test filters. Bundles work well for that arrangement. We could add a PostgresWithLoggingCoreComponents variant, for example, and select the logging-backed core in the same place.

But an application starting out with PostgreSQL may have little reason to define interchangeable database bundles yet. Early in a project, developers often prefer one implementation per feature, tied to its interface on purpose, because that keeps the application easy to reason about. If several contexts should always use the same user and post implementations, having each one select those bundles repeats a choice that never varies. We can instead record those choices once in a namespace and leave only the varying parts to each context. These are default implementations.

I see defaults as a way to adopt CGP gradually. Ordinary traits may already be enough for a single-crate application with one implementation of each operation. If that application later needs more modularity, it can move code into CGP components and record its initial provider choices as defaults. Bundles can follow when there are useful groups to swap.

These are alternative ways to register the same binding, so writing both would create a conflict. The namespace body looks like a delegate_components! table, but its choices apply to every context that joins the namespace. We bind the provider at the full path because the bare key is already taken. The route inherited from DefaultNamespace uses UserGetterComponent to send lookups on to @app.core.user.UserGetterComponent, so a second entry for the bare key would conflict with it.

These defaults are fixed choices. Once the namespace binds a provider, a joining context or inheriting namespace cannot override it, even with a more specific entry. A context also cannot disable just one default while retaining the rest of that namespace. So a choice that should vary between contexts belongs on a path the namespace leaves open, as we will do with the filters below.

There is also a constraint on where we write the registration. With a prefixed path, the binding must live in the crate that owns the namespace, here DefaultAppComponents. The path expands to CGP's PathCons type, and owning a component marker nested inside that type does not satisfy Rust's orphan rules. An unprefixed local component marker has different ownership rules, covered by the #[default_impl] reference.

We kept the prefixes in DefaultNamespace and the provider choices in DefaultAppComponents for a reason. Another configuration, such as a SQLite one, can then inherit the same routes without also inheriting PostgreSQL choices it could not override. So the routes belong in a base namespace, and the fixed choices in a configuration namespace that inherits it.

If we later need to replace one of these fixed defaults, we choose a namespace that leaves its destination open. We could return to the base DefaultNamespace and supply the required bindings explicitly, as in the earlier bundle examples.

While the application lives in one crate, #[default_impl] conveniently keeps each binding beside its implementation. Once providers move into crates of their own, that attribute would sit in a crate that does not own the namespace, which the ownership rule above forbids. So we move the bindings into the configuration namespace's body instead, and the namespace's crate assembles the providers from there.

There is room to start with direct wiring, share fixed choices through defaults, and introduce interchangeable bundles as the application needs them. I would choose whichever arrangement makes the current decisions easiest to see, rather than build the full hierarchy in anticipation of future growth.

The removed preset constructs and their replacements are:

cgp::prelude now exports only the names CGP code usually writes: the macros, the derives, PhantomData, and a few traits and providers such as HasErrorType, CanRaiseError, UseType, and DefaultNamespace. The code the macros generate reaches CGP's items through a separate cgp::macro_prelude, so the prelude no longer has to carry those items. If your code names one of the dropped items through the glob import, the compiler reports that it cannot find it, and you import it from its module:

The dropped names come from these modules:

A derive does not need its trait imported, so #[derive(HasField)] still works through the prelude, while a HasField bound or a .get_field() call needs the import. A provider for a handler trait such as Computer imports its key, ComputerComponent, beside the trait, because the provider's header names the key, as Other improvements describes.

Raw compiler output changes slightly as a result. Where v0.7.0 printed a type such as cgp::prelude::Chars, the compiler can now print cgp::macro_prelude::Chars, as in the cargo check comparison above.

The type-level types also lose their Greek-letter names. v0.7.0 declared them as π, ε, σ, θ, ζ, ψ, δ, and ω, with Cons, Nil, Either, Void, Chars, Symbol, Index, and Field as aliases, and the prelude exported both spellings. Only the English names remain, so code that wrote a Greek name switches to the English one, imported from cgp::core::field::types. Raw compiler output changes with them, printing Cons<…> and Chars<…> where v0.7.0 printed π<…> and ζ<…>.

The default features of cgp are now empty, so the library builds without std or an allocator. In v0.7.0, the defaults turned on DebugError and DisplayError, the error providers that format an error into a String. If your wiring uses either, turn on the alloc feature:

A component that generates a UseDelegate dispatcher moves the derive_delegate key of #[cgp_component] into an attribute of its own, one per dispatcher:

A new component does not need either form, because the open statement from Other improvements dispatches it per type.

The extra-feature macro crates are renamed from cgp-extra-macro and cgp-extra-macro-lib to cgp-macro-extra and cgp-macro-extra-lib. Update direct dependencies on those crates. Imports through cgp::prelude keep their names.

Self-contained handler-macro expansions may leave imports unused. Remove imports the compiler reports when they existed only for the old expansion.

#[cgp_auto_dispatch] rejects attribute arguments and typed receivers such as self: Box. It previously ignored the arguments or miscompiled those receivers.

The new Struct! and Enum! prelude exports can make a macro name ambiguous. Qualify the call if another glob import provides the same name.

DelegateComponent, IsProviderFor, HasField, and HasFieldMut no longer carry custom #[diagnostic::on_unimplemented] messages. Plain cargo check now reports an unmet bound on them in the compiler's own wording, and cargo cgp check rewrites those errors into its own summary. If a test compares compiler output, as a UI test does, update the messages it expects.

cgp-error-eyre enables eyre's automatic default-handler installation and tracks the caller of raise_error and wrap_error.

cgp-error-std changes how wrapped errors are displayed. Ordinary Display prints only the outer detail, while alternate Display and Debug include the chain. This avoids duplicated sources when a reporter walks source() itself. Update output assertions that depend on the old formatting.

The minimum anyhow and eyre dependencies rise to 1.0.104 and 0.6.14 respectively. The backend READMEs in the CGP repository describe their use.

We started with two manager choices and ended with applications that could share a core, change their filters, or use a different database. Namespaces let the top-level wiring express those choices even as we split the implementations into smaller pieces. I hope that makes similar refactorings easier to follow in your own projects, with cargo-cgp and the new documentation there to help when something is unclear.

CGP still takes time to learn. Its ecosystem is small, and I still have work to do on the tooling and documentation. My suggestion is to try it on one problem you already have. If you already use CGP, try grouping one area of your wiring while keeping its component checks in place. If you are new to CGP, the Quickstart provides a smaller starting point.
