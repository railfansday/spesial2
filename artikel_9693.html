Make Your Coding Agent Wait 7 Days for New Packages: npm, pnpm, Yarn, Bun and uv

Tanggal: 2026-11-08

Posted on Nov 8 • Edited on Nov 8 • AI-assisted

The malicious chalk release was live for under 12 hours. The Nx one for about 4 hours, rspack for about an hour. William Woodruff lined up ten well-known supply-chain attacks and found that 8 of them had a window of opportunity shorter than a week (his post).

Put your coding agent inside that window. It decides it needs a date library, runs npm install a few seconds later, and the registry hands it the newest version. Nobody has looked at that version yet, including the scanners and the maintainer whose account was phished an hour ago.

The fix is a release-age gate, also called a cooldown: refuse any version younger than N days. npm, pnpm, Yarn, Bun and uv all have one now. They spell it five different ways, in four different units, and one of them does nothing at all on an npm that is a few months old.

Sources for each row: npm 11.10.0 and the npm config docs, pnpm 10.16, Yarn's PR #6901, Bun 1.3, uv 0.9.17.

Get the unit wrong and the gate is either useless or absurd. minimumReleaseAge: 7 in pnpm is seven minutes. minimumReleaseAge = 7 in Bun is seven seconds. min-release-age=10080 in npm is about 27 years.

A cooldown lets a new version sit for a week before anything on your machine is allowed to install it.

In npm, the gate is one line in the project's .npmrc. The current npm 11 config docs also list an exclude key that takes names or globs, for your own packages:

The docs say npm "will build the npm tree such that only versions that were available more than the given number of days ago will be installed", and that if no version fits, "the command will error." If npm audit fix is blocked because the patched version is too new, npm keeps the vulnerable version, warns, and exits non-zero. That is your cue to add the package to the exclude list on purpose.

Only exempt a scope you own on the public registry. The npm config docs say you should own your private scope there "so that nobody else can publish a package with the same name." If you don't, someone else can publish @myorg/anything and walk past the gate. The same goes for the exclude lists in pnpm, Yarn and Bun below.

The trap is the version. min-release-age arrived in npm 11.10.0, released February 11, 2026. An older npm reads your .npmrc, does not know the key, and installs with no gate. From npm 11.2.0 on you at least get an unknown-config warning (npm docs). Before 11.2.0 you get nothing. The file in your repo says 7 days, and nothing on that machine enforces it.

Keep registry tokens in your user-level ~/.npmrc. The project .npmrc is going into git, and from there into every worktree.

pnpm counts in minutes. Since pnpm 11 it reads pnpm settings from pnpm-workspace.yaml and keeps .npmrc for registry and auth only (pnpm 11.0):

pnpm 11 already defaults to 1440 minutes, one day. The detail that matters is in minimumReleaseAgeStrict: it is true only when you set minimumReleaseAge yourself. With the default, pnpm falls back to a version that breaks the age rule when nothing else fits. Set the value explicitly and pnpm fails resolution instead. The exclude list takes names, globs and exact versions like webpack@4.47.0 || 5.102.1.

Yarn calls it an age gate and calls the exclusions pre-approved packages, which take descriptors or name globs:

Yarn keeps the value in minutes: in Classmethod's test, yarn config get npmMinimalAgeGate reported "21d" as 30240. For a range, Yarn installed the newest version that passed, and the gate held for transitive dependencies too. An exact pin that is too new fails with "No candidates found" in the PR's tests.

Bun's docs say it "filters out package versions published more recently than this threshold." Its exclude list takes package names, or name@version to exempt one exact release. The docs show no scope wildcard, so list your own packages by name.

A git worktree is a checkout of tracked files. Nothing ignored or untracked in your main checkout comes along. A setting in your user-level ~/.npmrc reaches every worktree on your machine, but not a teammate's laptop, CI or a container. That is why the gate belongs in a committed file: .npmrc, pnpm-workspace.yaml, .yarnrc.yml, bunfig.toml or pyproject.toml. Any agent that runs an install in any checkout of the repo reads it.

Test the gate on your own machine before you rely on it. The TypeScript nightly makes a good test, because a new build from main is published to npm by midnight PST every day (TypeScript docs). Its newest version is normally less than a day old.

The two npm view calls pass --min-release-age=0 so the gate can't hide the newest version or its publish time from you. The install keeps your .npmrc setting. With the gate working, npm stops with npm error code ETARGET and a notarget No matching version found for typescript@... line that names the cutoff date. That is the error Classmethod got pinning a too-new eslint. If the install succeeds instead, npm -v on the first line tells you why.

The same pin works as a test for the other managers: pnpm add -D "typescript@$v" should fail resolution, since you set minimumReleaseAge yourself. Run it before you trust it.

Know what seven days does not cover. In Woodruff's list, xz-utils had a window of about five weeks, and only a longer cooldown gets near it. A cooldown also delays the good releases, including security fixes, which is what the exclude lists and npm's audit fix warning are for. It doesn't read the code either. It only makes sure someone else got a week to.
