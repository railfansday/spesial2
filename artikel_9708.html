Our Undo Button for Releasing an Elastic IP Was Wrong

Tanggal: 2026-11-11

Posted on Nov 11 • Originally published at cloudcostwise.io

On 2026-11-08 we audited our own fix flow. We found two places where the product said something that was not true. The first one is about a button you hope never to need: Undo.

CloudWise's fix flow can release an Elastic IP address that is attached to nothing. Every fix has a plan, and a plan can carry an undo. For a released address, the undo ran allocate_address.

As we sent it, that call hands out a new address. It does not ask for the old one back. So you got a different public IP, a new charge for it, and a scanner that will flag it as waste on the next run. The plan said "undo". What it actually did was buy a different IP.

We found it by reading our own plans against what AWS really does. It had to go.

The AWS page on releasing an Elastic IP address is careful. After you release an address, "you might be able to recover" it. Then come the rules:

Recovery is possible, then, but only if nobody else has taken the address and you still have room under your limit. A release is not a pause. Whether you get the address back depends on things outside your account. AWS's own recovery call passes the old address to allocate-address. Ours did not.

Recovery is never guaranteed, so we stopped treating a release as something we can reverse.

We do not promise what AWS does not promise. So:

We also changed the approval step. A plan with no undo, and a saving above a small monthly threshold, now asks you to type the resource id before the Approve button works. The match is exact and case sensitive. Bulk approve skips those plans, so each one goes through its own approval. Fixes you can undo keep one-click approval.

The point is that the cost of being wrong should sit next to the button. An irreversible fix is not a bigger version of a reversible one. It is a different decision, and the interface should treat it that way.

Before the fix flow deletes an EBS volume, it takes a snapshot. That is the safety net. We had a problem with it too, and it was the opposite problem.

The snapshot was kept forever, and a snapshot bills for as long as it exists. So the saving we showed for a volume delete was overstated: part of it was quietly replaced by the snapshot's own storage bill. The undo also had a flaw. It recreated the volume with the defaults of the create call, which means no tags and a different type, not the volume you deleted.

Two honest notes, because a post about wrong claims should not make new ones.
