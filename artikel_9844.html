Refresh Tokens e Logout

Tanggal: 2026-11-03

Muitos sistemas de autenticação começam com um único token (o JWT do login), sem refresh token nenhum. Este guia explica, do zero, o que é um refresh token, por que ele existe, como ele muda o que significa "logout", e como isso se encaixa numa arquitetura em camadas típica.

O problema: um token só não dá pra otimizar duas coisas ao mesmo tempo. Quando um usuário faz login, a API devolve um token JWT que vale por um tempo configurado, por exemplo 60 minutos. Esse token é a única prova de identidade que o front-end tem.

Com um token só, você é obrigado a escolher um meio-termo ruim: nem seguro o suficiente, nem confortável o suficiente. A ideia do refresh token é separar essas duas responsabilidades em dois tokens diferentes, cada um otimizado pra uma coisa, ao invés de um token só tentando fazer as duas mal feitas.

O ponto central dessa tabela é a linha "dá pra revogar": um JWT é stateless de propósito, essa é a graça dele, permite validar sem bater no banco a cada requisição. Mas isso tem um preço: ninguém consegue "desligar" um JWT antes da hora. O refresh token existe justamente pra carregar esse fardo: ele tem estado no banco, porque sua função inteira depende de poder ser revogado.

Muitas aplicações front-end guardam tokens no localStorage. Isso funciona, mas tem uma vulnerabilidade conhecida: qualquer JavaScript que rode na sua página consegue ler o localStorage. Se um dia entrar uma dependência npm maliciosa, ou um ataque de XSS (alguém injeta um script via um campo mal sanitizado), esse script consegue roubar o token com uma linha de código que lê o localStorage diretamente.

Pra um access token de vida curta (5-15 min), esse risco é tolerável — na pior das hipóteses, o estrago dura poucos minutos. Mas um refresh token que vive por semanas não pode correr esse risco: se vazar, o atacante tem acesso por semanas, não minutos.

Ou seja: o access token continua vulnerável a XSS (tolerado, pela vida curta), mas o refresh token fica numa caixa que nem o próprio código da sua aplicação consegue abrir — só o navegador e a API.

Tem uma pergunta incômoda no fluxo acima: e se alguém roubar o refresh token (não o access token, o refresh)? Ele vale por 30 dias, isso é um problema sério.

A defesa chama-se rotação de refresh token: toda vez que o refresh token é usado pra pedir um access token novo (passo 4 do fluxo acima), a API não só devolve o access token, ela também invalida o refresh token usado e emite um novo no lugar. Ou seja, cada refresh token só serve uma vez; usar gera o próximo da cadeia.

Por que isso ajuda a detectar roubo? Pensa no cenário: alguém copiou seu refresh token (token A) sem você saber. Duas pessoas agora têm o mesmo token A: você e o atacante. Em algum momento, um dos dois vai usar o token A primeiro — digamos que seja você. Isso gera o token B, e A fica marcado como "já usado". Mais tarde, o atacante tenta usar o token A (que ele ainda tem, achando que ainda vale), a API vê um token já marcado como usado sendo reapresentado. Isso só acontece numa de duas situações: um bug, ou um roubo. Por segurança, a reação correta é tratar como roubo: revogar a família inteira de tokens daquela sessão (A, B e qualquer um que viesse depois), obrigando os dois — você e o atacante — a fazer login de novo. Incomoda você uma vez, mas tira o acesso do atacante.

Isso só é possível porque o refresh token tem estado no banco (volte à tabela comparátiva): sem isso, não teria como saber que um token já foi "gasto".

Num sistema que usa só um JWT, sem refresh token, normalmente não existe endpoint de logout, porque não há nada no servidor pra desligar. O JWT é stateless, então "sair" é só apagar o token do armazenamento local do navegador.

Com refresh token, isso muda: agora existe uma linha no banco representando aquela sessão (o registro do refresh token). Um POST /auth/logout passaria a ter trabalho de verdade pra fazer: marcar aquele refresh token como revogado. A partir daí:

É a primeira vez que "logout" significa revogar algo no servidor, e não só limpar o navegador. Esse é o ganho concreto de ter um refresh token: dá ao sistema um botão de pânico que ele simplesmente não tem pra um logout normal, nem pra reagir a um token roubado.
