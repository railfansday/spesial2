Teaching Your AI Assistant New Skills at Runtime — Without Rewriting It

Tanggal: 2026-11-09

Last post I showed the architecture of my local AI assistant, Xiaoqingting (Little Dragonfly). This one is about the part users actually notice: how the assistant gains new abilities without me shipping a new version.

Say "review this PR properly" or "write me a weekly report" — those are not generic chat behaviors, they're procedures. Procedures belong in prompts, and prompts belong in files. Here's the system we ended up with.

A skill is nothing more than a directory with a manifest and instructions:

SKILL.md is markdown with a tiny front-matter:

At session start, the server scans the skills directory, reads every manifest, and injects a table of contents into the system prompt — name, one-line description, when to use it. Not the full text. When the user's request matches a skill, the assistant reads the full SKILL.md on demand.

My first version injected all skill bodies into the system prompt at once. Three skills in, this was fine. Ten skills in, two problems showed up:

The fix — load manifests always, load bodies on demand — cut the system prompt by ~70% and made skill-following more accurate, because each procedure arrives fresh, right when it's relevant, with nothing else competing for attention.

This mirrors how the big agent platforms converged on the same design (progressive disclosure of instructions), which was reassuring to discover after the fact.

Users shouldn't have to hand-copy folders. So the assistant supports a skills registry — you point it at a URL serving a JSON manifest:

The client shows the list, you tick what you want, it downloads and verifies each pack before mounting. Sets SKILLS_REGISTRY_URL, get a marketplace.

Deliberate scope cut: our registry only distributes pure-markdown skills. No scripts, no executables in skill packs, version one. Every "skills marketplace" that allowed arbitrary code turned into a supply-chain nightmare waiting for a Tuesday. Markdown instructions can still be abused (more below), but they can't rm -rf anything by themselves.

Skills are prompts, and prompts are instructions the model will follow. That makes the skills folder an injection surface, and we treat it like one:

Rule 3 is the one that matters. Skills change what the model says; the tool allowlist changes what it can do. Never let a downloaded file touch the second layer.

I added a "release-notes" skill as a test: given a version range, read the commits, group them by user-facing impact, write notes in a fixed format. It took one markdown file, four minutes, zero code — and the next morning the assistant produced better release notes than the template I'd been copy-pasting for two years.

That's the whole pitch: the assistant's capability list should be data, not code. Ship the engine once; let the skills folder grow forever.

The implementation lives in github.com/lujianfu2008/xiaoqingting — @blm/server has the loader and registry client, and a couple of example skills are in skills/.
