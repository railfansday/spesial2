Multi-Tenant Login Routing: Domain Discovery & Enforced SSO

Tanggal: 2026-11-21

The first enterprise customer's SSO works. Then the second one signs, then a tenth, and the login page becomes the problem. One email box and one password box no longer make sense. A user at acme.com should be sent to Acme's Okta. A user at globex.io should go to Microsoft Entra ID. A freelancer with a Gmail address invited into Acme's workspace should still be able to log in with a password, and Acme's own admin must not be able to bypass SSO by typing a password. All of that has to happen from one email field, without telling an attacker which companies use your product.

That routing step is usually called home realm discovery (HRD). This post covers how I build it in a multi-tenant SaaS app, and how I turn on "enforced SSO" for a tenant without locking anyone out.

I wrote this with help from AI tools and checked the behaviour against the Okta, Microsoft Entra and WorkOS documentation on domain verification and HRD. I am a Principal Software Engineer in Karachi with 9+ years building Laravel, Node and .NET SaaS backends, and everything here is defensive design for your own application.

Direct answer: Ask for the email first, extract the domain, and look it up in a table of verified domains mapped to tenant SSO connections. If a match exists and SSO is enforced, redirect to that IdP; otherwise show the password or social login step. Only map domains proven by a DNS TXT record, and give the same response for unknown and known domains.

I usually ship email-first HRD as the main path, plus a tenant-slug fallback and support for IdP-initiated login.

Never let a tenant admin claim gmail.com, or a competitor's domain, just by typing it. Issue a token and require a DNS TXT record:

Rules I enforce: block a list of public email providers (gmail.com, outlook.com, yahoo.com and so on), store domains lowercased, allow one verified owner per domain, and re-check the TXT record periodically so a lapsed domain does not keep routing.

Email parsing is where routing bugs hide. Alice@ACME.com, alice@acme.com. (trailing dot), alice+test@acme.com and IDN domains should all route the same way, while alice@acme.com.evil.io must not match acme.com.

Always compare whole labels from the right, never with str_contains or an unanchored regex. When I write the matching pattern, I test it against the nasty cases in a regex tester first, and I check redirect targets with a URL parser to make sure the RelayState or returnTo host is ours and not an open redirect.
