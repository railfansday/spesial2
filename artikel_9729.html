SGLang for Multi-Turn Agents: Prefix-Cache Wins, Speculative-Decoding Risks

Tanggal: 2026-11-12

Posted on Nov 12 • Originally published at effloow.com

The production problem I want SGLang to solve is repeated work: an agent sends its instructions, repository context, previous answers, and tool results back to the server on every turn. Much of that prompt has already been processed. Paying to prefill it again wastes capacity that could serve another session.

No GPU server or AgentX traces were run locally, and the retrieved AgentX results are unofficial; validate cache reuse, latency, throughput, and correctness before claiming savings.

SGLang’s RadixAttention makes reusable token prefixes central to serving. Speculative decoding attacks a different cost: generating output by proposing candidate tokens and verifying them with the target model. I evaluate these as separate optimizations, not as one “agent acceleration” switch.

The evidence boundary matters: I reviewed the available installation instructions, launch examples, and AgentX optimization material, but I did not launch a GPU server or replay AgentX traces for this article. I have no local cache-hit, TTFT, or throughput measurements to present. The commands below are reproduction recipes, not a claim of completed deployment.

That distinction is especially important here. The supplied InferenceX AgentX optimization page includes an explicit warning that the retrieved copy is unofficial and its data may be modified or outdated. I use its results as leads for validation, not as a basis for buying fewer GPUs.

My evaluation matrix would separate a cache-disabled control, the ordinary cache-enabled baseline, and cache plus speculation. I would confirm the cache-control option in the pinned build rather than invent a flag. Each arm needs cold-cache and warm-cache runs, plus repeated trials under session churn.

A non-streaming response time is not TTFT. Likewise, textual prefix similarity is not a measured cache-hit rate.

The immediate roadblock in this review was missing execution evidence, not a demonstrated SGLang crash. I could inspect recipes, but I could not establish local performance results or verify a specific vLLM issue. I keep those gaps visible because otherwise the most persuasive part of an infrastructure review becomes fiction.

The technical failure modes still give me a concrete validation checklist.

Window traffic can compete with durable prefixes. In my evaluation, I would stress the shared pool used by sliding-window allocations and prefix pages, where transient window activity can displace reusable history under memory pressure. I would test this with interleaved sessions and enough pressure to force eviction. Repeating one prompt immediately after itself is insufficient.

My mitigation order would be to verify the allocator fixes in the selected build, measure reuse under churn, and then consider offload. Increasing memory allocation without understanding eviction can hide the problem rather than solve it.

Offload has model-specific state requirements. I interpret the hybrid-cache discussion narrowly: full-attention KV can be offloaded while a short sliding-window tail is reconstructed. Recurrent state requires its own checkpointing support; it cannot simply be treated as another reconstructible window.

I would not generalize that path to every supported model architecture.

Host-memory accounting also deserves an explicit budget. For my capacity estimate using the GLM AgentX configuration, I would budget --hicache-size in host-tier GB per rank. At 180 GB across each of four ranks, I would therefore allocate approximately 720 GB for those host cache tiers, not 180 GB for the whole deployment. I would reserve additional host capacity for the operating system and other processes.

Release labels do not prove feature availability. When reviewing the GLM deployment recipe, I found two version gates to check before launch: the dated 2026-10-25 nightly includes checkpoint-loading change #40776, while the v0.5.22 release does not; an AMD monokernel pin predating sgl-amd-mono#60 rejects FP8 KV cache and causes startup to fail.

My workaround would be an immutable image digest and a startup smoke test for the actual checkpoint, attention backend, and KV dtype. A package version alone is not enough.

Speculation changes scheduling as well as decoding. I would not use NGRAM as a neutral, no-extra-weights substitute for EAGLE3. In my comparison, I would account for NGRAM's CUDA-only support, incompatibility with --attn-dp-size > 1, and disabling of overlap scheduling and mixed chunked prefill. That changes the experiment.

Cache correctness must survive transfer. In my correctness review, I identified misplaced cache offsets during heterogeneous-disaggregation staging as a regression case to test. I would use the 127,500-token shared-prefix case, with 2 correct needles out of 128 before the fix and 128 out of 128 afterward, as a validation target. I treat that as an external regression-test lead, not my result or a universal failure rate.

Before introducing disaggregation, I would require correctness tests across cold, partially cached, and heavily reused prefixes. A fast wrong answer does not qualify as throughput.

Finally, I had no specific vLLM issue to inspect, so I cannot identify an affected version or recommend an issue-specific workaround.

My comparison starts with workload fit, not a blanket ranking.

I would not describe this as RadixAttention beating PagedAttention. PagedAttention concerns KV-memory management; automatic prefix caching concerns reuse. A meaningful vLLM comparison must enable and validate the relevant reuse behavior rather than compare a tuned SGLang configuration against an unrelated default.

In my performance review, I separated the externally reported 26.75% output-throughput improvement and 36.25% reduction in mean TTFT at concurrency 384 from speculative-decoding gains: the change replaced context-length-driven kernel specialization with a runtime scalar, reducing compilation overhead rather than accelerating computation. These are not local benchmark results or measured benefits of enabling speculative decoding.

I also treated the FlashInfer GDN recurrent-state checkpointing result—47,771 to 53,004 tokens/s/GPU at 92.4% cache-hit rate—as a separate, configuration-specific comparison. I cannot transfer that result to the Llama smoke-test recipe, a different GPU, or an ordinary chat workload.

For capacity planning, I would use SLO-compliant completed sessions, not peak output tokens alone. For my AgentX replay plan, I would count concurrency as live sessions and track active requests separately, because subagent branches can create multiple simultaneous requests within each session.

Monthly benefit = removed GPU capacity + avoided external inference spend − added operating costs.

For an illustrative budget—not measured SGLang performance—assume:

Removing one continuously allocated GPU saves $2,190 monthly before the added operating costs. Net savings are $1,790, giving a simple payback of about 3.4 months.

But a benchmark improvement does not guarantee that an allocation can be removed. If the service still requires the same replica count for peak demand, failover, or tail latency, immediate GPU-bill savings may be zero.

I would approve the change only after demonstrating that the smaller deployment meets the same TTFT and completion-latency objectives with acceptable correctness and failure behavior.

My verdict is shortlist SGLang for a controlled agent-serving evaluation; do not claim validated savings from this review alone.

I see a credible architectural fit between reusable prefixes, cache-aware routing, and long-running agent sessions. I also see enough state-management complexity that a generic throughput benchmark would give me false confidence.

The next useful artifact is a pinned replay bundle: request traces, launch commands, runtime identity, cache telemetry, streaming timings, and correctness assertions. That is what turns an optimization story into a deployment decision.
