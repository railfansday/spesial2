Deploy Supabase Migrations by Merging a Pull Request

Tanggal: 2026-11-04

You can ship database changes by merging a pull request, with no tokens or database passwords copied anywhere. I tried it, broke it on purpose, and then built a small page that answers "did my change land?". Everything is from my run on 2026-10-31. Prices change, so every number is dated.

How this was made: I wrote this with Claude's help: it drafted, and I ran every step, edited the text, and checked the results. The mistakes are mine. This is a personal learning project, not an official guide, and I don't work for Supabase.

The non-technical version (changes as ordered files): https://medium.com/p/b6127c51d676 The code: https://github.com/tomozilla/github-deploy-en-demo

One term: a migration here is one SQL file describing one change. The number at the start of the file name decides the order.

The first migration creates a small table:

Project Settings -> Integrations -> GitHub -> Choose GitHub repository.

My repo was not in the list. Add GitHub Repositories opened GitHub's install page for the Supabase app. It offers "All repositories" or "Only select repositories". I chose the second and picked this one repo. The app asks for read access to code and metadata and read/write on actions, checks, pull requests and workflows.

After installing, my dashboard tab stayed on "Completing GitHub Authorization...". Reopening the dashboard fixed it, and the repo appeared. (I had used a second tab, which may be why.)

Press Enable integration. The button turns into "Disable integration".

Right after connecting, Database -> Migrations was empty, although the repo already had migration 1. Files that existed before connecting are not applied until the next merge.

Migration 2 adds a column and two fake rows:

On the PR, the Supabase Preview check showed skipped on the Free plan. Skipped means it didn't run, not that it passed.

After the merge, Database -> Migrations listed both files. The integration applies every pending migration in file-name order, including migration 1.

One oddity: the INSERTED AT column showed times like 00:02:00, exactly the file-name timestamp. I read that as "derived from the file name, not the real apply time". That is my guess, not something I confirmed.

I merged a migration that adds a column that already exists:

On the Free plan nothing stopped it on the PR. I created and merged this PR quickly, so I did not look at its checks and can't say what they showed. After the merge, the check on the main commit went red, with the real Postgres error:

The message is readable. But the dashboard shows nothing: the overview still says Healthy, and LAST MIGRATION shows the previous change.

So on Free, GitHub is the only place you learn about the failure, and only after the merge. Production isn't broken (the change just didn't apply), but nobody sees that unless they open GitHub.

I left the broken file in and merged a valid one (an index). It failed with the same old error.

The fix was in the broken file. It had never been applied, so I edited it in place (add column if not exists) and merged. The remaining migrations then applied together.

Editing a file that was already applied is a different story. The usual advice is to fix it with a new file. I didn't test that.

The docs say the integration deploys migrations and the Edge Functions declared in config.toml. I checked both.

A setting: in the same PR I changed [api] max_rows from 1000 to 7. The Data API settings page still said:

Dashboard-only settings did not ship, even when I wrote them into config.toml.

For a PR-time failure, the integration can create a preview branch per PR: a throwaway copy of the database structure (no data) where the new migrations run. It needs Pro.

The form says branch compute is not covered by the spend cap. Because that limit doesn't apply, delete branches when you're done.

At the docs rate my short test was a few cents at most. I did not check an invoice, and I did not check whether partial hours are rounded up. A branch left running adds up.

The integration works, but I wanted an answer to "did my change land?" without hopping between GitHub and the dashboard. So I built one page.

If any of the three sources fails to load, the table shows only "No data" plus a yellow banner. A partial table would be false comfort.

One thing I avoided from the start: auto-refresh. GitHub allows 60 unauthenticated requests per hour per IP, and each refresh uses 2. A tab left open would eat the quota.

I disabled the integration (Settings -> Integrations -> Disable integration), dropped the table and its migration records, deleted the function and the throwaway Pro project. The GitHub app can be removed at github.com/settings/installations.
