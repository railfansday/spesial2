Reuse a Cached App Shell Without Blurring Query-Driven Responses

Tanggal: 2026-11-12

Posted on Nov 12 • Originally published at chriseugenerodriguez.com

A cached app shell may fail to load offline when a navigation adds a tracking or cosmetic query parameter. A request for /app and one for /app?utm_source=newsletter are different URLs under default cache matching, even when both should receive the same shell document.

The safe fix is route-scoped rather than global. First classify the request: allow only GET requests for a canonical shell path such as /app. For that one lane, use a cache lookup that ignores the URL search component. The cached shell can then satisfy navigations with campaign tags or other parameters that do not alter the shell response. The request still carries its full URL; only cache comparison changes.

Leave every other request on exact matching. API endpoints, searches, filtered results, user profiles, reports, and locale-specific content often use query parameters to select the response. In those cases, ignoring search could make one request receive a response intended for another query. Non-GET requests should bypass this shell-cache policy and continue to the network.

Expected behavior is intentionally limited. Two shell navigations with harmlessly different query strings can use one cached shell entry. If that entry is absent, the request falls back to the network. A query-sensitive request remains keyed by its complete URL and cannot select another query’s cached response.

Keep the decision function separate from service-worker event wiring. A controlled fixture can verify that application code selects the intended lookup option, preserves exact matching elsewhere, and bypasses non-GET requests. It cannot prove browser Cache API behavior, secure-context requirements, or the service-worker lifecycle; those require browser integration verification.

Ignoring search does not normalize different paths, reorder parameters, or establish a caching strategy for every route. Use it only where the path identifies a reusable shell and the search string does not change what that response means.
