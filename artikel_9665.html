Decoding Morse Code with a Finite-State Machine in TypeScript

Tanggal: 2026-11-06

Morse code is a stream problem. Signals arrive one at a time — a short beep, a long beep, a pause — and the decoder has to turn that stream into text without ever seeing the future. Most hobby decoders handle this with nested if statements and a handful of timers, and most of them break the moment input gets noisy: a slightly long dit becomes a dah, a hesitant pause splits a letter in two, and the whole message drifts out of sync.

There is a cleaner way to think about it. Morse decoding is exactly what finite-state machines were invented for: a small set of states, a small set of events, and a transition table that says what happens next. This article builds a complete Morse decoder as an explicit state machine in TypeScript — no libraries, no timers scattered through the logic, and a design you can test exhaustively.

A finite-state machine (FSM) is a program that is always in exactly one state, moves between states only on defined events, and carries a small amount of memory with it. Morse decoding maps onto that shape perfectly:

Because every decision lives in the transition table, there is nowhere for timing bugs to hide. If a decode is wrong, you can point at exactly one transition.

The common first attempt buffers raw on/off durations into arrays, then post-processes them: anything under X milliseconds is a dit, anything over is a dah, gaps under Y milliseconds are intra-character, and so on. It works on clean, machine-generated input — and fails on humans, because human keying is uneven. A beginner's dah at 12 WPM can be shorter than an expert's dit at 30 WPM. Fixed thresholds assume a single speed, and real senders vary.

A state machine does not fix that by itself. What it does is isolate the classification logic in one place, so you can swap fixed thresholds for adaptive ones without rewriting the decoder. That is the design we will build toward.

Two timers matter, and both are derived from the unit length — the duration of one dit at the current speed. At N words per minute, one unit is 1200 / N milliseconds (the PARIS standard). A dit is 1 unit, a dah is 3, the gap inside a character is 1 unit, between characters 3 units, and between words 7 units.

The classification thresholds sit at the midpoints: a mark shorter than 2 units is a dit, longer is a dah. A space shorter than 2 units is an intra-character gap (do nothing); between 2 and 5 units it ends a character; 5 units or more ends a word.

Note what is absent: there is no setTimeout per element, no queue of pending durations, and no string-splitting pass. The machine consumes events as they arrive, which means it works identically on live keying and on recorded audio.

Fixed thresholds break on real humans, so the machine should learn the sender's speed as it goes. The trick is to track a running estimate of the dit length and derive the unit from it, rather than fixing the unit up front.

A simple, robust estimator: keep a rolling average of the shortest marks seen recently. Dits are the most common element in English Morse (the letter E, a single dit, is the most frequent letter), so the shortest marks in a rolling window are almost always dits. With this one change, the same decoder handles a nervous beginner at 8 WPM and a confident operator at 25 WPM, and it recovers gracefully when a new operator takes over mid-message — the failure mode of every fixed-threshold decoder.

Because the state machine is pure — no DOM, no audio, no timers inside it — you can unit-test it by feeding synthetic event sequences and asserting the output text. That is the real payoff: a decoder you can prove correct before it ever hears a real signal. Test a decoder with property-based checks, not a handful of examples. The round-trip property is the strongest one: for any random string, encoding it to timed events and decoding those events must return the original string. Why three states and not two? Two states (on/off) force the gap logic into the mark handler, where it does not belong. The SPACE state exists so that gaps are classified exactly once, in one place, whether the next mark arrives or silence simply continues. It is the state that turns "nothing is happening" into information.

Do I need the tick? Yes — without it, the final character of a message never flushes, because no event ever arrives to close the last space. A 25 ms interval is plenty; at 20 WPM a unit is 60 ms, so the tick fires more than twice per unit and adds no visible latency.

What about characters that are not in the table? flushChar silently drops unknown symbol sequences. For a practice tool that is the right call — a mistyped character should not crash the session. For a logging tool, emit a placeholder like � instead so the error is visible in the transcript.

Can this decode audio from a real radio? Yes, with the analyser-threshold glue described above. Real-world signals add noise, fading and interference, so expect to tune the energy threshold and the debounce window for your band conditions. The state machine itself needs no changes — that separation is the whole reason to build it this way.
