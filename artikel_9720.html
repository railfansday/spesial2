I Built a Tool That Lets You Work on Multiple Projects in One AI Environment

Tanggal: 2026-11-26

Use separate MCP endpoints to give each project its own services, then switch access without rebuilding your setup.

An online store has an order-status bug. A booking service has an availability problem. You want an AI assistant to investigate both, in separate conversations, while you review the results in the same development environment.

Opening another chat is easy. Keeping the tools attached to each project understandable takes more care. Both projects might use PostgreSQL and Redis. Both might have tables called users. A tool named “query database” says very little about which application it can reach.

The setup in this walkthrough gives each project a named access path: one MCP endpoint for the store, another for the booking service. Both can stay available while work runs in parallel. Each also has a switch for temporarily stopping access, without deleting its configuration.

Disclosure: I build GateRook, the application used below. The screenshots show a local development build with fictional project data.

There are two things to organize when working on several projects with AI.

The first is the working context: the repository, instructions, conversation history, and task. Give each project its own workspace and conversation in your AI application.

The second is access to external services. The store needs its orders database and cache. The booking service needs its reservations database and availability cache. These are different resources even when they use the same technology.

MCP provides the connection between an AI application and tools. Its architecture allows a host application to connect to multiple servers; it does not prescribe how that application manages the model's context. That distinction matters here. MCP architecture overview

In GateRook, an endpoint is one MCP URL with its own selected connections, tool modes, and tokens. For this example, the layout is:

The same AI application can be configured with both endpoint URLs. Calls through shop-dev use the store's configured services; calls through booking-dev use the booking service's configured services.

That does not automatically bind a particular chat to an endpoint. If an AI client exposes both endpoints globally, both may be available in either conversation. Use its project-level configuration when you need project-specific tool availability.

Start by creating two endpoints in GateRook: shop-dev and booking-dev. Use names that identify the project and environment before any tool call happens.

Create the database and cache connections for each project. In the connection wizard's endpoint step, add shop-db and shop-cache only to shop-dev. Add booking-db and booking-cache only to booking-dev.

Then open Overview and select each endpoint. This is a useful check: does the list of services match the project you think you are working on?

Keep the underlying credentials scoped too. The two demo database connections use separate PostgreSQL roles with read access to their respective project tables. GateRook's connection test reported SELECT access and no table ownership or CREATE privilege.

This matters because an endpoint's tool policy and a database role govern different parts of a request. An approval in the gateway cannot grant a database privilege the role does not have. PostgreSQL documents these permissions separately, including SELECT, INSERT, UPDATE, and DELETE. PostgreSQL privileges

For an investigation, enable the reads you need and review the write-capable tools. You can leave mutations behind approval or turn them off for that endpoint. Avoid giving a debugging session an administrator account just because it is convenient to configure.

From Overview, select shop-dev, choose Connect an AI app, and follow the setup for your client. Review the configuration change before saving it. Repeat from booking-dev for the same client.

For the local Cursor example, this produces two server entries, gaterook-shop-dev and gaterook-booking-dev, pointing to different endpoint URLs. Complete any enable or restart step requested by the client before using the tools.

Choose the configuration scope deliberately. Cursor supports project configuration in .cursor/mcp.json and global configuration in ~/.cursor/mcp.json. Global entries are available across projects, so adding two global entries is a convenient shared setup, not a per-project access restriction. For project-specific availability, configure only the appropriate endpoint in each workspace and remove any global duplicate that exposes the other project. Keep literal tokens out of committed configuration. Cursor MCP documentation

With both endpoints enabled, keep a store conversation and a booking conversation open. Each should identify the project, the allowed endpoint, and the expected result.

Work on the online store. Use the shop-dev endpoint and shop-db connection. Read the orders schema and summarize order counts by status. Do not change data. Include the connection name in your result.

Work on the booking service. Use the booking-dev endpoint and booking-db connection. Read the reservations schema and summarize reservations by status. Do not change data. Include the connection name in your result.

These are example tasks you can reproduce with the demo's data. They give you something concrete to review: which service was used, what was read, and whether the answer addresses the correct application.

Explicit instructions help the agent choose tools, but they are not an access-control mechanism. Pair them with the workspace configuration and endpoint permissions described above.

This follows a useful theme in Alex Cloudstar's HackerNoon account of an AI coding workflow: write the constraints before asking the agent to work. Here, those constraints include the service access available to each task.

Parallel work needs both endpoints available. At other times, you may want to concentrate on the store and temporarily stop new requests to the booking services.

Turn Access off on booking-dev. GateRook preserves the endpoint's tool modes, tokens, and settings, while blocking new service operations through that endpoint. shop-dev stays enabled.

Turn it back on when you need that project again. There is no need to recreate the connections or replace the endpoint URL.

The switch applies to every client using that endpoint. If another conversation is actively investigating the booking service, pausing booking-dev also blocks its new service requests. Treat this as a shared access control, not a private switch for the chat you happen to be viewing.

Also, do not assume switching off cancels an operation already in progress. The useful guarantee for this workflow is control over subsequent requests.

Sometimes the database is still useful but the cache is not. Perhaps you are checking whether an answer can be derived entirely from persisted records.

Turn shop-cache off and leave shop-db on. The endpoint stays enabled, and the database remains available under its existing rules.

In this demo, each connection belongs to one project endpoint. If you later share a connection between endpoints, its connection switch affects all of them. Use endpoint-specific tool modes when the restriction should apply to only one access path.

An off connection may still be discoverable, allowing the AI to ask you to enable it. Off means operations are blocked; it does not necessarily mean the client removes every reference to the service.

Before starting a task, check the workspace, endpoint, and enabled services. When reviewing a result, check which connection supplied the data. When putting a project aside, decide whether its endpoint should remain available to other ongoing work.

Keep the limits of this arrangement clear. Switching access does not erase information already in a conversation. GateRook governs requests routed through it; an agent's separate shell tools or direct credentials are outside that path. And although service credentials stay in GateRook, tool results can still enter the AI application's context and reach its model provider.

The practical benefit is a setup you can inspect and change quickly: two project contexts in one AI environment, two named service-access paths, and controls for pausing either a whole project or one connection. When both projects are active, leave both available. When the task narrows, narrow the access with it.
