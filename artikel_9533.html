CocoaPods freezes on December 2. Here's the SwiftPM migration checklist I'd run first.

Tanggal: 2026-11-25

Posted on Nov 25 • Originally published at Medium

Trunk goes read-only on 2 December 2026. Existing builds keep working, but the pods behind them stop getting updates. Here is how to list yours and plan the move to Swift Package Manager, for native iOS, Flutter and React Native.

Run this in the folder that holds your Podfile.lock. The shell blocks in this post are written for bash.

Every name it prints is a pod your app pulls from CocoaPods trunk. From Wednesday 2 December 2026, trunk stops accepting new pods and new versions. Your builds won't break that day, but those names are the dependencies that stop getting updates, so this CocoaPods to SwiftPM checklist starts with that list.

It covers native iOS, Flutter and React Native, and it says where each one stands today. Every date and command traces to an official page listed at the end. This is a plan built from those pages, and I haven't run it on a real migration.

The CocoaPods team's read-only plan puts the permanent switch on 2 December 2026 and says any new podspec will be denied at the server level. It also planned a test run of the same behavior for 2 to 6 November.

CocoaPods itself is in maintenance mode too. The team's support plan aims for at least two releases a year to keep up with Xcode, and says there is no plan for new features.

My read is that 2 December starts a clock. The first real problem is a pod that needs a fix for a new Xcode or a security issue and has no way to ship it. The CocoaPods post does say the dates aren't set in stone, but Swift.org and the Flutter docs both quote 2 December, so plan for that date.

The command at the top lists trunk pods. If it prints nothing, open Podfile.lock and look under SPEC REPOS. This command only reads the entry named trunk. Pods installed with :git, :path or :podspec show up under EXTERNAL SOURCES in the same file. They don't depend on trunk, but they do depend on CocoaPods, so write them down too.

Next, find out which of those already work with SwiftPM. Swift.org's post says most maintained pods are already SwiftPM compatible, and that the easiest check is the Swift Package Index, since every package in it is a SwiftPM package. Search each name there. To script a first pass, this reads each pod's source repository from its podspec and asks GitHub whether a Package.swift sits in the repository root.

A 200 means the default branch has a manifest, which tells you nothing about releases. Pods hosted outside GitHub, or with a name pod spec cat can't match as a regex, are listed under 'check by hand'. SwiftPM's docs expect a Package.swift in the root of the repository and a tag that is a full semantic version with major, minor and patch numbers, and they warn that a tag like 1.0 isn't recognized, so tag releases as 1.0.0.

Put the result in a file in your repo with one row per pod and a yes or no for Package.swift. For the pods that say no, add a note on whether a SwiftPM alternative exists. The pods with neither are what the last section is for.

I haven't run the Xcode or iOS build steps in this post on a Mac. The menu names, flags and commands come from the official docs, starting with Apple's here, and Flutter's and React Native's later on.

Flutter's docs say that as of the 3.44 release, Flutter uses Swift Package Manager for iOS and macOS native dependencies, that CocoaPods stays supported in maintenance mode, and that the CocoaPods registry becomes read-only on 2 December 2026.

Upgrading and running your app adds the SwiftPM integration for you. Flutter falls back to CocoaPods for any dependency that doesn't support SwiftPM yet. To confirm the integration in Xcode, run the app and check that the Run Prepare Flutter Framework Script pre-action ran and that FlutterGeneratedPluginSwiftPackage is a target dependency.

The Flutter tool decides per plugin by looking for a manifest at ios//Package.swift (or the macOS or darwin equivalent), which is the layout the plugin docs describe. This lists which of your plugins have one:

Don't remove CocoaPods until every plugin in your app reports SwiftPM. The docs say Flutter falls back to CocoaPods if any dependency lacks SwiftPM support, and that edits you made to the Podfile beyond Flutter plugins have to be removed by hand. When you're ready, the docs give these steps:

If a plugin needs a higher iOS version than your app, Xcode reports a Target Integrity error. Raise your Minimum Deployments, then run flutter build ios --config-only to regenerate the configuration.

To turn SwiftPM off, which Flutter says not to do in general, use one of these two. The docs add that disabling it won't be allowed in the future, and that SwiftPM stays integrated in your project when you do.

To undo the first one, run flutter config --enable-swift-package-manager. Flutter prints a warning each time it runs with SwiftPM off: "Enabling Swift Package Manager will be required in a future version of Flutter."

If you maintain a plugin, the plugin author guide has the full steps. In short, add ios//Package.swift with a dependency on FlutterFramework, move your sources under Sources/, set the pubspec to sdk: ^3.11.0 and flutter: ">=3.41.0", and point the podspec at the new paths. Flutter asks plugins to support both SwiftPM and CocoaPods until further notice, because as of 3.44 a plugin that drops CocoaPods can't be used by projects that haven't migrated.

React Native 0.87, announced on 11 August 2026, added experimental SwiftPM support for iOS. The post says it is opt-in and additive, that CocoaPods remains the default and supported path, and that the commands, flags and generated layout may change. Its last known-limitations line reads "Do not use it in production yet."

React Native 0.88, announced on 19 October 2026, says SwiftPM support remains experimental and opt-in while CocoaPods remains fully supported. It also states the plan: 0.89 targets SwiftPM as the default with an opt-out for apps that are still blocked, and a later release removes CocoaPods support. No date is given for that removal. The open RFC says existing apps should not need to migrate immediately.

So here is what is and isn't true today. The official environment setup page still lists CocoaPods as a requirement, and the existing-app guide still installs React Native with bundle exec pod install. SwiftPM is available behind a command, and React Native itself says not to ship it yet.

In August 2024 the CocoaPods maintainer wrote that for React Native a read-only trunk could be fine as it is, because most of its libraries come through npm and not trunk. React Native's own rn-tester app fits that picture: its Podfile.lock lists two pods under trunk, OCMock and SocketRocket. Your app's lock file settles it for you, so run the command at the top of this post.

The 0.87 post says a community library must ship a Package.swift, and tells you to generate one from the podspec if it doesn't. The RFC adds that a library with its own manifest, in its root or in ios/, is detected automatically. This lists your libraries that have a podspec but no manifest:

To reverse the injection, run npx react-native spm deinit. For a library that only has a podspec, run npx react-native spm scaffold from the app root or from ios/. The file is written into the library's folder in node_modules, so keep it with patch-package until the library ships its own. That command can fail: on async-storage 3.1.1 it stopped with an error that the library mixes Swift and Objective-C, which Swift Package Manager cannot compile in a single target. After a fresh clone and in CI, run npx react-native spm, the analog of pod install.

The 0.87 post says the command injects package references into your existing .xcodeproj and leaves signing, capabilities and build phases alone. To go back to CocoaPods after --deintegrate, the RFC says to restore the Podfile from git and run pod install. One breaking change to check for: React Native headers imported without a namespace need one, so #import becomes #import .

My position is that most React Native teams should run the inventory this week, try the SwiftPM path on a branch, and keep shipping on CocoaPods until React Native's own docs stop recommending it. Pods already published to trunk keep installing, so nothing forces your hand on 2 December.

Some of the names from step 1 will have no Package.swift and no sign of getting one. You have five options, and I'd go in this order.

Replace it. Swift.org suggests searching for an alternative so you don't end up with an unmaintained dependency. If the pod is abandoned anyway, this is the cheapest fix.

Keep it on CocoaPods at the version you have. Podfile.lock pins the exact version, and the CocoaPods guide says pod install keeps installing that version unless you update it. If you need the pod to stop depending on trunk, point the Podfile at a Git tag or a local path. The podspec has to sit in that repository's root or folder.

Fork it and add a Package.swift. Put the manifest in the root of your fork and tag a release with a full three-number version, then add the fork's URL in Xcode like any other package. SwiftPM's docs say that is what it expects. A Swift-only pod can be this small. For C or Objective-C sources, SwiftPM's docs say public headers go in a directory commonly named include.

Use a binary target. If the vendor ships an XCFramework, or you can build one, wrap it in a package. Apple's docs say a binary target has to match the artifact's module name, a hosted one needs a ZIP with the XCFramework in its root plus a checksum, and binary targets only work on Apple platforms.

In your own manifest, use the value compute-checksum printed for the ZIP you host. For a framework that lives in your own repository, .binaryTarget(name:path:) takes the path to the XCFramework and needs no checksum.

Vendor it into a local package. Copy the source into a local Swift package in your repo, add a manifest, and add the package to your target. Apple's local packages guide shows File > New > Package, then adding the library product under Frameworks, Libraries, and Embedded Content. Check the license before you copy anything.

If you only have time for one thing before 2 December, run the first command and commit the list with a Package.swift yes or no beside each name.
