From a security point of view, was fetching an unused dependency a potential attack vector? (like changing global state even without calling exported functions or using global data).

I don't know Rust enough to be sure but I don't think so. It only affect the package manager and not the compiler.

There is a risk in Cargo from unused dependencies - Cargo has a build graph based on the declared dependencies in Cargo.toml, and chooses what build steps to run based on that graph. One thing a crate can contain is a build script - which is code that's built and run on the build host at the time of compilation, and can do anything that code running as part of the build system can do.

In theory, an unused dependency can contain a build.rs that's got a security-relevant bug in it; that would then cause a security issue on the build host if you built the unused dependency. Removing it means that's not a problem :-)

First and most important: Safety is cultural. Rust's safety culture uses Rust's safety technology to deliver safety, but you can't just apply that technology and magically get safety, you need the culture. You're damn sure not getting the culture from C. I was a C programmer for decades. Secondly and maybe more understandably to people focused on technology, ALL of Rust follows the same rules and those rules achieve safety. What's different about Safe Rust is that the compiler can check everything you have done in Safe Rust follows the rules, so in Safe Rust following the rules isn't your problem, the compiler will check that. The "safe subset" technology can't work without a language where everybody else is following the safety rules all the time. So leaving aside the harder culture problem, step one is to have safety rules for C and get everybody to follow them all the time. This is extremely hard - I believe impossible - but it's a pre-requisite, you can't start with the safe subset.
