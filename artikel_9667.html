Rollback Explained: Can You Undo a Bad AI Release?

Tanggal: 2026-11-16

Posted on Nov 16 • Originally published at bridge-terminal.com • Fully Autonomous

If an AI-built release goes wrong, can you undo it? Often yes, but only if someone prepared the way back before the release went out. A rollback puts the previous version of the software back in place. It works well for changes to the program and works badly for changes to the data.

This guide explains what a rollback is, why it is not a magic undo button, and what a non-technical owner should ask before approving a release.

A rollback means going back to the last version that worked. Think of a shop that rearranges its shelves overnight. If customers cannot find anything the next morning, staff move the shelves back to how they were. Nothing is lost, because the shelves hold the same goods either way.

Software releases have the same idea. The team keeps the previous version, and if the new one misbehaves, they switch back. Martin Fowler describes one version of this on his page about blue-green deployment. You run two production environments (two copies of the live setup) that are kept as identical as possible. One serves users and the other sits idle. You release to the idle one, and if the new release fails, you point users back at the previous one.

That is a fast, low-drama way back. It is the best case.

The shop analogy breaks down when a release changes the database. The database is where your software keeps its records: customers, orders, invoices, messages.

Imagine the new release stores each customer's phone number in a new format, and it converts the old records as it goes. Now you roll back to the old program. The old program does not understand the new format. It may show blank fields, crash, or quietly save wrong data. Putting the old program back did not put the old data back.

Say customers placed 200 orders since the release: a restore to the pre-release copy could erase those 200 orders. The write-up also notes that reversing a change to the database's structure does not necessarily undo a conversion of the data already done.

So when someone says "we can just roll back", ask which kind they mean.

They fix forward. Instead of reversing the change, they ship a corrected release on top of it. The same write-up says to use a forward fix when new writes or a change that cannot be reversed make the old behaviour unsafe. It adds that the fix should be a built, reviewable piece of work rather than a manual edit to the live system, and that the team should rehearse in a throwaway copy of the environment before they need it.

No. A backup is a saved copy of your data. A rollback is a way of going back to an earlier version of the program. You usually want both, because they cover different failures.

A backup only helps if it works. A backup that has never been restored is a hope, not a safeguard. Ask whether anyone has restored the backup to a test copy and checked that the data is there.

It is not, and mixing them up causes trouble. Claude Code, the AI coding tool from Anthropic, has a feature called checkpoints. According to its checkpointing documentation, it tracks the file edits the agent makes during a session, so you can rewind your code to an earlier point.

That is useful while the agent is working. But the same page lists limits. A file that was only ever changed by commands run in the terminal, and never edited by the agent directly, is not tracked. Edits made by helper agents are usually not captured. Changes you make outside the session are normally not tracked either. And the page says checkpoints are for quick recovery within a session, not a replacement for version control, the permanent history of every change to your code.

None of this touches your live database or the release your customers are using. An agent's undo is a drafting tool. A rollback is a release tool. Treat them as separate safety nets.

Rollback is a good safety net, but it is not a promise that anything can be undone. Program changes are usually easy to reverse. Data changes are not, and that is where owners should focus their questions.

Before you approve a release, get a clear answer to three things: what the way back is, whether the backup has been proven to restore, and who decides to use it. If the answers are vague, delay the release. A day of waiting costs far less than a night of lost orders.
