Shared Caddy 2 Reverse Proxy for Multiple Self-Hosted Docker Apps

Tanggal: 2026-11-24

Posted on Nov 24 • Originally published at vpsfolio.com

Per-container RAM: vaultwarden 46.9 MB · memos 21.7 MB · caddy 10.9 MB (sandbox verified 2026-11-24)

View the interactive benchmark plate and full VPS sizing comparison or compare all measured stacks on VPSFolio Benchmarks.

One public entrypoint, many private backends. Caddy 2 sits on a dedicated bridge network (proxy_net) and is the only container that publishes a host port. Vaultwarden and Memos join the same network but never expose ports: to the host, so their HTTP listeners are reachable only from Caddy. That is the whole pattern: a single TLS terminator, a shared L2 segment, and per-app Compose files that can come and go without touching the proxy.

Caddy is a good fit here because its config is small, its automatic HTTPS is real (ACME + OCSP stapling + HTTP/3), and it handles WebSocket upgrades in reverse_proxy without extra directives. Vaultwarden needs WebSockets for live sync notifications; Memos is a plain HTTP app. Both work through the same reverse_proxy block.

The sandbox-safe Compose file below uses auto_https off and binds Caddy to 127.0.0.1:18080 so you can verify routing with curl -H "Host: ..." before any DNS or certificate work. In production you flip two lines and Caddy gets real Let's Encrypt certs on 80/443.

Splitting Caddy into its own stack. Once you have more than a couple of apps, move the proxy to /opt/proxy/compose.yml and use an external network so app stacks can join and leave without restarting Caddy:

In /opt/proxy/compose.yml, set networks: proxy: external: true and attach Caddy to it. In each app's Compose file, declare the same external network and add it to the service. Caddy resolves backends by container name on that network, so reverse_proxy vaultwarden:80 keeps working as long as the container is named vaultwarden and joined to proxy.

Remote backups. The named volumes are the state. Back them up with a one-shot container that mounts the volumes read-only and writes a tarball to a remote target. For example, using rclone against an S3 bucket:

Schedule that with cron or a systemd timer. Restore is the reverse: download the tarball, stop the stack, extract into the volumes, start again.

Upgrades. Caddy, Vaultwarden, and Memos all publish rolling tags. Pin versions in .env (MEMOS_TAG=0.22.0, and replace vaultwarden/server:latest with a digest) if you want reproducible deploys. Upgrade one service at a time: docker compose pull vaultwarden && docker compose up -d vaultwarden. Caddy reloads its config on SIGHUP, but docker compose restart caddy is simpler and takes under a second.

Failure modes. If Caddy is down, every app is down — that's the cost of a single entrypoint. Keep the Caddy container's restart policy at unless-stopped and monitor it. If a backend is down, Caddy returns 502 for that host only; the other sites keep serving. If proxy_net gets recreated (e.g., you delete the network), Caddy's upstream DNS cache goes stale; restart Caddy after network changes.

Backups. The critical volumes are vw_data (Vaultwarden's SQLite DB and attachments) and memos_data (Memos' SQLite DB). caddy_data holds certificates and ACME account keys; back it up too, or accept a brief re-issuance on restore. Test restores quarterly — an untested backup is a guess.

Trade-offs. A shared Caddy is simpler than per-app reverse proxies and uses less RAM, but it couples app availability to the proxy. Splitting Caddy into its own stack with an external network decouples lifecycle: you can docker compose down an app without touching the proxy. The cost is one more Compose file and a network that must exist before any stack starts. For a 1 GB VPS running two or three apps, the single-file version in this guide is the right default; split when you outgrow it.

Security headers. The security_headers snippet sets X-Content-Type-Options, Referrer-Policy, and X-Frame-Options. Vaultwarden's admin panel and web vault work fine with these. If you embed Memos in an iframe elsewhere, drop X-Frame-Options for that site block only.

WebSockets. Vaultwarden's ENABLE_WEBSOCKET=true and IP_HEADER_TRUSTED_PROXIES=local are set so it trusts Caddy's X-Real-IP and accepts upgrade requests. Caddy's reverse_proxy forwards Upgrade and Connection headers automatically; no extra config needed. If live sync doesn't work, check docker compose logs caddy | grep -i upgrade and confirm the browser is hitting the same hostname Caddy is configured for.

Measured in our sandbox run: total memory 79.6 MB (sum of per-container peaks over a 30s idle window after startup) across 3 containers; largest container 46.9 MB; published port(s) 18080; HTTP probe returned 200, 200. The run took 102.6s including the image download. Required secret(s) ADMIN_TOKEN, PUSH_INSTALLATION_KEY were generated for the test run, as the tutorial instructs. Container breakdown: vaultwarden 46.9 MB, memos 21.7 MB, caddy 10.9 MB. Verified routes: Vaultwarden via shared Caddy (HTTP 200), Memos via shared Caddy (HTTP 200).

Verification: we ran this docker-compose stack in a disposable Docker environment and recorded the measurements above. They describe that run, not a guarantee for your host.
