Chat memory for an on-device notes assistant, without a bigger prompt

Tanggal: 2026-11-12

Posted on Nov 12 • Originally published at mindscendinc.com • AI-assisted

Originally published on the Mindscend blog.

Mindscend Notes (formerly MindPage) is our notes app for handwriting, PDFs and books on iPhone, iPad, Mac and the web. Notes stay on your devices and in your own iCloud Drive or Google Drive; the AI runs on the device. Version 1.1.1 just shipped on the App Store, and the free version no longer has limits: unlimited folders and notebooks, sync and on-device AI, no account.

This post is the technical part: how "Ask my notes" got chat memory without giving the model the conversation, what the search under it does, and a SwiftUI hit-testing bug we managed to ship twice.

How much each search layer matters, on our 21-question test library:

The embedding model in the app is our fine-tune, MindPage Search v2 (Apache-2.0, 300M, Q8_0 GGUF via llama.cpp, Matryoshka-truncated to 256 dims). It was trained on what Apple Vision actually reads from handwriting, misreadings included. On 234 held-out handwritten pages, it ranks the right page first 85.9% of the time vs 80.3% for v1.

The 1.1 Ask was one question, one answer. Users then type follow-ups:

when is the physics exam? and where is it?

The textbook fix is to pass the chat history to the model. That fails here twice: the context window is already spent on retrieved passages, and the model never sees the right page anyway, because "and where is it?" retrieves nothing.

So we detect follow-ups and fix the query:

Retrieval sees the previous question's words, so it finds the exam page again. The model keeps its one-question prompt, so none of the answer evals had to change. Chats are stored as chat: root keys in the library's Automerge document, with messages in a map keyed by ULID, so they sync and merge like everything else.

Without Apple Intelligence, there's no writing model, so Ask shows the one line of the notes that answers the question: EmbeddingGemma scores each line and line pair of the two best pages, with the page heading as context. 15/15 on our extraction eval.

In the iPad library's list view, tapping a notebook row only worked on the text. Tapping the middle of the row did nothing.

With .plain, only drawn content is hit-testable. A Spacer draws nothing, so most of the row wasn't a button. The fix:

We hit the same thing in October on the Mac pen bar (only an icon's drawn pixels took clicks). Lesson recorded twice now: any .plain button with a Spacer or thin icon needs .contentShape. A UI test (testListRowOpensNotebook) now taps the middle of a row on iPhone and iPad.

That test came from a batch written for features that had no UI tests: empty library, folders, export, recordings, sync choices, largest accessibility text, landscape, flashcards. The batch also found an export sheet that could spin forever (the sheet showed a URL set by a separate Task; now the sheet runs the export itself) and flashcards unreadable in Dark Mode.

One more from the test suite: a test that queried a sticker the wrong way made XCUITest snapshot the whole accessibility tree, which took up to 15 minutes. Checking it as a button first fixed it.
