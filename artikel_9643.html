The Concierge Knows Too Much — Prompt Injection and Social Engineering

Tanggal: 2026-11-17

In this write-up, I will document my experience completing The Concierge Knows Too Much, the first challenge in TryHackMe's Hacker Holidays 2026 event.

Unlike traditional CTF challenges, this room does not require me to enumerate network ports, exploit a vulnerable service, or execute commands on a remote machine. Instead, the target is an AI-powered hotel assistant named VERA (Very Efficient Resort Assistant).

The objective is to understand how VERA handles user identities, discover why she trusts certain guests, and manipulate the conversation to reveal an internal escalation code that she has been instructed to protect.

What I found interesting was that the vulnerability did not involve exploiting traditional application code. The weakness came from how the AI assistant interpreted user-provided information and applied its internal instructions.

After opening the room, I reviewed the challenge description and the concierge briefing.

The scenario introduced VERA, an AI concierge working for the fictional Byte Lotus Hotel.

VERA appeared unusually familiar with her guests. She could provide information such as a guest's room number and preferred coffee order, even before the guest explicitly supplied those details.

At first, this seemed like a normal personalised assistant feature. However, the challenge description suggested that VERA also had access to confidential information.

My objective was to discover the internal escalation code.

The briefing also provided an important clue: VERA behaved differently when interacting with guests she already recognised.

This suggested that the assistant might have different trust levels or conversation rules depending on the identity claimed by the user.

I started by interacting with VERA normally.

Rather than immediately attempting to extract the protected information, I wanted to understand her behaviour and identify what information she was willing to disclose.

I asked ordinary questions about the hotel and its services.

During this process, I noticed that VERA could provide personalised information and behaved as though she already knew the person interacting with her.

This raised an important security question:

How does VERA determine whether someone is a recognised guest?

In a properly designed application, identity should be established through a trusted authentication mechanism, such as a verified session or access token.

However, the challenge suggested that VERA might be relying on conversational context instead.

That became the direction of my investigation.

VERA began disclosing information from her internal instructions.

This was the critical point of the challenge.

The assistant's behaviour demonstrated that its trust mechanism could be manipulated through a conversational identity claim.

The main vulnerability demonstrated in this room is prompt injection combined with insecure identity verification and system prompt leakage.

There are several security issues worth understanding.

Prompt injection occurs when an attacker crafts input that manipulates an LLM into behaving in an unintended way.

Unlike SQL injection, which targets the way an application constructs and executes database queries, prompt injection targets how a language model interprets instructions and context.

In this challenge, the attacker used conversational input to influence how VERA interpreted the user's identity and the permissions associated with that identity.

VERA appeared to accept a guest's identity based on information supplied directly through the conversation.

This is not a reliable authentication mechanism.

An attacker can simply claim to be another person. Without an independent verification process, the AI assistant has no reliable way to establish that claim.

In a real application, identity should be verified outside the LLM using trusted authentication mechanisms.

A system prompt contains instructions that influence how an LLM behaves.

System prompts should not be treated as secure storage.

Even if an application instructs the model not to reveal its internal instructions, that instruction alone is not a reliable security boundary.

If sensitive information is placed inside the model's context, carefully crafted input may cause unintended disclosure.

The most important lesson from this room is that natural-language statements should never be treated as proof of identity or authorization.

This statement does not prove that the user is an administrator.

Similarly, telling an AI assistant that I am a recognised hotel guest should not automatically grant access to confidential information.

The application must enforce authorization independently of the model's interpretation.

If I were reviewing VERA from a security engineering perspective, I would recommend several improvements.

The backend should verify the user's identity using established authentication mechanisms.

For example, a hotel assistant should retrieve guest information using an authenticated session rather than accepting a guest name from the conversation.

The LLM should not be responsible for deciding whether a user is authorized to access sensitive information.

Instead, the backend should validate permissions before returning protected data.

System prompts are instructions, not secret vaults.

Sensitive information such as API keys, escalation codes, passwords, and internal credentials should be stored in secure backend systems.

The model should only receive information required for its current task.

An AI assistant should only have access to the data and tools necessary to perform its intended responsibilities.

For example, a hotel concierge may need to retrieve a guest's booking information, but that does not mean it should have unrestricted access to all hotel records.

This room helped me understand several important concepts in AI security.

1. Prompt injection is a real application security concern.

An attacker does not always need to exploit traditional software vulnerabilities. Manipulating an LLM through natural-language input can also expose sensitive information.

2. Identity must not be based on user claims.

A user saying they are an administrator or a recognised guest does not make that statement trustworthy.

3. System prompts are not secure storage.

Confidential information should never rely on the model following an instruction to keep it secret.

4. Authentication and authorization must be enforced outside the model.

The backend should remain responsible for verifying identities and controlling access to protected resources.

5. AI security requires a different testing mindset.

When testing an AI application, I need to consider how the model interprets context, handles conflicting instructions, and interacts with external data and tools.

The The Concierge Knows Too Much room was a short but valuable introduction to AI security and prompt injection.

What I found most interesting was how a simple conversational interaction could expose a weakness in the application's trust model.

By analysing the challenge clues, identifying the recognised guest names, and testing VERA's identity assumptions, I was able to understand how conversational input could influence access to confidential information.

My biggest takeaway is that an LLM should never be treated as an authentication or authorization mechanism.

As AI assistants become increasingly integrated with customer data, APIs, and internal business systems, protecting their trust boundaries becomes just as important as securing traditional web applications.

This challenge is a good starting point for anyone interested in AI red teaming, LLM security, and modern application security.
