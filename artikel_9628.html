I Ran the USB Coding Expert Demo's Same Prompt in 4 Languages. Only 1 of 16 Survived Unchanged

Tanggal: 2026-11-23

Most product demos are marketing surfaces: a textarea that returns whatever the vendor wants to show you, with nothing underneath. The interesting demos are the ones where you can pull the mechanism apart.

So that is what I did with the USB Coding Expert demo — the "Live Demo — Code Generator" panel on the product page. You type a request in plain English, pick Python / JavaScript / Bash / Solidity, and it returns a snippet.

The claim on that page is that it generates "real working code instantly." That is a testable claim. I extracted the generator's logic and the full snippet table, then ran every one of the 16 combinations under the real interpreters and a real Solidity compiler.

Result: 8 of 16 pass unchanged. 2 pass with a flag. 6 do not pass — and 2 of those six ship something that looks like a feature but isn't.

Here is the breakdown, the method, and what it tells you about evaluating a tool like this before you pay for it.

Before judging the output, it helps to know what the generator does, because it is not what the copy implies.

The generator is a keyword router over a hardcoded table. There is no model in the browser. The logic, verbatim from the page:

Four buckets (reverse, http, file, token) × four languages = 16 snippets total. Any prompt that matches no keyword falls through to reverse. That is the entire engine.

I verified the router behaves as written by driving the page's real script in a VM with a DOM stub — 16 checks, all passing: empty input is rejected, http/file/erc/solidity keywords route to the right bucket, an unmatched prompt falls back to reverse, preset buttons fill the textarea and auto-generate, the language highlight moves, and the output mirrors the textarea.

One thing worth flagging on the security side: the page script contains zero outbound primitives. No fetch, no XMLHttpRequest, no WebSocket, no sendBeacon, no dynamic import. No localStorage, sessionStorage, or indexedDB either. Whatever your prompt is, it never leaves the tab. For a product whose whole pitch is air-gapped operation, that is the correct behaviour and it is verifiable in the source.

I ran each of the 16 snippets in the matching real runtime, and compiled the Solidity ones with solc.

All six execute without modification and produce the documented output. Note the pattern: these are the snippets that do not depend on an interactive prompt or a network port.

The http bucket (all 4 languages). All four actually start a server and serve

The break is inside the loop body, so it fires after the first request and the loop exits. It works for a single request — which is all a demo needs — but anyone copying this into a real service would get a one-shot server that dies immediately. The Python and JavaScript versions use serve_forever() / a long-lived server.listen(), so they behave correctly.

python.token is the most interesting failure, because it is a routing bug rather than a broken snippet:

The token bucket under the Python language button contains a Solidity contract. Compile that same text as Solidity and it builds fine — 4013 bytes of bytecode, contract MyToken. So the code is correct; it is filed in the wrong language. If you click Python, then the ERC-20 preset, the generator hands you a Solidity contract and tells you it is Python code.

javascript.token fails on a missing dependency — require('web3') with no web3 installed. Not a bug in the snippet's logic, but it is not "working code instantly" either; it is working code once you install a package.

bash.token shells out to solc and geth, neither of which is present:

The script prints "Compiling contract..." and "Deploying to network..." before it discovers the tools are missing. That is the part worth learning from: the output lies to you about how far it got.

The four Solidity snippets are the cleanest result in the whole audit — all four compile under solc with zero errors. The only warning on every single one is the missing SPDX identifier, which is cosmetic.

Two readings are possible, and I would rather give you both than pick the flattering one.

The honest reading: the demo is a static lookup table, not a code model. The product page describes "a fully autonomous, self-contained AI coding model" and "code generation, review, debugging, refactoring." What you can test in the browser is a 16-entry dictionary. That gap between what is demoable and what is being sold is exactly why I run these tests — a demo is not evidence of the shipped product.

The reading that still matters: the demo does exactly what a demo should do. It is deterministic, it has no network calls, it never leaks your prompt, and eight of its sixteen outputs are genuinely usable snippets. There is no tracking, no telemetry, and no hidden phone-home — which, for a tool marketed on air-gapped security, is the single most important property to verify. I verified it.

If you are evaluating this, the useful question is not "does the demo work" but "does the delivered image contain the model the page describes." The demo cannot answer that. Only the package can.

Final tally: 27 of 27 checks passed — 16 on the router, 5 on Solidity compilation, 6 on runtime execution.

The two findings I would not have found by reading the page: python.token is a Solidity contract in the Python bucket, and the Bash http snippet is a one-shot server.

The generator is live and free to poke at: usb-coding-expert — $149.99 USD, one-time, lifetime license, boots from a USB 3.0 drive (16 GB+) on any x86-64 machine.
