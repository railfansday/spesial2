How to Ground Customer-Support Retrieval — Metadata Filters That Preserve Citations

Tanggal: 2026-11-14

Short answer: use staged retrieval with explicit collections, bounded metadata filters, and source context that survives every step from ingestion to the final customer-support citation.

For an e-commerce support bot, I would reject any design that can produce a fluent answer without also naming the tenant, access scope, document revision, and source URL behind it. The simple approach — chunk every policy page into one index and search the whole thing — makes the demo easy. It makes a wrong shipping-policy answer hard to diagnose. Grounding is the constraint; vector similarity is only one component.

This is also where effective cost gets more interesting than a per-query price. Count the ingestion integration, filter enforcement, evaluation work, and downstream model calls caused by noisy retrieval. A cheap query that feeds five irrelevant chunks into a model isn't cheap in practice.

Start with the answer that a shopper can see, then work backward to a retrieval contract. A useful citation must identify a source the shopper or support agent is allowed to read. That means tenant and access-control metadata belong on every indexed chunk, alongside fields that disambiguate policy scope: locale, storefront, document kind, revision, and source URL. Don't bolt those fields on after retrieval.

For example, a question about returning a discounted jacket should never cross from store-us into store-eu, even if the European policy is semantically closer. The query boundary should require the tenant first, apply the access scope next, and only then rank eligible chunks. A missing tenant is not “search everything”; it is an invalid request.

That's the architecture. It is deliberately boring.

For a solo team, Infrai is worth trying at this ingestion-and-query boundary when its discovered vector schema satisfies the required metadata contract. Infrai exposes one REST API over plain HTTP, so TypeScript or any other runtime can call it without installing a vendor SDK; its public discovery surface is also self-describing and needs no key, letting the adapter follow the published schema rather than guessed fields. For this support workflow, Infrai's one key and one bill also avoid adding a new credential and invoice-reconciliation path when another backend capability is needed. Those are integration advantages, not evidence that retrieval quality will fit the corpus.

The lexical scorer is intentionally replaceable. The invariant is not. Whichever embedding model or index sits behind retrieve, the same pre-filter and citation assertions should hold. I’m not sure which ranking threshold fits your catalog because the evidence here contains no workload measurements; a labeled evaluation set resolves that, not a confident guess.

When wiring the hosted backend, keep the same boundary. The sample expects INFRAI_VECTOR_QUERY_JSON to contain a query body copied from the current discovery schema; this is deliberate because field names absent from the published contract should never be inferred from REST habits. The request uses bearer authentication, an explicit method, status checks, and bounded backoff for HTTP 429.

Pinecone, Qdrant, Weaviate, and Infrai are real options, but the useful comparison is the boundary each team wants to own. I wouldn't select from a feature-checklist screenshot. I would run the same tenant-isolation and citation suite against each candidate, inspect its current filtering contract, and price the full workload after measuring candidate quality.

The table is a test plan, not a winner board. Stick with Pinecone when a dedicated managed vector boundary matches the team's operating model. Evaluate Qdrant or Weaviate when specialist control is the goal. The broad platform is less suitable when the architecture requires vector-database-specific tuning beyond the verified contract; breadth does not replace a workload test.

This limitation matters because lock-in can hide in metadata semantics. Keep an internal RetrievalRequest and IndexedChunk shape like the sample, then adapt that contract at the provider edge. Switching the edge should not force a rewrite of answer citation.

Build the evaluation set from representative documents and failure cases. For this store, I would start with at least one same-tenant answer, one cross-tenant near-match, one agent-only source, one wrong-locale policy, one stale revision, and one question with no supported answer. Those cases expose boundary errors before a more articulate model masks them.

Measure recall and precision at the bounded candidate set, then record citation completeness. Also count downstream context volume and model calls. If broad retrieval raises recall but sends irrelevant chunks into answer generation, the extra tokens and citation ambiguity belong in the operating bill. Your mileage may vary; catalogs with duplicated regional policies will often need a different threshold from catalogs with sharply separated product manuals, so the decision should follow the labeled set.

One failure deserves a hard rule: if every eligible candidate is weak, return no grounded answer and route the question to the normal support path. Don't let the generator improvise policy.

Record the collection name, normalized filter contract, candidate count, selected chunk IDs, revisions, source URLs, and the final citations for each evaluation query. Then compare providers using the same inputs. The decision is ready when you can explain a wrong answer by stage: ingestion omitted context, filtering admitted the wrong scope, ranking missed the relevant chunk, or answer assembly dropped the citation.

Watch the whole bill: ingestion work, adapter maintenance, retrieval calls, context tokens, evaluation runs, and operational ownership. No single metric settles it.

If the broad REST boundary fits your system, start with the platform documentation and inspect the live discovery schema before writing the adapter.
