durable-viz: a new look across all six SDKs

Tanggal: 2026-11-25

Posted on Nov 25 • Originally published at gunnargrosch.com

durable-viz started as a way to see what an AWS Lambda durable function does. Point it at a handler and it draws the steps, parallel branches, callbacks, and conditions without deploying anything. The first version supported three SDKs and had a look that could charitably be called functional.

Version 0.14 changes the view and closes a few gaps I cared about. The diagram now reads like a set of cards, covers all six Durable Execution SDKs, and shows the spans the OpenTelemetry plugin will emit.

Each node is now a card with an icon, a kind label, and the operation name. Start and End are yellow circles. Parallel and loop bodies sit in thin rounded containers. Edge labels have their own boxes. The legend uses the same icons as the cards, so you can read the flow without memorizing the colors.

The view follows the host theme. In VS Code, the colors come from the editor theme, and the diagram re-renders when you switch between light and dark. In the browser, it follows the OS setting. Save PNG now exports the styled diagram with a solid background and margin. The export no longer drops the page CSS or clips labels.

The classic Mermaid output is still the default. That matters for READMEs, GitHub comments, and anyone piping the CLI output into another tool. The interactive browser page and the VS Code panel use the card view. If you call the renderer yourself, you have to opt in:

durable-viz now parses TypeScript/JavaScript, Python, Java, C#, Rust, and Go. Each SDK has its own entry point, builder style, and naming rules. The parsers share the same graph model and renderers, so the diagram stays consistent even when the source does not.

A child context or retry block used to appear as a black box. Now its body is drawn inside the same container, so you can see retries and child work on the main flow.

The OpenTelemetry plugin gives a durable execution one trace across invocations. durable-viz now detects the plugin registration in TypeScript/JavaScript, Python, and Java, follows imported helpers, and shows an OTel badge on the diagram. Click the badge to jump to the plugin registration.

The OTel tab shows the span tree the plugin should emit. At the top is the Workflow or Invocation root, followed by operation spans, attempt spans, nested operations, and branch children. It also warns about unnamed or duplicate operation names, so you can catch a broken trace hierarchy before you deploy. The tab reads the handler, not live traces.

The plugin itself ships for TypeScript/JavaScript, Python, and Java. The other three SDKs are supported in the diagram, but they do not have a durable OTel plugin today.

The --open flag starts a local interactive view in your browser. The VS Code panel refreshes when you save the file.

The VS Code extension is on the Marketplace and Open VSX.

What should the diagram show next? Real trace timings, or a deeper view of nested child contexts? Let me know in the comments.
