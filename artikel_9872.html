NestJS for Spring Boot developers: a TypeScript backend that will feel familiar

Tanggal: 2026-11-20

If your team writes Spring Boot and is about to build something in TypeScript (a new service next to a frontend that's already in TypeScript, a backend for a product that's moving off the JVM, or just a team that wants one language), the Node.js world can look like a pile of small libraries you're expected to assemble yourself. Express, a validation library, a DI container someone picked, a folder structure someone invented. That's the part that usually puts Spring developers off, and it's fair.

Nest is the framework that takes that decision away. Its architecture came from Angular rather than from Spring, but the two ended up close, because they solve the same problem: a container that creates your classes and wires them through constructors, controllers and services in layers, decorators that read like annotations, and first-party modules for configuration, validation, security, scheduling, health checks and OpenAPI. Most of what you know carries over.

This post is the tour I'd give a Spring team on day one: the tools, the structure, each Spring feature and its Nest counterpart with code on both sides, how it ships, and the differences that will actually bite.

Constructor injection, no @Autowired, and private readonly declares and assigns the field in one go. The one real difference is that there's no component scanning. Every provider belongs to a module, and the module lists it:

That looks like boilerplate at first, and I'd argue it's the best part. A module is a boundary Spring's application context doesn't have: OrdersRepository isn't exported, so no other module can inject it. In a big Spring codebase you rely on package conventions and ArchUnit tests for that. In Nest the container enforces it, and you can read what a feature exposes from one file. A module that needs OrdersService adds OrdersModule to its imports.

If a dependency can't be resolved, the app fails at startup with an error naming the class, the missing dependency and the module, much like Spring's "unsatisfied dependency" failure.

A @Bean method builds something you don't own, or something that needs setup:

In Nest it's a factory provider. inject lists what gets passed to the factory, in order, and the factory can be async:

And the starters? There's no auto-configuration. A package ships a module, and you import and configure it: ConfigModule.forRoot(), TypeOrmModule.forRootAsync(), ScheduleModule.forRoot(). Nothing turns on because it's on the classpath, which I think is the right trade for a language where "the classpath" is node_modules.

This is the first thing that trips Spring developers up. In Java you inject PaymentGateway, the interface, and the container finds the implementation. TypeScript interfaces are erased when the code compiles, so there's nothing left for the container to look up. Use an abstract class as the contract: it exists at runtime, so it doubles as the injection token.

Where you'd use @Qualifier("primary") to pick one of several beans of the same type, Nest uses a string or Symbol token and @Inject(TOKEN) on the parameter.

The defaults match, and you should keep them: almost every provider should be a singleton. Request scope works differently from Spring's, which I'll come back to under "What's actually different".

Here's the gotcha. In Java, Jackson builds the class you declared, so a request body is at least the right shape before validation even runs. TypeScript types are erased when the code compiles. Without a pipe, @Body() dto: CreateOrderDto is whatever JSON the client sent, with whatever fields it felt like sending. Register a validation pipe globally on day one and you never think about it again. Forget it and the compiler won't warn you.

The same thing in Nest. @Catch() names the exception types, like @ExceptionHandler:

Register it app-wide as a provider in the root module, { provide: APP_FILTER, useClass: OrderNotFoundFilter }, and it can inject other providers like any bean. Exceptions nobody handles become a 500 with a generic body, and the stack trace goes to the log, not to the client.

Spring Security's default is "everything requires authentication", and you open things up with permitAll(). @nestjs/authentication works the same way: the moment you register the module, every route answers 401 unless the request carries valid credentials, and @Public() opens a route. @CurrentUser() is your @AuthenticationPrincipal.

For @PreAuthorize, @nestjs/authorization uses policy classes. The check on a route is type-checked against the policy, so a typo in an ability name doesn't compile, which is more than a SpEL string gives you:

Its guard denies by default too, so a route that declares no check at all is closed, not open. Checks that depend on the record, the job you'd give @PostAuthorize, go in the service: authorizationService.authorize(OrderPolicy, 'view', user, order) throws when the policy says no.

application.yml and profiles become .env files and environment variables through @nestjs/config. Real environment variables win over the files, which is what you want in a container:

There are no profiles as such. NODE_ENV picks the file, and the first file in envFilePath that defines a variable wins, so .env.production overrides .env the way application-prod.yml overrides application.yml. The schema is checked at startup, so a missing or malformed variable stops the deploy instead of failing the first request that reads it.

@Value("${...}") becomes config.get('PAYMENTS_URL'), or getOrThrow() for a value that must be there. @ConfigurationProperties becomes registerAs(), injected with its type:

And @ConditionalOnProperty has a cousin in ConditionalModule.registerWhen(FeatureModule, 'FEATURE_ENABLED'), which imports a module only when an environment variable allows it.

TypeORM is the closest thing to JPA in Node: entities are decorated classes, and each module registers repositories for the entities it uses.

Two things you'll miss. Derived query methods: findByCustomerIdAndStatus becomes findBy() with an object of conditions, and anything bigger goes through the query builder. And @Transactional: transactions are a callback that commits when it resolves and rolls back when it throws.

@InjectRepository(Order) names the entity for the same reason interfaces don't work as tokens: Repository and Repository are the same class at runtime.

If you like jOOQ more than Hibernate, Drizzle is the other first-party option (@nestjs/drizzle): tables are plain TypeScript, queries look like SQL, and every result type is inferred from the schema, with no entity classes. MikroORM, whose unit of work and identity map are the closest thing to a JPA persistence context, Prisma and Mongoose all work too. Flyway or Liquibase migrations become the ORM's own migration tool, run as a separate step before the new version starts.

@Scheduled becomes @Cron() from @nestjs/schedule. Same six fields, seconds first:

A Nest cron job runs on every replica, exactly like @Scheduled. The second decorator is the ShedLock part: @OnOneInstance() from @nestjs/locks takes a lease in a store every instance shares, so the job runs on one of them. fixedRate becomes @Interval(ms).

ApplicationEventPublisher and @EventListener become @nestjs/event-emitter:

@Async has no counterpart, and you won't miss it: database calls and HTTP requests in Node are already asynchronous, so an async method that awaits them doesn't hold a thread while it waits. Work that should leave the request entirely, like sending emails or building reports, goes on a queue with @nestjs/bullmq, which plays the role a JMS or RabbitMQ listener does in Spring.

RestClient and WebClient become HttpClient from @nestjs/http-client, built on Node's own fetch. Each upstream service gets a named client with its base URL and timeout:

Resilience4j's timeouts, retries and circuit breakers become @nestjs/resilience. You describe each dependency once as a preset, and routes opt in with a decorator:

@Signal() injects an AbortSignal that fires when the attempt times out; pass it to the HTTP call and the request is actually cancelled, not just abandoned. Retries only apply to safe methods like GET by default, so a retried POST never charges a card twice. Inside services, where decorators don't apply, the same presets are available as policy objects.

Actuator's health endpoints become a controller using @nestjs/terminus, with separate liveness and readiness checks for Kubernetes:

(@Public() because @nestjs/authentication closes every route, and probes don't sign in.)

For logging, private static final Logger log = LoggerFactory.getLogger(OrdersService.class) becomes private readonly logger = new Logger(OrdersService.name). The built-in ConsoleLogger writes JSON with json: true, which is what your log pipeline wants in production; pino and winston plug in if you already have a preference. For the metrics and traces Micrometer and an APM agent give you, nest new offers to set up NestJS Observe, which reports requests, jobs and errors in terms of your controllers and providers.

Swagger UI is at /api. Its compiler plugin reads property types and optionality from your DTOs at build time, so you don't put @ApiProperty() on every field, and Zod schemas describe the document too.

For a @SpringBootTest, import AppModule instead and swap individual providers with .overrideProvider(OrdersService).useValue(fake). And for a plain unit test you need no framework at all: a provider is a class, so new OrdersService(fakeRepository) works.

You don't have to move a Spring codebase to Nest to start using Nest. The pattern I'd recommend:

The syntax takes a week. These take longer, so I'd rather you hear them from me than find them in production.

One thread. Spring MVC gives each request a thread. Node.js runs all of your code on one thread with an event loop: while a request waits for Postgres, the others run. That's why a modest Node process handles thousands of concurrent connections without any pool tuning, the same promise WebFlux and virtual threads make. The flip side is that CPU-heavy work in a handler, like hashing a big file or a long synchronous loop, blocks every other request in the process. Push that work to a queue (@nestjs/bullmq) or a worker thread, and scale with more processes instead of more threads. If your service is mostly number crunching, the JVM is the better runtime, and I'd say so to anyone.

No ThreadLocal, and request scope is contagious. Per-request state goes in AsyncLocalStorage, which follows a request through every await. Don't reach for request-scoped providers to get the current user: Spring injects a request-scoped bean into singletons through a proxy, but Nest has no proxies, so a request-scoped provider makes everything that injects it request-scoped too, all the way up to the controller, rebuilt on every request. Keep providers singletons.

No proxies, no AOP. Nest's DI reads constructor types from metadata the TypeScript compiler emits, once, at startup. There's no bytecode generation and no proxy around your beans. You lose @Transactional, @Cacheable and @Retryable on arbitrary methods, and you also lose the self-invocation trap that comes with them. Cross-cutting concerns live in interceptors, guards and pipes around route handlers, and in decorators from packages like @nestjs/resilience (on handlers) and @nestjs/locks (on scheduled jobs).

Types are a compile-time check. Interfaces and generic type arguments don't exist at runtime, which is why injection uses abstract classes or tokens, and why a request body, a database row or a message from another service is only as typed as the code that validated it.

Decorators are functions. A Java annotation is passive metadata read by reflection. A TypeScript decorator runs when the class is defined, and Nest's decorators use that moment to record what Nest reads at startup. You'll rarely notice, but it's why a decorator can take any expression as an argument.

Numbers are doubles. There's no BigDecimal. Keep money in integer cents, or use a decimal library and your database's numeric type, which most drivers return as a string anyway.

ES modules. A new project imports local files with a .js extension, even from .ts files, because that's the name of the compiled file. It looks wrong for about a day.

To be fair to Spring: if you have a large, healthy Spring codebase, a rewrite to get TypeScript is rarely worth it. If the work is CPU-bound, or depends on a JVM library with no Node equivalent, stay. And Spring's ecosystem for things like batch processing is deeper than anything in Node.

Nest is a good fit when the new thing is a new service, when the people building it also write the TypeScript frontend, or when you want one language from the browser to the database without giving up the structure you're used to.

Then nest g resource orders, and you have a module, controller, service, DTOs and tests to compare against the Spring version in your head. The Coming from Spring Boot page in the docs keeps this mapping as a reference, with a link from each row to its full chapter.

If something there doesn't match how you'd do it in Spring, tell me. It's written for you, and it's easy to fix.
