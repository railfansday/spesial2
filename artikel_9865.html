NestJS for ASP.NET Core developers: a TypeScript backend that will feel familiar

Tanggal: 2026-11-20

If your team writes ASP.NET Core and is about to build something in TypeScript (a service next to a frontend that's already in TypeScript, a backend for a product that's leaving .NET, or just a team that wants one language), the Node.js world can look like a pile of small libraries you're expected to assemble yourself. Express, a validation library, a DI container someone picked, a folder structure someone invented. Coming from a framework where dotnet new webapi gives you DI, configuration, logging, validation and a request pipeline out of the box, that's a step back, and it's a fair objection.

Nest is the framework that takes those decisions for you. It has a DI container with lifetimes, attribute-style routing, a pipeline of middleware and filters, typed configuration, and first-party packages for authentication, authorization, background jobs, health checks and OpenAPI. Most of what you know carries over.

This post is the tour I'd give a .NET team on day one: the tools, the structure, each ASP.NET Core feature and its Nest counterpart with code on both sides, how it ships, and the differences that will actually bite.

In Nest, services are registered in modules, and main.ts only creates the app from the root module:

Constructor injection, and private readonly works like a C# primary constructor. Where ASP.NET Core registers everything on one IServiceCollection, Nest registers providers in modules:

Think of a module as the AddOrders() extension method you'd write for a feature, with one addition: what it doesn't export stays private. OrdersRepository above can't be injected anywhere outside OrdersModule. In a large .NET solution you'd get that with separate projects and internal. Here the container enforces it, and you can read what a feature exposes from one file. A module that needs OrdersService adds OrdersModule to its imports.

If a dependency can't be resolved, the app fails at startup with an error naming the class, the missing dependency and the module.

A registration that builds the instance itself, like AddSingleton(sp => new S3Client(...)), becomes a factory provider. inject lists what gets passed to the factory, in order, and the factory can be async:

Libraries that you'd register with an AddXyz() extension method ship as modules you import and configure: ConfigModule.forRoot(), TypeOrmModule.forRootAsync(), ScheduleModule.forRoot().

AddScoped() is the first thing that has no direct translation. TypeScript interfaces are erased when the code compiles, so there's nothing left for the container to look up. Use an abstract class as the contract: it exists at runtime, so it doubles as the injection token.

Keyed services, AddKeyedSingleton() with [FromKeyedServices("primary")], become a string or Symbol token and @Inject(TOKEN) on the parameter.

Nest has the same three lifetimes, under different names:

The difference is the habit around them. In ASP.NET Core, scoped is everywhere, mostly because DbContext is scoped. In Nest, providers are singletons unless you say otherwise, and that's right for almost all of them. ORM clients are singletons holding a connection pool, so there's no per-request context to scope.

And request scope behaves differently. ASP.NET Core's scope validation, on by default in Development, rejects a scoped service injected into a singleton as a captive dependency. Nest instead makes the singleton request-scoped too, along with everything up to the controller, and rebuilds that chain on every request. It works, but it's slower and rarely what you meant. When you need the current user or tenant deep in a service, read it from AsyncLocalStorage, which flows through await the way AsyncLocal does, instead of reaching for an IHttpContextAccessor equivalent.

IHostedService.StartAsync() and StopAsync() have counterparts too: any provider can implement onApplicationBootstrap() and onApplicationShutdown().

There's no app.MapGet("/orders/{id}", ...) style in Nest. The smallest Nest app is still a controller and a module, and nest new orders-api --minimal puts them in a single file, src/main.ts. It grows into the layout above by moving things out of that file, not by rewriting them.

An interceptor is an IAsyncActionFilter, with next.handle() in place of await next():

next.handle() returns an RxJS stream of the handler's result, which the interceptor can transform before it goes out, the way a result filter would.

In Nest, @Catch() says which exception types a filter handles, so there's no type check to write:

Register it app-wide as a provider in the root module, { provide: APP_FILTER, useClass: OrderNotFoundFilter }, and it can inject other providers. Exceptions nobody handles become a 500 with a generic body, and the stack trace goes to the log, not to the client.

One thing to know if your clients parse problem details: Nest's own error responses, validation errors included, are not RFC 9457 problem details out of the box. They're plain JSON objects with a statusCode and a message. If you need problem details everywhere, one catch-all filter like the one above does it.

[ApiController] validates models before your action runs, with rules from Data Annotations:

In Nest, a global pipe does that job. With classes, it's class-validator decorators and ValidationPipe:

whitelist drops fields the DTO doesn't declare, and transform turns the body into an actual CreateOrderDto instance.

If you like FluentValidation's rules-in-code style better, Nest 12 takes a Zod (or any Standard Schema) schema per parameter, and the parameter's type is inferred from it:

Here's the gotcha. System.Text.Json creates the type your action declares, so a body is at least the right shape. TypeScript types are erased when the code compiles. Without a pipe, @Body() dto: CreateOrderDto is whatever JSON the client sent. Register a validation pipe globally on day one and you never think about it again. Forget it and the compiler won't warn you.

@nestjs/authentication closes every route the moment you register it, like a fallback policy that requires an authenticated user, and @Public() is your [AllowAnonymous]:

Authorization will feel natural if you use policies. @nestjs/authorization puts them in classes, and the check on a route is type-checked against the class, so a misspelled ability doesn't compile:

Resource-based authorization, AuthorizeAsync(User, resource, policy), is authorizationService.authorize(ProductPolicy, 'view', user, product) in a service. And the guard denies by default, so a route that declares no check is closed.

appsettings.json, the per-environment files and environment variables become .env files and environment variables through @nestjs/config. Real environment variables win over the files, as they do in .NET:

NODE_ENV plays the role of ASPNETCORE_ENVIRONMENT, and the first file in envFilePath that defines a variable wins, so .env.production overrides .env the way appsettings.Production.json overrides appsettings.json. The schema is your ValidateOnStart(): a missing or malformed variable stops the app at startup instead of failing the first request that reads it. Keep secrets out of committed files, the way you'd use user secrets locally and a vault in production.

configuration["Orders:PageSize"] becomes config.get('ORDERS_PAGE_SIZE'), or getOrThrow() for a value that must be there. IOptions becomes a registerAs() namespace, injected with its type:

There's no EF Core in Node, and I won't pretend otherwise: nothing matches LINQ. TypeORM is the closest in shape, with entity classes, a repository per entity in place of a DbSet, and migrations:

orders.Where(o => o.CustomerId == id && o.Status == OrderStatus.Pending) becomes findBy() with an object of conditions, and anything bigger goes through the query builder. There's no SaveChanges() sweeping up tracked changes: save(), insert() and update() write when you call them. Transactions are a callback that commits when it resolves and rolls back when it throws, where you'd write a using var transaction block with CommitAsync():

@InjectRepository(Order) names the entity for the same reason interfaces don't work as tokens: Repository and Repository are the same class at runtime.

The alternatives: MikroORM is the closest in behavior, with a unit of work and an identity map like EF's change tracking, and its em.flush() is the one that works like SaveChanges(). Drizzle (@nestjs/drizzle, the other first-party option) is the one I'd point a Dapper fan to: typed SQL, inferred result types, no entities. Prisma and Mongoose work too. dotnet ef migrations becomes the ORM's own migration tool, run as a separate step before the new version starts.

A BackgroundService splits into three tools, depending on what it does.

Work on a timer becomes @Cron() from @nestjs/schedule:

A Nest cron job runs on every replica, just like a hosted service does. @OnOneInstance() from @nestjs/locks takes a lease in a store every instance shares, so the job runs on one of them, the way you'd use a Hangfire recurring job or a distributed lock.

Work handed off by a request (send this email, build that report) goes on a queue with @nestjs/bullmq, with retries and delays, which is what Hangfire's background jobs give you. And startup or shutdown work goes in the onApplicationBootstrap() and onApplicationShutdown() hooks from earlier.

And if you use MediatR for commands and queries, @nestjs/cqrs has command and query buses with handlers in the same style.

IHttpClientFactory with typed clients becomes HttpClient from @nestjs/http-client, built on Node's own fetch. Each upstream service gets a named client with its base URL and timeout:

Polly's timeouts, retries and circuit breakers become @nestjs/resilience. Like a named resilience pipeline, you describe each dependency once as a preset, and routes opt in with a decorator:

@Signal() injects an AbortSignal, the JavaScript CancellationToken, which fires when the attempt times out. Pass it to the HTTP call and the request is actually cancelled. Retries only apply to safe methods like GET by default, so a retried POST never charges a card twice. Inside services, where decorators don't apply, the same presets are available as policy objects.

(@Public() because @nestjs/authentication closes every route, and probes don't sign in.)

ILogger becomes private readonly logger = new Logger(OrdersService.name). The built-in ConsoleLogger writes JSON with json: true, and if you're used to Serilog, pino plugs in the same way. For the traces, errors and metrics Application Insights gives many .NET teams, nest new offers to set up NestJS Observe, which reports requests, jobs and errors in terms of your controllers and providers.

Swashbuckle and NSwag become @nestjs/swagger:

Swagger UI is at /api. Swashbuckle gets your types by reflection. TypeScript has no runtime types to reflect on, so @nestjs/swagger comes with a compiler plugin that reads property types and optionality from your DTOs at build time, and you don't put @ApiProperty() on every field. Zod schemas describe the document too.

You don't have to move an ASP.NET Core codebase to Nest to start using Nest. The pattern I'd recommend:

The syntax takes a week. These take longer, so I'd rather you hear them from me than find them in production.

async/await looks identical, and the runtime isn't. I/O behaves the same: while a request awaits the database, others run. But ASP.NET Core runs continuations on a thread pool, and Node.js runs all of your JavaScript on one thread. CPU-heavy work in a handler, like hashing a big file or a long synchronous loop, stalls every other request in the process, and there's no Task.Run() to push it aside. Move it to a queue or a worker thread, and scale with more processes or containers. If your service is mostly computation, .NET is the better runtime, and I'd tell anyone that. On the bright side, there's no SynchronizationContext and no ConfigureAwait(false) to think about.

No cancellation token unless you ask. ASP.NET Core binds RequestAborted to a CancellationToken parameter. Nest handlers get nothing by default. The JavaScript equivalent is an AbortSignal, and the HTTP client, fetch() and @nestjs/resilience all take one.

Types are a compile-time check. Interfaces and generic type arguments don't exist at runtime, which is why injection uses abstract classes or tokens, and why a request body, a database row or a message from another service is only as typed as the code that validated it. There's no reflection to fall back on.

Decorators are functions, not attributes. An attribute is passive metadata read by reflection. A decorator runs when the class is defined, and that's how Nest records what it reads at startup. In practice you'll rarely notice, but it explains why decorators can take arbitrary expressions.

Numbers are doubles. There's no decimal. Keep money in integer cents, or use a decimal library and the database's numeric type, which most drivers return as a string.

No LINQ. Array methods (filter, map, reduce) cover in-memory queries, and query builders cover the database, but nothing composes over both like IQueryable does.

ES modules. A new project imports local files with a .js extension, even from .ts files, because that's the name of the compiled file. It looks wrong for about a day.

To be fair to .NET: if you have a large ASP.NET Core codebase that works, a rewrite to get TypeScript is rarely worth it. If the work is CPU-bound or leans on EF Core's LINQ for complex queries, stay, or put the TypeScript service next to it rather than in place of it.

Nest is a good fit when the new thing is a new service, when the people building it also write the TypeScript frontend, or when you want one language from the browser to the database without giving up the structure you're used to.

Then nest g resource orders, and you have a module, controller, service, DTOs and tests to compare against the ASP.NET Core version in your head. The Coming from ASP.NET Core page in the docs keeps this mapping as a reference, with a link from each row to its full chapter.

If something there doesn't match how you'd do it in .NET, tell me. It's written for you, and it's easy to fix.
