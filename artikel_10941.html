Prerequisites: Code samples require TypeScript 4.0 or later and a tsconfig.json with "target": "ES2016" or higher and "strict": true. The FormState recursive type alias requires TypeScript 3.7+.

Boolean flags paired with optional fields are a common source of impossible-state bugs in TypeScript codebases. Discriminated unions eliminate these invalid states at compile time, so the compiler rejects objects that combine fields illegally. This article traces the pattern from its simplest form through a common the pitfalls of building members from booleans and into a fully typed multi-step form state machine with an exhaustive reducer.

Consider a common pattern: a response object shaped as { success: boolean; data?: string[] }, where data exists only when success is true. TypeScript cannot enforce this relationship. The type system sees data as string[] | undefined regardless of the value of success, because both fields belong to a single interface. Nothing prevents a caller from constructing { success: true } with no data, or { success: false, data: ['oops'] }.

The non-null assertion hides the real problem. The type permits a state that the business logic considers impossible, and the compiler cannot help.

Control-flow narrowing in TypeScript operates on the type of the property being checked, not the shape of the enclosing object. When the type is a single interface rather than a union, checking if (res.success) narrows res.success from boolean to true within that branch, but it does not change the type of res itself. The object's shape remains ApiResponse, and data stays string[] | undefined. To narrow an object's shape, its type must be a union of distinct types in the first place. Without that union, the compiler has nothing to narrow to.

Discriminated unions combine multiple object types that share a common property whose type is a unique string, number, or boolean literal in each variant. This shared property is called the discriminant property. The pattern is also known as a tagged union or algebraic data type. When code branches on the discriminant, TypeScript narrows the entire object to the specific variant, making all fields of that variant available without assertions.

The compiler rejects the impossible state entirely. If success is true, data must be present. If success is false, providing data causes a type error.

A different construction problem shows up when a union member is built from a runtime boolean. A variable typed boolean is the union true | false, and the object { b: flag, c: value } has to fit one member of Result below. The first option builds each variant in its own branch. Each branch returns an object literal that matches exactly one union member, so c only exists when b is true. The second option uses a generic type parameter constrained to true | false, allowing the compiler to resolve the correct branch based on the argument's literal type at each call site. A runtime guard protects against callers passing a widened boolean value, which can bypass the compile-time conditional rest type guarantee (a boolean-typed argument makes the rest type [c: number] | []).

switch on a discriminant property narrows the union to exactly one variant per case block. Each case branch sees only the fields defined for that variant. While if/else if chains work identically for narrowing purposes, switch is the conventional choice for tagged unions because it maps one branch per variant and integrates naturally with exhaustiveness checking via a default clause.

When a unique property exists only in one variant, the in operator can narrow without a dedicated discriminant field. Checking if ('data' in obj) narrows to the variant containing data. However, this approach is less explicit, harder to exhaust systematically, and breaks when two variants share a property name, since the in check can no longer distinguish between them. Use it to supplement, not replace, literal discriminants.

Exhaustiveness means branching logic handles every member of a union. When a new variant is added to the union, the compiler flags all unhandled cases. Without exhaustiveness, adding a variant silently falls through existing branches, typically into a default case that was written for a different set of states, producing runtime errors that surface only after refactors reach production.

The canonical exhaustiveness technique places an assertNever function in the default branch of a switch. If every variant is handled, the remaining type in default is never. If a variant is missed, the type is not never, and the assignment to the never parameter fails at compile time. In a pure TypeScript codebase this line is unreachable at runtime; it guards against JavaScript callers or unsafe type assertions that bypass compile-time checking.

A FormState type with a kind discriminant models each step as a distinct variant. Each variant carries only the data relevant to that step, making impossible combinations unrepresentable. The FormState type uses a recursive type alias (supported since TypeScript 3.7) to allow the error variant to reference FormState itself.

The step2 variant includes validated step1Data, ensuring that reaching step two without completing step one is structurally impossible. The error variant carries lastState for retry logic, but excludes nested errors via Exclude.

Actions model the transitions between states. Each action is its own tagged union member. The NEXT action is split into step-specific variants so that each transition carries only the data relevant to its source step, preventing structurally incomplete payloads.

The reducer uses nested switch statements. The outer switch dispatches on state.kind, the inner on action.type where multiple actions apply to a single state. Both levels use assertNever to guarantee exhaustiveness.

Each inner switch must enumerate every member of FormAction, either as a handled transition or an explicit no-op, for the default branch to see never. This verbosity is the cost of the pattern, and it pays for itself: adding a new action type to FormAction produces compile errors in every inner switch that does not list it.

A flat alternative like { step: number; isSubmitting: boolean; error?: string; data?: object } permits states that should never exist: isSubmitting: true with error defined simultaneously, step: 3 with no data from steps one or two, or error populated while isSubmitting remains true. With the flat type, you write guards like if (state.isSubmitting && !state.error) at every consumption site. The discriminated union eliminates these guards structurally. Adding a sixth state to the union triggers compile errors everywhere the reducer and any consuming code fails to handle it.

The ?: never pattern works by marking a property as optional with type never, which prevents any non-undefined value from being assigned; undefined remains assignable unless exactOptionalPropertyTypes: true is set in tsconfig.json. It is useful for lightweight exclusive-field constraints but provides none of the narrowing or exhaustiveness guarantees that discriminated unions offer.

Discriminated unions fit well in these scenarios:

Two-variant unions also get compile-time exhaustiveness and narrowing from the pattern, as the ApiResponse example earlier demonstrates.

Using string instead of a string literal for the discriminant defeats narrowing entirely. With kind: string on every variant, switch (x.kind) does not narrow the union, so reading a variant-only field such as x.a inside case 'a' fails with error TS2339 (property does not exist on the union).

Building union members from a runtime boolean without branching can produce objects that carry fields the other variant should not have, even when the compiler accepts it (see above).

Nesting unions more than one level deep (a discriminated union inside another discriminated union) complicates narrowing and makes reducers harder to read. Prefer flat discriminants with descriptive kind values like 'step2-loading' over nested structures.

Boolean flags hide impossible states behind runtime assumptions. Discriminated unions surface those states at compile time, and exhaustive checking with assertNever ensures that future additions to the union cannot silently slip through existing code paths.
