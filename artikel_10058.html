How We Could Have Backdoored Bash (Hacktron blog)

Tanggal: 2026-11-03

Given the increase in supply chain attacks, I really don't understand why so many projects still feel comfortable to fully rely on centralized, server-side security mechanisms. Almost every time I look at a real or potential supply chain attack, I cannot help but wonder how much more difficult or fragile the attack would have been if regular code signing would be more ubiquitous.

Almost every modern system has a HSM, Secure Enclave, or whatever; and if you don't like those, there are OpenPGP-smartcards, YubiKeys, ... you name it. If you don't like PGP, OpenSSH also supports signing for over six years now, including FIDO2-backed signatures. Git support for OpenPGP signatures goes back for decades, and OpenSSH signatures are also supported for more than 5 years now. Yet, nobody seems to care – worse, even basic infrastructure like cargo, pip, npm, etc., don't offer an optional possibility to attach and require signatures.

To be clear: I neither blame individual developers nor maintainers; I'm a big fan of provided-as-is – nobody should be forced to buy a YubiKey just because they are hobby devs. Nonetheless if we operate at an institutional scale, where we have legal entities and supply core infrastructure... I don't get it – not even to blame someone, I just simply don't get it.

Classical banking provides a more nuanced (if less formalized) picture. Entities have credit risk, collateral must be made available, and all sorts of derivatives are traded against those things. The trading is both hedging (to protect yourself against a business partner's default) and speculative (because you have an opinion about their decline or recovery). Clearing houses like the Options Clearing Corporation create a safe harbor for mutual trust by holding its members to a high standard of credit-worthiness. In technology we have lots of perfectly correct, cryptographically-sound signing solutions. We don't have the semi-formal credit systems that banking has shown to mostly work. I think this is largely because trust is radically efficient, and mistrust carries a lot of overhead and capital drag. It's better if we can rely on trust, but best if we could formalize credit efficiently and solve for distributed trust management.

Definitely, trust is hard, and code signing is by no means a silver bullet; it only helps against certain attack scenarios, and also has to be applied correctly. Nonetheless, E2E signature chains make a lot of attacks much harder or fragile or – in abstract terms – more expensive.

It's a bit like saying: TLS is not perfect, CAs are not secure, and someone might roll a private key of 4 (obligatory xkcd). Nonetheless, nobody would seriously argue that we probably should ditch TLS and go back to plain HTTP.

Of course, this doesn't scale well (especially to regular people which often don't even know what TLS is), but if you don't need to trust many web servers (and I don't) and your users are capable of verifying a PGP signature manually (mine can), it can be enough.

This is on top of needing to repeat the PGP verification step manually for each new server (or each new key rotation), rather than verifying the private CA just once... For v3 certificates CA:FALSE is also the default if the whole extension is absent. The point though is that trust anchors have different treatment from regular certificates. I've heard that some platforms ignore most of the metadata of a cert that's been specified as a trust anchor (e.g. root CA expiry dates certainly seem to be commonly ignored), and/or the fact that they're installed into a "Trusted *authorities*" store is interpreted as a user override of the CA:FALSE, and/or something along those lines. So if one tells users "install my web server's self-signed certificate into /etc/ssl/certs, it has CA:FALSE so it's safe", I'd be more than a little cautious about that. Well, of course, the same goes for a whole personal CA – but what I mean to say is, telling users "install my whole CA into /etc/ssl/certs" is *explicitly* an informed trust decision, while telling users "install my web server cert into /etc/ssl/certs" can be an accidental trust decision that *looks* like it is scoped to a single server but secretly is much broader. Even with SHA-1, this is not feasible. While the collision resistance of SHA-1 is broken and you can craft special pairs of inputs that share the same arbitrary hash, the pre-image resistance still is comparatively solid – finding a different input for a given hash is still not practical.

There are some attacks for very long messages (2^100 operations for 2^60 bytes), but for the given scenario "commit hashes unchanged [aka given] and the diffs relatively similar", there are no known attacks against SHA-1. We still should probably switch to SHA-2 sooner than later nonetheless; but for this specific requirement, SHA-1 is still more than strong enough for now.

If you have A-B-[you merge C]-C'-[others pull]-[others push]-[you pull because others pushed], you will be the only one who has a diverging history. Now, if that is a problem depends on your git config – if you have pull.ff, git will abort; but if you have pull.rebase or pull.no-rebase, you need to be rather vigilant to notice anything.

As an attacker, I probably would also try to insert a new commit instead of rewriting one; but on the other hand if you know that people are using (no-)rebase, a silent rewrite would be really hard to detect afterwards. And (no-)rebase is not super uncommon in my experience, because depending on how you or your team work, feature branches are not necessarily linear.

If I were an attacker, I think crafting an evil Merge remote-branch 'master' into 'my-topic' commit which adds the evil content among a sea of "sync" changes in a contribution would be a juicy target. Especially in squash merge workflows.

I really need to finish the "reject up-merges" check to ban such "wrong way" merges…but any merge commit is ripe for abuse. At least in the standard forge-based flows. Email, Gerrit, and other per-patch mechanisms would be "immune" from it just by the fact that they don't handle merge commit contributions like that.
