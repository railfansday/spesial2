Image AI in the browser or on a CPU server: what we run where, and why

Tanggal: 2026-11-27

oMyImage is a free set of image tools: compress, resize, convert, and a handful of AI ones like removing a background or an unwanted object. We wanted as much as possible to run in the browser, so photos stay on the user's device. Some of it does. Some of it can't, and the reasons turned out to be more interesting than "the model is too big".

Our server has no GPU. It's four virtual CPUs shared with the PDF tools on our sister site. That one fact shaped almost every decision below.

To remove an object or watermark you paint over it, and MI-GAN fills the hole. It's an MIT-licensed inpainting model, and the ONNX file is 28,079,181 bytes.

Our host, Cloudflare Pages, rejects any single file over 25 MiB. So the model ships as two parts. The browser fetches both in parallel, streams them into one preallocated buffer (which also drives the progress bar), then checks the SHA-256 before trusting it:

The first 8 characters of the hash are in the file name, so the files can be cached for a year with immutable. There's no IndexedDB or Cache API code at all. The plain HTTP cache does the job.

ONNX Runtime Web runs here on WebAssembly, on the CPU. Its WebGPU builds are 27 MB each, again over the per-file limit, and our notes put MI-GAN at about a second on a laptop CPU anyway.

Multi-threaded WebAssembly needs SharedArrayBuffer, which needs cross-origin isolation headers, which break third-party popups. For a model this small, one thread in a worker was the better trade.

One small bug shaped the pipeline. MI-GAN works on a 512 px crop around the hole. If you mark two small spots in opposite corners, one crop around both is nearly the whole image, shrunk to 512 px, and the fill comes out blurry. So separate marks are found on a 16 px grid and filled one region at a time, each with some surrounding context.

Face blurring uses MediaPipe's BlazeFace model. The model is only 0.23 MB, but the WebAssembly runtime is 11.8 MB, and we host both ourselves. MediaPipe's examples load from a CDN, but our page says nothing leaves the device, and that should be literally true.

Our first rule copied the PDF site's: files up to 15 MB stay in the browser. For images, that was wrong in both directions.

The router now decides on decoded pixel area, and probes the canvas instead of trusting it. It paints the far corner and reads it back. Over the limit, Safari hands back zeros. We tested it with a 1,000-megapixel canvas that "worked" and returned [0,0]. If the probe fails, the tool retries on the server.

Background removal runs rembg with the U²-Net model on the server. It takes about 6 to 7 seconds per image. We assumed bigger images were slower. They aren't: the time is almost all spent loading the 168 MB model into a fresh process on every request. Image size barely matters, so there's no size cap on this route. (Keeping the model loaded in a long-running worker is the obvious next step.)

Upscaling uses Real-ESRGAN through its ncnn/Vulkan build. With no GPU, Vulkan falls back to Mesa's software renderer on the same four CPUs.

On a 512×384 test image, the standard x4plus model took 3 minutes 29 seconds and 12 minutes of CPU time. The much smaller realesr-animevideov3 model took 8 seconds. A normal 12-megapixel phone photo with x4plus would have pinned every core for tens of minutes and hit nginx's 300-second timeout while still running.

So production uses the smaller model (yes, an anime-video model on photos; it does a decent job, and the trade-off is written down), and the size is checked before the process starts:

Anything larger gets a clear 413 instead of a timeout. Two smaller lessons from the same tool:

iPhone photos are HEIC, and people want JPG. There are several JavaScript HEIC decoders, but they're all the same Emscripten build of libheif, which is LGPL-3.0. Sending it to the browser counts as distributing it, which brings source and relinking obligations. Running it on our server is just running a service.

We couldn't use our usual image library either. sharp's prebuilt binaries include libheif with only the AVIF decoder, not HEVC. So HEIC goes to ImageMagick built with libheif, on the server. It's the one tool where the user-facing text says plainly that the file is uploaded.

All of this shares four CPUs, so the heavy image routes go through a small queue:

The queue is bounded on purpose. An unbounded queue holds every waiting upload in memory, which is a reliable way to hit the process manager's memory limit and restart the API for everyone.

Results are deleted after an hour. One easy-to-miss detail: scratch folders must be named omyimage-
