Why WireGuard Fails on LXC NAT VPS (and How to Fix It)

Tanggal: 2026-11-17

Posted on Nov 17 • Originally published at vpsfree.io • AI-assisted

You've got a cheap NAT VPS – shared IPv4, a small range of forwarded ports, maybe 192 MB of RAM inside an LXC container – and you want your own WireGuard VPN on it.

You run the popular install script and get this:

…or a script that refuses to run with "LXC is not supported".

This post explains why that happens, how to tell in one line whether your box can do it, and the minimal setup that works on a NAT VPS with only a handful of forwarded ports. I tested every step on a 192 MB LXC container on an AMD EPYC host – screenshots below.

WireGuard lives in the Linux kernel. A VM (KVM) has its own kernel and can load the module itself. An LXC container shares the host's kernel and isn't allowed to load modules. So it depends entirely on the host:

The user-space alternatives (wireguard-go, boringtun) need /dev/net/tun passed into the container – which many hosts don't do either.

WIREGUARD OK → continue. Not supported → the host doesn't allow it, no amount of apt installing will fix that.

The only NAT-specific part: WireGuard must listen on one of your forwarded UDP ports. In my case the range is 20001-20019, so I use 20001. Replace it with yours.

Only the user-space tools – the kernel part comes from the host, so don't install wireguard-dkms.

The accept_ra = 2 line matters: turning on IPv6 forwarding normally makes Linux ignore router advertisements, which can silently kill your VPS's own IPv6.

Clients get private IPv4 + ULA IPv6 addresses and are masqueraded out, so the tunnel works for both IPv4 and IPv6 sites even though the IPv4 is shared.

Scan it in the WireGuard app (+ → Scan from QR code). The QR contains a private key – don't post it anywhere.

PersistentKeepalive = 25 is worth keeping on NAT setups: it stops the connection-tracking entries on both sides from expiring while the tunnel is idle.

A recent latest handshake and growing transfer = done. Browsing to ifconfig.co from the phone now shows the VPS address:

The port is wrong or blocked. ListenPort and the port in Endpoint must match and be inside your forwarded range. If you run ufw in the container: ufw allow 20001/udp.

Forwarding or NAT is missing. Check sysctl net.ipv4.ip_forward returns 1 and iptables -t nat -S shows the MASQUERADE rule.

Classic MTU issue. Add MTU = 1280 under [Interface] in the client config and reconnect.

ping prefers IPv6, and some routes filter ICMPv6 echo. Try ping -4 google.com – if that works, your network is fine.
