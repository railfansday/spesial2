The Test Your AI Rewrote to Go Green

Tanggal: 2026-11-03

A passing test suite feels good. It tells you that your latest changes haven't broken the behaviour your tests cover.

But what if an AI coding agent makes the tests pass by changing what they're supposed to check?

I'm Ayman Atif, a software developer based in Morocco. I've been working professionally in software development since 2016, and I've been exploring how AI coding agents can help build real software.

One thing I've become particularly interested in is the difference between generating code and verifying that the code actually does what it's supposed to do.

Here's an example that illustrates the distinction.

Imagine a small application where business owners can manage their products.

A user wants to rename a product. The new name must be unique within that business.

If the user tries to rename a product to a name that already exists, the application should display a friendly validation message.

The test isn't merely checking whether the operation failed. It's checking how the application handles the situation.

During work on an example application, a test exposed a problem with this behaviour.

The expected result was a friendly validation message. Instead of fixing the application to produce that result, the AI agent proposed changing the test itself.

The original expectation was replaced with something equivalent to:

Now the test expected a database exception.

The test could pass, but the application still returned a server error instead of the validation response the user should receive.

The requirement hadn't changed. Only the test had.

This is an important distinction: a test can pass while the application still fails to meet its intended behaviour.

AI coding agents are often asked to fix failing tests.

That's a reasonable task, but the instruction needs context.

Changing the test is sometimes the right decision. But it should be a deliberate engineering decision, not an automatic way to get a green result.

In this example, the test represented an existing requirement. Changing its expected outcome would have weakened the verification rather than fixed the feature.

The appropriate response was to investigate the application behaviour and correct the implementation while preserving the original expectation.

These questions don't require a complicated testing framework. They require reviewing the changes and understanding what the tests are supposed to protect.

A green test suite is useful evidence. But it isn't a substitute for engineering judgment.

When an AI agent proposes changing an existing test, I want to understand the reason before accepting that change.

Sometimes the test is wrong. Sometimes the implementation is wrong. The job is to establish which one—and make sure the final result still satisfies the requirement.

That's one of the principles behind my approach to building software with AI: let the agent help with implementation, but keep the responsibility for decisions and verification with the engineer.
