Catch Overlapping Labels Before Rendering With a Sweep Over X

Tanggal: 2026-11-07

Posted on Nov 7 • Originally published at homingolearn.blogspot.com

A label that fits today can land on its neighbor tomorrow when someone renames a metric or adds a series, and you may not notice until the chart is on screen. You can flag likely collisions without rendering by estimating a box for each label and checking the boxes against each other.

To find collisions, sort the labels by left edge and walk through them, keeping an active list of boxes that may still overlap something. Each new label does three things:

Removing a box is safe because of the sort order. Every later label starts at or to the right of the current one, so a box that ends at or before the current left edge can't overlap any of them.

Every box left in active starts at or before the current left edge and ends after it. For a label with nonzero width, that guarantees overlap in x, so only y needs testing.

Comparisons are strict, so boxes that merely touch don't count as colliding.

The check reports four colliding pairs and prints FAIL. Net margin, Q3 forecast, and Churn all collide with one another, while Revenue and Refunds collide separately, so moving one label won't clear the report.

The sweep ran 10 y tests where checking all pairs would take 21, but that saving depends on this layout. The count also leaves out the sort and the x comparisons that filter active.

If every pair of boxes overlaps in x, nothing is ever removed from active, and the sweep tests all pairs. A single left-aligned column of non-empty labels does this. The sweep saves y tests only when some boxes don't overlap in x.

The program asserts that the sweep finds the same set of pairs as a brute-force pass over all combinations. This check can fail: change other.x1 > label.x0 to >=, and Refunds stays active when Net margin arrives. The sweep then reports a pair that brute force rejects, and the assertion fires.

Small overlaps may not be real. Revenue and Refunds overlap by 4.0 units in x, while one estimated character at size 10 is 6 units wide. Real glyphs could shift that result either way, and the same goes for the exact touch at x 90. To flag near misses as well, inflate each box by a margin before testing. The program doesn't do this, so you'd need to choose and test a margin yourself.

Text length is a crude measure of width. At the same size, a string of i and a string of W get the same estimated width if they have the same length. len() also counts code points, so emoji, combining marks, and wide scripts can be badly misjudged.

Coordinates must mean what the code assumes. x0 is the left edge and y0 is the edge from which height is added. Convert centered or right-aligned labels before building a Label.

Empty labels break the x guarantee. A zero-width box inside another box's x range and overlapping its y range is reported by the sweep but rejected by brute force. Filter out empty strings first.

Printing FAIL won't stop a build. The script exits normally when it finds collisions. To use it as a gate, import sys and call sys.exit(1) when hits is not empty.

This check is an early warning based on estimated boxes, not a verdict on the rendered result. It stops being enough when the exact font matters, or when labels are rotated, wrap across lines, or get moved at render time. It also ignores collisions with anything that isn't a label, such as lines and markers. In those cases, measure the rendered text and check the measured boxes, using the same sweep if the boxes are axis-aligned.
