Solr's security.json Is Not a Safe Read for Low-Trust Administrators

Tanggal: 2026-11-25

Access to cluster coordination data can reveal more than topology. Apache Solr CVE-2026-53672 shows how a zk-read role can cross into authentication configuration.

Apache published CVE-2026-53672 on 2026-11-22. The ZooKeeper HTTP endpoints in affected Solr releases allow an authenticated user with zk-read permission to read /security.json without the separate security-read check. The file can contain credential hashes and authorization configuration. Affected versions are Solr 8.11.1 through 9.10.x and Solr 10.0.0. The fixed releases are 9.11.0 and 10.1.0. The CVSS 3.1 score is 6.5.

The advisory lists three requirements: the deployment uses Solr's Basic Auth plugin, the attacker has direct network access to the cluster, and the attacker holds credentials for an account with zk-read permission. That combination is narrower than an unauthenticated internet break-in, but it is still a meaningful separation of duties failure. zk-read is often assigned to operators who need coordination visibility, not to people who should be able to collect authentication material.

A password hash is not plaintext, but it can support offline guessing when the attacker also knows the account names and hash format. Authorization configuration can reveal protected paths, roles, and the identities worth targeting. Rotating the affected accounts is therefore more reliable than assuming the hash algorithm made the disclosure harmless.

Upgrade to Apache Solr 9.11.0, 10.1.0, or later. If the upgrade must wait, grant zk-read only to users who are trusted to read security.json, as the advisory recommends. Restrict direct access to Solr and ZooKeeper management interfaces, and review whether any non-administrative automation holds the permission. After changing access, verify both the authorization rule and the actual endpoint response with a low-privilege test account.

Review Solr and ZooKeeper request logs for reads of /security.json from accounts that should not have security-read authority. Check for new administrator sessions, rule changes, or source addresses that indicate follow-on access. If the file was disclosed, rotate the credentials represented in it and review all role assignments. Record the fixed version and the reduced permission set so the next audit can prove the control remained in place.
