Upgrading Old PHP Versions Safely With Rector and CI

Tanggal: 2026-11-21

In almost every legacy PHP project Loop Origin takes on, the first question is the same: which PHP version is production on? The answer is often 7.2 or 7.4, sometimes 5.6, on a server nobody wants to touch. PHP 7.4 reached end of life in November 2022, and PHP 8.0 followed a year later, so these apps run without security fixes and block every modern package. The team knows it. The upgrade keeps getting postponed because it feels like one big risky jump.

It does not have to be one jump. With the strangler fig from Part 1 and clean module boundaries from Part 2, the version upgrade becomes a series of small, tested pull requests that each leave production working. This post is the playbook I use.

I wrote this with help from AI tools and checked the tooling details against the Rector, PHPStan and PHPCompatibility documentation and the official PHP migration guides. I am a Principal Software Engineer in Karachi with 9+ years maintaining Laravel and plain-PHP systems, and the numbers below come from real upgrades, not benchmarks.

Direct answer: Add CI that runs your tests on both the current and target PHP versions, scan for incompatibilities with PHPCompatibility and PHPStan, let Rector apply the mechanical code changes in small batches, upgrade Composer dependencies one at a time, then roll the new runtime out to one server or container first, with a quick way back.

None of these is enough alone. Static tools miss dynamic code (call_user_func, string class names, extract()), and tests rarely cover everything in a legacy app. Together they catch most of it.

If the app has no tests, I do not start by writing unit tests for everything. I write 20 to 40 HTTP-level characterization tests for the money paths: login, checkout or invoicing, the main reports, any import job. They record what the app returns today, so I know when an upgrade changes it.

The key idea: code must pass on the old version and the new one at the same time, so every PR can ship to the current production server.

At first the 8.3 job fails. That is fine. Mark it allowed-to-fail, and the list of failures becomes your backlog.

Rector applies the mechanical changes: each() loops, curly-brace string offsets, create_function, implicit nullable parameters, and so on. Configure it to stay compatible with the old version first, then raise the target later.

I run Rector one directory per PR, using the module boundaries from Part 2. A 300-line diff gets reviewed properly; a 30,000-line diff gets rubber-stamped.
