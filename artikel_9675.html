LogTreeDB: Building a Crash-Safe, Zero-Dependency Document Database from Scratch in C++17

Tanggal: 2026-11-19

Author: Praveen Kumar Date: November 2026

Databases are often treated as black boxes. When application developers need a document store, they default to MongoDB; when they need an embedded engine, they grab SQLite or RocksDB. But under high-concurrency write workloads requiring strict physical durability (fsync on every acknowledged write), traditional database designs encounter severe architectural bottlenecks—most notably Write Amplification (WAF) and Random I/O Thrashing.

LogTreeDB is a crash-safe, multi-threaded document database written from absolute scratch in modern C++17 without a single third-party dependency. It combines an append-only Value Log (vLog) with a disk-backed, sibling-free Copy-on-Write (COW) B+Tree index that stores only 24-byte document location references. It exposes a full MongoDB-compatible query interface (find, $set, $inc, secondary indexes, aggregation pipelines) over a custom length-prefixed TCP wire protocol on port 7070, complemented by a zero-dependency Node.js driver, an interactive shell, and an embedded administrative web console.

text LogTreeDB at a Glance: ┌────────────────────────────────────────────────────────────────────────────────────────┐ │ • 16-Thread WAF: 1,384 bytes/update vs. SQLite's 33,300 bytes (24.1x reduction) │ │ • 16-Thread Speed: 3,363 updates/sec vs. SQLite's 313 updates/sec (10.7x faster) │ │ • Crash Resilience: 354+ randomized kill -9 crash runs, 0 acknowledged writes lost │ │ • Zero Dependencies: Engine, server, driver, shell, and UI use ONLY stdlib & POSIX │ └────────────────────────────────────────────────────────────────────────────────────────┘ The Architectural Blueprint

LogTreeDB synthesizes four foundational systems techniques:

WiscKey Key-Value Separation: Document payloads are appended sequentially to immutable segment files (vlog_%08u.log) and never updated in place. The B+Tree index remains lightweight because it stores only slim 24-byte physical pointers (VPtr). Bounded Delta Update Logging (kMaxDeltaChain = 4): Mutating a single field via $set or $inc appends an ~96-byte delta record rather than rewriting multi-kilobyte documents, slashing write amplification by 3.65 × 3.65× to 4.78 × 4.78× while guaranteeing point read latencies under 130 𝜇 s 130μs. Dual-Slot Ping-Pong Superblock & COW Index: Metadata updates alternate between two 4 KiB disk slots with monotonic epoch counters and hardware-accelerated CRC32C validation. Sibling-free copy-on-write index pages ensure committed state is never mutated in place, completely eliminating write corruption and the need for a separate Write-Ahead Log (WAL). Adaptive Leader/Follower Group Commit: Overcoming the physical disk barrier of SSD write flushes (~3.7 ms per flush) by coalescing parallel transactions into a single sequential disk write and a single flush barrier.

Across 354+ randomized kill -9 process crashes during active group commits, live checkpoints, and background garbage collection, LogTreeDB demonstrated zero data loss and zero dead-version resurrection across hundreds of thousands of verified operations.

Before building LogTreeDB, I had spent two years building full-stack applications on the MERN stack (MongoDB, Express, React, Node.js). To an application developer, the database is an abstraction: you call db.users.updateOne({ _id }, { $set: { "profile.bio": "New bio" } }), get an { acknowledged: true } promise back, and move on.

Eventually, curiosity took over: What actually happens on the physical SSD when an app calls updateOne? How does the engine ensure that if power cuts out 50 microseconds later, that modification is not lost? Why does updating a 10-byte string in a 4-kilobyte document consume so much disk I/O?

Can I build an ACID crash-safe document database from scratch in modern C++17, with zero external dependencies, that writes fewer bytes per update than a classic page-based engine while keeping every acknowledged write safe through process crashes?

To answer that question, every claim in this paper is measured empirically, and every trade-off—including where LogTreeDB loses to mature engines like SQLite—is documented transparently.

Early in the project, I planned to build a latch-free index using pointer swizzling (LeanStore) and thread-per-core execution (ScyllaDB). A 10-second CPU profiler trace under a 16-thread mixed workload (~52,800 stack samples) abruptly killed that plan:

93.2% of worker time was spent blocked waiting for the group commit's F_FULLFSYNC system call. 5.8% of worker time was spent waiting inside the sequencer condition variable. The read path took only 180 samples (<0.4%), and JSON parsing took under 70 samples (<0.15%).

Building a latch-free in-memory index would have produced zero measurable throughput gains because the physical disk write barrier was the entire bottleneck. As a result, the index retained a clean, maintainable reader-writer lock per tree, and engineering effort was directed where it mattered: batching physical flushes and moving checkpoint I/O out of write locks.

To understand why LogTreeDB is designed the way it is, one must understand how its predecessor failed.

My first engine, MongoLite, followed textbook database implementation to the letter:

Slotted Pages: Fixed 4096-byte pages with an array of line pointers at the front growing forward and variable-length document cells growing backward. BufferPoolManager & LRUReplacer: A frame pool with an 𝑂 ( 1 ) O(1) LRU replacer using a textbook steal/no-force policy. WALManager: Monotonic Log Sequence Numbers (LSNs), redo log records, and checkpoint truncation. Primary Index: Documents addressed by RecordId(page_id, slot_id) with an in-memory index.

Initial synthetic benchmarks appeared astonishing: 183,383 inserts/second and 1.52 million reads/second on 4 threads. But those numbers were an illusion: the WAL had never called fsync. It was measuring RAM bandwidth, not a durable database.

When MongoLite was subjected to true durability testing—triggering F_FULLFSYNC after every transaction and injecting kill -9 process crashes during writes—the engine collapsed:

LogTreeDB solves the slotted-page bottleneck by combining WiscKey key-value separation, an append-only Value Log, a sibling-free COW B+Tree, and a dual-slot ping-pong superblock.

The value log is organized as a sequence of immutable disk segments: /vlog/vlog_%08u.log.

On macOS with internal Apple Silicon SSDs, issuing an fcntl(fd, F_FULLFSYNC) forces the SSD controller cache to flush to non-volatile NAND flash. This hardware operation takes ~3.7 milliseconds, imposing a hard physical ceiling of ~270 sync operations per second for a single thread.

LogTreeDB bypasses this barrier through an Adaptive Leader/Follower Group Commit Pipeline:

5.3 Sibling-Free Copy-on-Write (COW) B+Tree

LogTreeDB's primary index (index.db) stores 4 KiB slotted pages, but deviates completely from textbook B+Trees:

Lightweight Pointers: Leaf cells store only the document key and a 24-byte VPtr (sequence, segment ID, offset, length). For 100,000 documents, the entire B+Tree is 10.5 to 13.7 MiB, fitting entirely within the OS page cache (compared to >130 MiB if documents were stored in leaves). Why Sibling Pointers Were Eliminated: In a classic B+Tree, leaf nodes maintain bidirectional horizontal pointers (prev / next) for range scans. In a Copy-on-Write tree, modifying a page allocates a new page ID. If leaves had sibling pointers, updating a leaf would require modifying its neighbors' pointers, which would trigger COW cloning of their ancestor paths—cascading across the entire tree! Eliminating sibling pointers isolates path cloning strictly to the single modified leaf's ancestors ( 𝑂 ( height ) O(height)). In-Memory Parent-Stack Traversal: Range scans (store_->scan()) traverse ordered keys without sibling pointers by maintaining a lightweight traversal stack of parent node IDs and slot offsets in memory, achieving 𝑂 ( log ⁡ 𝑁 + 𝐾 ) O(logN+K) scan complexity. The 𝐸 + 2 E+2 Delayed Page Reuse Rule: When a page is superseded during checkpoint epoch 𝐸 E, it cannot be recycled immediately. If the system crashes, recovery must roll back to checkpoint 𝐸 − 1 E−1. A freed page is returned to the allocator's free list only after checkpoint epoch 𝐸 + 2 E+2 commits, ensuring both superblock slots reference structurally intact trees. 5.4 Dual-Slot Ping-Pong Superblock & Crash Recovery

LogTreeDB eliminates the need for a separate Write-Ahead Log by treating the append-only vLog as the source of truth, synchronized via an 8 KiB dual-slot ping-pong file (superblock.db).

text Superblock Ping-Pong Layout (8192 Bytes): +-------------------------------------------+-------------------------------------------+ | Slot 0 (Bytes 0 to 4095) | Slot 1 (Bytes 4096 to 8191) | | Epoch: E | Root Page: #42 | Epoch: E+1 (Active Committed State) | | Replay VPtr: Seg 3, Off 1024 | Replay VPtr: Seg 4, Off 512 | | Hardware CRC32C Checksum | Hardware CRC32C Checksum | +-------------------------------------------+-------------------------------------------+ The Two-Phase Checkpoint Flush Protocol: Hold Locks Briefly: The engine acquires index locks only long enough to capture: the last applied sequence number, the current vLog file position, the root page ID, and in-memory clones of dirty index pages. Locks are released immediately. Phase 1 (Index Flush): The dirty index pages are written to index.db and flushed via F_FULLFSYNC. Phase 2 (Superblock Commit): The alternate superblock slot is updated with epoch 𝐸 + 1 E+1, the new root page, the vLog replay pointer, and its CRC32C, followed by a second F_FULLFSYNC.

If a crash or power cut occurs during Phase 1, the superblock still points to epoch 𝐸 E. On reboot, the engine opens epoch 𝐸 E and replays any newer vLog records. If a crash occurs during Phase 2, the CRC32C of the uncommitted slot fails, and the engine safely reverts to epoch 𝐸 E.

In automated crash testing, recovering a database with 6,000 operations across 30 segments with 200 uncheckpointed writes completed in 11.3 milliseconds.

5.5 Bounded Delta Update Logging (kMaxDeltaChain = 4)

When an application calls updateOne with update operators like {$inc: {"profile.views": 1}}, rewriting a multi-kilobyte document creates massive write amplification. LogTreeDB solves this with Delta Chains:

text Delta Chain Traversal (Bounded to kMaxDeltaChain = 4): +---------------+ +---------------+ +---------------+ +------------------+ | Index Head | ----> | Delta 2 | ----> | Delta 1 | ----> | Base Document | | (Points to D2)| | ($set status) | | ($inc views) | | (Full JSON Copy) | +---------------+ +---------------+ +---------------+ +------------------+ Hop 1 Hop 2 Hop 3 Strict Invariants of Delta Chains: The 4-Hop Cap: A chain is strictly capped at 4 deltas. If an update would push chain_depth > 4, or if accumulated delta operations exceed 50% of the document's total size, the engine consolidates: it resolves the document in memory and writes an unchained Full Document Entry flagged kFlagConsolidated. 1024 Key Stripe Locks: Every write operation computes

std::hash ( key ) ( m o d 1024 ) stripe=std::hash(key)(mod1024). The writer holds stripe_mutex[stripe] from reading the current version until the new vLog entry is applied to the index, preventing concurrent updates from creating branched or orphaned delta chains. Global Sequencer (applyInOrder): While group commit batches writes across different keys out of order to saturate disk throughput, index updates must be applied in strict log sequence. Each writer thread waits on a condition variable until next_apply_seq == my_assigned_seq, applies its modification to the B+Tree, advances next_apply_seq, and signals waiting threads. text Measured Byte Savings: 10,000 $inc Updates on Single Key: ┌───────────────┬────────────────────────────┬────────────────────────────┬─────────────┐ │ Document Size │ Full Rewrite (put) / Op │ Delta (cap 4) / Op │ WAF Savings │ ├───────────────┼────────────────────────────┼────────────────────────────┼─────────────┤ │ 1 KB Doc │ 1,074 bytes │ 293 bytes │ 3.67x lower │ │ 2 KB Doc │ 2,100 bytes │ 498 bytes │ 4.22x lower │ │ 8 KB Doc │ 8,257 bytes │ 1,729 bytes │ 4.78x lower │ └───────────────┴────────────────────────────┴────────────────────────────┴─────────────┘

A delta record consumes ~96 bytes. The average byte volume is dominated by the fifth update that writes a full consolidated copy: out of 10,000 updates, 8,000 wrote tiny deltas and 2,000 wrote consolidated baselines.

Because the vLog is append-only, superseded deltas and deleted documents accumulate dead space.

text Segment Lifecycle State Machine: [Active Segment] │ (Fills to 4 MiB) ▼ [Sealed Segment] │ (Overwrites / Deletes drop Live Ratio < 0.5) ▼ [Victim Selection] │ (Sort sealed segments by lowest live_bytes / total_bytes) ▼ [Striped Batch Relocation] │ (Acquire stripe locks in ascending order -> appendRelocated() -> update index) ▼ [Epoch Quarantine (E + 2)] │ (Wait until two successive checkpoint epochs commit & active readers unpin) ▼ [Superblock Condemned List] │ (Segment ID written to superblock condemned list -> F_FULLFSYNC) ▼ [Physical Unlink & Directory Fsync] In-Memory Space Accounting: A concurrent tracker maintains total_bytes and live_bytes per segment. A full document overwrite or tombstone deducts the previous chain's bytes from the respective segment's live counter. Deadlock-Free Relocation: When evacuating a candidate segment, live documents are read and their stripe locks acquired in strict ascending numerical order, eliminating lock inversion deadlocks with incoming client writes. Idempotent Relocation: Relocated entries retain their original seq sequence number. If a crash interrupts GC, recovery replay remains strictly idempotent. Crash-Safe Segment Unlinking: A segment file is only physically unlinked after its segment ID is recorded in the superblock's condemned array and fsynced across two checkpoint epochs.

6.2 Secondary Indexes & Order-Preserving Encodings

Secondary index values are encoded into sortable binary byte strings (encodeIndexValue):

Type Precedence: Null (0) < Numbers (1) < Strings (2) < Objects (3) < Arrays (4) < Booleans (5) < ObjectId (6). IEEE 754 Floating-Point Normalization: Converts 64-bit doubles to order-preserving unsigned integers with sign-bit inversion, allowing floating-point values to sort correctly under standard lexicographical byte comparison. Array Invalidation (hasArrays): If an application inserts an array into an indexed scalar field, the catalog permanently flags hasArrays = true, safely falling back to collection scans to preserve correct multi-key query semantics. 6.3 Aggregation Pipeline Engine

LogTreeDB implements a pull-based memory-bounded generator supporting:

Stages: $match, $project, $addFields, $group, $sort, $skip, $limit, $count, $unwind. Accumulators: $sum, $avg, $min, $max, $count, $push. Optimizer Pushdown: Leading $match stages are detected by Pipeline::leadingMatch() and pushed down to the storage engine as index range scans. 7.3 Optimization Impact: Before vs. After

During engine profiling, four targeted architectural changes transformed system throughput:

Segment Rollover Re-Check: Fixed a race condition where 16 threads encountering segment rollover simultaneously created 240 nearly-empty segment files. Open Descriptor Pool: Cached 64 file descriptors for active vLog segments. Adaptive 500 µs Commit Window: Doubled group commit batch size without penalizing isolated writers. To verify stability under resource constraints, the engine was stressed on a fanless MacBook Air under strict safety limits:

9.1 Million Documents: A 64-thread load inserted 9,095,650 documents before halting cleanly at a 40 GB write budget. Reopening took 53.9 seconds, with zero key holes across any thread. 30-Minute Chaos Soak: 8 writers and 4 readers with continuous GC, checkpoints, and a kill -9 every 5 minutes: 179,480 acknowledged writes, 61.8 million reads, zero corruptions. Reopening in read-only mode functioned without corruption; once space was freed, writes resumed normally. 16 MB Large Documents: Documents up to the 16,777,168-byte limit succeeded through put, get, delta update, scan, checkpoint, GC, and crash recovery. Many of the deepest insights came from code that failed during real-world testing:

fsync() Does Not Guarantee Durability on macOS: On macOS, standard fsync() only flushes dirty blocks to the drive's volatile cache. True durability requires fcntl(fd, F_FULLFSYNC). SQLite on macOS falls back to F_BARRIERFSYNC unless custom VFS shims are provided. POSIX write() Is Never Guaranteed to Be Complete: Under heavy disk load, write() frequently writes fewer bytes than requested or returns EINTR. Storage engines must wrap every I/O call in a strict writeAll() loop. The Segment Rollover Concurrency Race: When 16 threads filled an active segment simultaneously, each thread attempted to roll over the segment, creating ~240 nearly-empty segments instead of 36. The fix: threads must re-check segment size under the lock after waiting on an in-flight flush. Catastrophic Regex Backtracking: Standard std::regex in libstdc++ uses exponential backtracking. A malicious regex like (a+)+$ against a repetitive payload hangs worker threads indefinitely. On Linux, nested repeating groups are now rejected at parse time. The Missing Databases Mystery: During testing, two test databases (myapp and test) vanished from a local server instance. Investigation revealed that demo/run.sh was silently attaching to an existing background instance on port 7070. Test harnesses must strictly enforce isolated ports and ephemeral directories. Laptop Sleep Stalls Benchmarks: Two benchmark runs recorded unexplained 17-minute write pauses: the MacBook had gone to sleep while running unattended! All subsequent benchmark suites ran under caffeinate. Client Driver Reconnection Semantics: In the Node.js driver, if a connection drops, operations already sent across the wire are never silently retried, because the write may have already committed on disk. Silent retries would violate non-idempotent operation semantics ($inc).

LogTreeDB is a single-node engine designed for embedded and local workloads. Engineering honesty requires highlighting where it is not yet complete:

Current Limitations: Single-Node Architecture: No clustering, consensus protocols (Raft/Paxos), sharding, or multi-node replication. No Multi-Document Transactions: ACID durability is guaranteed per document; there are no cross-document multi-statement transactions. Range Scan Penalty: Because keys are separated from values (WiscKey), full collection range scans incur random pread() calls across vLog segments. Local Interface Binding: The server listens on 127.0.0.1 only. It lacks TLS encryption and role-based authentication, making it unsuitable for direct exposure to untrusted public networks. Startup Reopen Scaling: Rebuilding GC tracking counters on startup requires reading one entry per key, taking 15.5 seconds at 2.5 million keys and 53.9 seconds at 9.1 million keys. Next Engineering Iterations: Persistent GC Metadata: Persisting segment live-byte counters in the superblock to drop startup reopen times from 53 seconds to under 50 milliseconds. Clustered GC Relocation: Grouping logically adjacent documents into identical physical segments during GC to accelerate range scan performance. Server Audit Trail: Logging all collection drops and bulk deletes with timestamps and client metadata. Rust Native Desktop GUI: Developing a high-performance native desktop application to complement the web admin console.
