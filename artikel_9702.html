The MP3 Header Said 7:15. The Audio Ran 3:03, and I Bill by the Minute

Tanggal: 2026-11-27

I run a visa agency in Bali, and in the evenings I build data tools on Apify. One of them is MP3 to Text: you give it MP3 links and it returns a transcript with timed passages. Under the hood it is Whisper behind Groq's API. Most of my code is the plumbing around the model: downloading, converting, splitting long files and billing.

Billing is per started minute of audio, so the most important number in my code isn't the transcript. It's the duration. This post is about one MP3 that reports a duration 2.4 times longer than its real length, and why a transcriber should never trust what a file says about itself.

I didn't want to guess, so I made the file myself. I took the one-minute test MP3 I use for daily checks (a passage from Pride and Prejudice read aloud), put three copies in a row, and added three seconds of silence at the front. I encoded it as variable bitrate with LAME, then copied the frames into a new file without the Xing header:

The audio in both files is byte-for-byte the same, and both are 1.74 MB. The only difference is a small frame at the start of the first file that says "this stream has N frames".

The 7:15 has a simple cause. An MP3 has no length field. A VBR file can carry a Xing (or VBRI) frame that gives the frame count. Without one, the demuxer reads the bitrate of the first frame and divides the file size by it. My file starts with three seconds of silence, and LAME encodes silence at the lowest rate it can, which here is 32 kbps. So:

The guess from file size is wrong in the other direction because the speech in this file averages about 76 kbps, not 128.

You might say I built this case on purpose. I did, but the parts are common. Podcasts usually open with a jingle or a pause. Most phone recorders and podcast tools encode VBR. And there are plenty of ways to lose the header, or end up with a stale one: joining MP3s with cat, cutting a file with a tool that copies frames, or a recorder that streams to disk and never goes back to finish the header. A joined file can be even worse, because it keeps the first part's Xing frame and reports the length of that part only.

With 435 seconds as input, that's 8 minutes. With 183 seconds, it's 4. The same problem hits any other step that uses duration: your cost estimate before sending a batch, the "Max cost per run" check, timeout planning and queue ordering.

So the Actor never asks the original file how long it is. The first thing it does is decode the file to 16 kHz mono Opus, the format the recognizer gets anyway. Then it measures that file:

Ogg Opus stores the real sample position in every page, so its duration is counted, not estimated. The billable minutes come from that number.

I uploaded vbr_noxing.mp3 to a test account and sent it through the Actor with default settings:

The run log says 4 min billed, 183.0s of audio recognised. The charged events were audio-minute × 4 and file-processed × 1, $0.038 in total, and the run took 6.3 seconds. If I had trusted the header, it would have been 8 minutes and $0.074 for the same 643 words.

The last segment ends at 182.5 s, and the decoded file is 183.05 s long. That half second at the end is the trailing pause after "It is a truth universally acknowledged." So the duration and the transcript agree with each other. That's the cross-check I use when I don't trust a number.

The same conversion turned the 1.74 MB MP3 into a 525 KB Ogg file, about 0.17 MB per minute of speech. That matters because Groq refuses uploads over 25 MB. A 128 kbps MP3 reaches that at about 26 minutes, so a normal podcast episode is too big to send as it is. After conversion, more than 100 minutes of speech fit in one upload. Longer files get cut into 100-minute parts, and each part's segment times are shifted by its offset. Then a three-hour episode comes back as one transcript with continuous timings.

There's one ffmpeg detail I learned the hard way. When you split with -f segment -c copy, you need -reset_timestamps 1. Without it, every part after the first keeps its original timestamps and reports a wrong duration, and the recognizer rejected those parts outright.

Compare the first segment of the plain one-minute file with the first segment of this one:

The text is the same, and the second segment is exactly three seconds longer. The model doesn't output an empty segment for the silence. It adds the silence to the first passage, so the passage "starts" at 0 even though the reader starts at 3 s. If you use segment times to cut clips or place a first subtitle, the first timestamp can be early by the length of the intro. Later segments are fine. In this file the next one starts at 7.96, which is right.

If you estimate cost before sending a batch, decode the file instead of reading its header. It's slower, but it's the real number:

On my file this returns 183.04. After the run, compare it with durationSeconds on each row. If they differ by more than a second, look at the file before you look at the bill.

What I'd take away from this: an MP3's reported duration comes from metadata the file may not have. If you price, bill or time out by duration, measure it from the decoded audio.
