# From Database Tables to Long-Term Memory with Hindsight

Tanggal: 2026-11-07

Most postmortems are write-only documents. An on-call engineer spends four hours debugging a cascading failure at 3:00 AM, writes up a detailed timeline, lists three things that failed before finding the fix that worked, and files the ticket away into an archive where nobody ever reads it again.

Two months later, under similar traffic conditions, another engineer gets paged for the exact same symptom. And what do they do? They repeat the exact same failed fix that made things worse the first time around.

When we set out to build RecallOps—an operational intelligence layer for Kartly, an e-commerce platform processing checkout transactions across six distributed microservices—we wanted to break this loop. We did not want another dashboard that dumps thousands of raw log lines onto an engineer’s screen. We wanted an AI incident response system that actually remembers what happened in previous outages: what alert fired, what recent deployment preceded it, what the on-call engineer tried that failed, and what finally restored service.

To make this work, we had to solve a fundamental architectural challenge: relational databases are built for operational state, not episodic reasoning, while raw vector retrieval over unstructured logs produces noisy, ungrounded hallucinations.

Here is how we designed a dual-tier architecture combining PostgreSQL with Hindsight on GitHub, how we structured operational memory, and what we learned about bridging relational data and long-term agent recall.

At its core, RecallOps sits between our observability stack and our incident response workflow. The infrastructure runs six core microservices: checkout-api, payments-svc, inventory-svc, search-svc, notification-svc, and delivery-eta-svc.

Our operational data pipeline separates concerns across two purpose-built storage engines:

PostgreSQL (The Operational Source of Truth): Postgres maintains relational integrity: staff engineering ownership, 400 deployments over six months, threshold alerts, 110 incidents (INC-0001 to INC-0110), 3,500 raw log lines, and fix attempts strictly categorized as worked, failed, or partial.

Hindsight (The Episodic Agent Memory Engine): Postgres cannot perform semantic reasoning over past human actions. If an alert fires for db_connection_pool_active_ratio > 0.90, querying Postgres for exact text matches fails when pod names or stack frames differ. We pipe distilled postmortems into Hindsight, a dedicated long-term memory engine for AI agents that organizes memories into managed banks with temporal reasoning and entity graphs.

When engineers first experiment with LLMs for incident management, the standard approach is naive Retrieval-Augmented Generation (RAG): chunk your application logs, compute embeddings, store them in a vector database, and retrieve nearest chunks when an alert fires.

Building and operating this system taught us several concrete lessons about AI-assisted infrastructure operations:

Dumping raw logs into an agent's memory bank degrades recall quality. Logs contain ephemeral noise (pod IPs, request IDs, memory addresses) that dilute semantic meaning. Extracting the structured causal arc—symptom, prior change, failed action, root cause, working fix—into clean markdown units improved retrieval accuracy across all eight failure families.

In production outages, engineers often jump to intuitive remedies: restart the service, clear the cache, or scale horizontal replicas. In distributed systems, these intuitive actions frequently trigger secondary failures (cache stampedes, connection storms, or replication lag). Recording failed fixes with explicit FAILED outcomes prevents agents from recommending disastrous shortcuts.

We did not replace our relational database with an AI memory engine, nor did we try to force semantic reasoning into PostgreSQL. Postgres is unmatched at maintaining foreign key referential integrity, enforcing CHECK constraints, tracking ACID transactions, and storing high-volume log streams. Hindsight is unmatched at synthesizing historical human experience, managing temporal context, and retrieving relevant prior lessons. Using both in tandem gave us the best of both worlds.

In any real-world data pipeline, ingestion jobs will be triggered multiple times. Without deterministic document identifiers (document_id=f"kartly-{inc['code'].lower()}"), re-running ingestion creates duplicate memory entities that fragment agent attention. Designing idempotency into the schema and the memory API from day one saved dozens of debugging hours.

Engineering incident response is not a lack-of-data problem; it is a memory problem. The logs, alerts, and postmortems already exist in every modern engineering organization. By pairing a robust relational backbone with long-term episodic memory via Hindsight, we can ensure that when systems fail, our tools remember the lessons we already paid to learn.
