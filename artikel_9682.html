Using Entire to pick up where your teammate’s coding agent left off

Tanggal: 2026-11-14

Imagine you're at a hackathon. While you nap, your teammates leave a coding agent running overnight. You wake up to a tonne of new code, and nobody has any idea what's going on. Before blindly continuing to build, I'd personally want to recover the original request sent to the coding agent and understand the changes.

Entire does exactly that: it's built on top of Git, and it connects a commit (a saved code change, if you're unfamiliar with Git) to the agent session behind it. A coding agent (e.g. Claude Code, Antigravity, etc.,) reads files, edits code and runs commands in response to your prompts. Entire essentially captures that work in checkpoints, so you can retrieve the conversation alongside the code.

This post is a walk-through of a simple Python project showing what you can do with Entire. Jump to setup if you want to install Entire first.

The demo project I made is straight-forward - it literally just calculates delays between attempts to send a web request. Suppose a teammate's commit starts allowing retries for POST requests, which can create things like orders. Repeating one could create a duplicate. What did they ask the agent to do?

Original prompt to my coding agent, retrieved by Entire:

Add retries for POST requests, but only when the caller supplies an idempotency key. Preserve the existing behaviour otherwise, add tests, and explain the design choice.

This is a small retry-schedule CLI, not an HTTP client. Expose the option through the Python function and CLI. Assume the caller uses an endpoint that supports idempotency keys and sends the same key on each attempt; document that contract.

(Beginner tip: An idempotency key allows us to identify an operation so a supporting server can recognise a repeated request and avoid doing it twice. CLI means command-line interface, and this project's CLI calculates delays).

The first version accepted a key containing only spaces. I continued the same coding agent session with this follow-up prompt:

A caller supplied an idempotency key containing only spaces, and POST retries were enabled. Treat empty or whitespace-only keys as missing. Do not strip or otherwise alter a real key: keys are opaque values. Add regression tests for the function and CLI, keep Python 3.9 support, and explain why you chose validation rather than normalisation.

The resulting commit was fc42200. Opening its checkpoint reveals the response to that request:

Empty and whitespace-only keys now leave POST retries disabled. Keys containing any non-whitespace character remain valid, including keys with surrounding whitespace.

Validation uses isspace() without stripping or rewriting the key. Idempotency keys are opaque; normalization could change the identity of an operation.

The follow-up prompt explicitly told the agent to preserve spaces in valid keys. Entire keeps that instruction alongside the resulting code change, so a teammate can see why the behaviour exists before changing it (if needed). It's worth highlighting that each commit gets its own Entire checkpoint even if its all one agent session - pretty handy. Opening the later checkpoint with --full shows both requests from that conversation.

Brain can also receive the ID through an environment variable, ENTIRE_BRAIN_SESSION_ID: a value supplied by the program launching Brain. When that value is supplied, you can omit --session. In the new copy, I gave a fresh coding agent this review prompt:

You are picking up a teammate's retry-policy CLI. Explain why POST retries now require an idempotency key and why whitespace around a nonblank key is preserved. Start from the latest two Git commits and use Entire's saved checkpoints to recover the actual requests and recorded explanations before reading the code.

The agent recovered both requests, read the code and passed all ten tests. It also noticed the tests wouldn't catch the code silently stripping spaces from keys. Reading the implementation confirmed it preserved them. The session supplied the requirement; reviewing the code checked whether it was met.

In my original checkout, Entire found the saved conversation and printed the command to reopen it in my coding tool. Replace feature/keyed-post-retries with your own branch name and follow the instructions Entire displays.

For my next change, I'd start with the relevant checkpoint, retrieve any saved decisions, then ask the agent to work against those requirements. That gives both of us the original context before we edit the code.

Mirroring means Entire stores a second copy of your GitHub project's files and Git history on servers it runs, and keeps that copy updated from GitHub. You and your coding agents can download the project from Entire. When you push a mirrored branch through Entire, it forwards the changes to GitHub, where your existing permissions and branch protection rules still apply. GitHub remains the main repository. More on how mirrors work.

I'd consider this when a team wants to review proposed code changes in Entire's website and see automated review findings in its Trails pages. It can also help when agents running in different regions repeatedly download a large project: Entire can keep copies near those agents to reduce the time they spend waiting for the code. Mirroring is optional for the local workflow above, though. The mirroring guide walks through signing in, giving Entire access to your GitHub repository and choosing where to host the copy.
