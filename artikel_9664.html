Reject Oversized Image Uploads — Metadata Admission Bounds Thumbnail Storage and Cache

Tanggal: 2026-11-23

Read image metadata before thumbnail processing, reject oversized uploads at admission, and allow only a bounded set of responsive variants. For marketplace listings, the deciding constraint is storage and cache growth: accepting an original should not authorize an unlimited family of derivatives.

Short answer: enforce separate byte, dimension, and pixel limits before a file reaches the thumbnail worker. A 200 megapixel upload should fail at that boundary. Publish the limits in the upload UI and return a specific rejection reason; a silent failure becomes a support ticket, while a timeout ten seconds later has already spent the seller's patience.

This record treats thumbnail generation as resource admission. The application needs responsive thumbnails on upload, but the original file and its eventual delivery variants have different budgets. A small compressed file can still describe a large image. Checking the request size alone doesn't establish that decoding it is acceptable. Metadata supplies dimensions before expensive pixel decoding.

Choose the budget before choosing the service. As an illustrative policy, allow at most 12,000,000 input bytes, 24,000,000 pixels, and 12,000 pixels along either axis. These are application policy examples, not vendor limits or measured capacity. A 20,000 by 10,000 image represents 200,000,000 pixels and fails immediately. A 10,000 by 3,000 image also fails, despite passing both individual dimension checks.

For this policy, three illustrative responsive widths are 320, 640, and 960 pixels, with one configured output format and no upscaling. The upper bound is three derivatives per admitted original, before accounting for deletion and replacements. Allowing arbitrary widths or arbitrary format combinations removes that bound. Store and cache only variants the listing interface actually requests, or generate the approved set eagerly when immediate availability matters. That choice trades unused stored derivatives against work on the first read; neither strategy excuses admitting an oversized original. The limit belongs in a versioned application policy so a later interface redesign doesn't quietly expand the retained object set for every existing listing.

The admission decision must refer to the same immutable bytes the worker will decode. Checking one upload and then fetching a mutable object under the same name defeats the check. Bind the decision to an immutable object version or content digest, and have the worker verify that binding. A digest identifies content; it doesn't prove the content is safe.

The failure boundaries are deliberately separate. The ingress layer caps bytes while receiving the upload. The metadata reader rejects unacceptable dimensions without requesting a pixel decode. The thumbnail worker performs full decoding under its own memory and execution limits, validates the decoded image, and publishes derivatives only after successful completion. A readable header is not a certificate that the rest of the file is valid.

This resembles an OTP delivery pipeline in one useful respect: admission, processing, and successful delivery are distinct states. An accepted upload should not make a listing claim that thumbnails are ready. Return a reason such as an exceeded pixel limit to the seller, retain a support correlation identifier, and avoid copying private image contents into error logs. Make retry behavior explicit too. The same original and the same transformation policy should resolve to the same derivative identity, so a repeated job doesn't create another stored object. Sending another notification on every retry would be just as unhelpful as generating another thumbnail; notify on the state transition that matters to the seller.

For private or unpublished listings, derivative access must follow the listing's authorization rules. Keep originals private and use signed access where remote processing requires it. A long-lived cache entry can outlast a visibility change, so decide expiration and invalidation behavior before treating a successful thumbnail write as publication. Don't assume a content hash enforces access control.

Managed delivery, source-backed transformation, a local conversion tool, and a shared backend API are different integration choices. A team already operating image workers may prefer to keep inspection beside decoding. A team consolidating backend integrations may value the shared service boundary. Neither preference establishes how many responsive objects a listing should retain. The Python example below makes that application-owned boundary visible around a remote metadata request.

There is no supported universal cache-cost winner here. Measure admitted original sizes, actual variant requests, retained derivative bytes, and cache behavior for the marketplace's own traffic. Don't infer those quantities from the number of API calls.

This runnable Python example requires requests. Save it as admission.py. Its three command-line arguments are a JSON request file conforming to the metadata operation's public discovery schema, followed by JSON Pointers locating width and height in the response. Obtain those pointers from the response schema rather than guessing field names. Set INFRAI_API_ORIGIN to the documented HTTPS API origin without a path, and INFRAI_API_KEY to an environment-held credential. The request file must identify the immutable upload already checked against the illustrative 12 MB byte budget at ingress. Its output is an application admission record, not a claim that the image has been decoded or published.

The field mapping avoids assuming a response envelope. A missing field or malformed response fails admission. The printed state, width, and height form this application's output contract; they are not vendor response fields. Keep raw error bodies in a restricted diagnostic channel because they may contain request details. Return a sanitized reason and correlation identifier to the seller. An ingress cap is still necessary because a metadata call cannot undo an oversized network transfer.

Use a deployment-owned API origin. Redirects are refused so credentials do not follow a response to another host. If a request identifies a private object through a presigned URL, attach the API credential only to the metadata request, never to a fetch of that object. Rate-limit retries reuse the same idempotency key.

Unsupported or malformed images can fail before dimensions are available. Report that outcome as a failed inspection, never as an invitation to try a full decode in the request handler. Animated input needs a separate frame-count and total decoded-work policy before support is enabled; this gate alone does not budget animation processing.

After admission, persist or reference the exact inspected bytes under private access and submit the immutable identity to the worker. Include the approved transformation policy in the derivative key. If a crop rule or output encoder configuration changes, distinguish the new result from an older cached object. The code stops at admission because storage and queue request shapes belong to the chosen integration, not to this local inspection contract.

Decoding an unrestricted original before testing dimensions spends the worker resource that admission is supposed to protect. It also moves the seller's rejection later in the workflow. For this marketplace, reject that ordering and reject caller-selected arbitrary derivative widths: both let input expand downstream work before a useful budget is established.

Full decoding still has a valid use case. A controlled ingestion pipeline with bounded, trusted inputs needs it to validate image content and create thumbnails, and an admitted marketplace upload needs it inside the isolated processing stage. The decision is about where expensive work begins. Put metadata admission first, keep the approved responsive set finite, and track readiness separately from acceptance.
