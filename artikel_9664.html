Nebula Go SDK: A Type-Safe Go Client for Market Intelligence APIs

Tanggal: 2026-11-15

Every market has two stories: the one printed on the price chart, and the one people tell each other. Prices record what already happened. Sentiment, mindshare, and prediction markets hint at what the crowd expects next. The Nebula API from Hidden Systems serves both stories as structured data, and nebula-go is the Go client that makes it pleasant to consume.

If you have ever wired a market-data endpoint into a Go service, you know the drill. You write an HTTP client, invent a struct for half the response, keep the other half as map[string]any, add retries, forget to respect Retry-After, and then repeat the whole ritual for the next endpoint. nebula-go is an MIT-licensed attempt to delete that ritual. It covers all 41 operations of the Nebula Public API with typed requests and responses, a real error taxonomy, retries that listen to the server, server-sent-event streaming for the Nebula Agent, and an optional adapter for x402 pay-per-request billing.

In this overview you will see what the SDK covers, how its API feels in practice, which design decisions make it pleasant to live with, and where the sharp edges are.

Quick start: from zero to sentiment in one file

Design decisions that matter in production

Generated from a contract, not from memory

Nebula is a market-intelligence API that watches the public conversation around financial assets — equities, commodities, indices, crypto, and AI-related names — and turns it into queryable signals. Instead of scraping social platforms and stitching together your own sentiment pipeline, you ask the API a question and get typed observations back.

The surface is broader than a single "sentiment endpoint":

The same data is also exposed through a Nebula MCP server and a CLI, which makes the API a natural fit for coding agents and terminal workflows. But if you are writing a Go service, the REST API is the integration point — and that is exactly where nebula-go lives.

The project is young. The first version landed in late October 2026, and the changelog already lists five versions, from the initial 0.1.0 to 0.3.2 in mid-November. What it lacks in age it makes up for in discipline: the repository reads like someone sat down and decided to get the boring parts right.

The feature list is longer than the version number suggests:

Typed DTOs generated from OpenAPI. Requests are ordinary structs, responses have concrete field types all the way down to nested time-series points.

context.Context** on every call.** Timeouts and cancellation behave the way Go developers expect, including during retries and streamed responses.

Retries with server hints. Eligible GETs retry on 429, 500, 502, 503, and 504, honoring Retry-After and RateLimit-Reset before falling back to exponential backoff with jitter.

An inspectable error hierarchy. Sentinel errors for errors.Is, rich *APIError values for errors.As, and client-side validation before a request ever hits the network.

SSE streaming for the Agent. ChatStream exposes a channel of chunks and a terminal Err() so you can tell a completed answer from a truncated one.

Response metadata everywhere. Request ID, rate-limit figures, credits charged, credits remaining, and payment receipts are available on every response.

Localization. A global locale and per-request overrides, with constants for Spanish, Italian, Turkish, Russian, Korean, Japanese, and Chinese.

Opt-in x402 payments. A separate adapter for paying per request in USDC on Base, with explicit spend controls and a no-wallet preview mode.

An offline generator. go generate ./... rebuilds the typed surface from the pinned OpenAPI contract; a -check mode detects drift without writing files.

That last point deserves emphasis. Many SDKs are handwritten once and slowly drift from the API they wrap. This one treats the OpenAPI document as the source of truth and keeps the generated surface, the handwritten business rules, and the tests in separate layers. We will come back to that.

A few things are worth noticing in that small program.

The first call resolves a human-readable name to an API identifier. The second call carries both the AssetID and the AssetClass forward in an AssetRef. That pairing matters: a display symbol alone may not identify the asset you mean, especially in crypto, where several tokens can share a ticker. The SDK's type system nudges you to keep the identifier and its class together instead of passing loose strings around.

The sentiment signal is a decay-weighted bullish-minus-bearish measure. Positive values lean bullish, negative values lean bearish, and the magnitude also depends on activity. Read it alongside the timestamps and post counts rather than as a standalone trading signal.

Finally, HTTPMetadata() is available on the response even though the JSON body has its own metadata field. It reports the request ID, rate-limit state, and credit accounting for the call you just made. That is the kind of detail that usually gets bolted on after the first production incident.

The API surface is only half of an SDK. The other half is how it behaves when the network misbehaves, the server pushes back, or the data is missing. This is where nebula-go shows its personality.

Optional request fields are pointers, so the SDK can distinguish "use the server default" from "send this exact value":

Helpers like StringPtr, IntPtr, Int64Ptr, Float64Ptr, BoolPtr, TimePtr, and typed-constant pointers keep the call sites readable. Explicit values still have to satisfy endpoint rules — Limit: IntPtr(0) is rejected for asset listings — but the SDK checks required fields, selector conflicts, enums, and numeric ranges before the HTTP call and returns a ValidationError that names the operation and the field.

The same philosophy applies to responses. Nullable scalars are pointers, so an unavailable price is nil, not a fake zero. That sounds pedantic until you build a chart and a missing data point silently becomes a crash to zero.

Errors are classified with sentinels and enriched with details. Application code can branch with errors.Is, while diagnostics use errors.As:

The sentinel list covers the cases you actually branch on: validation, transport, bad request, unauthorized, out of credits, forbidden, not found, rate limited, server errors, and payment states. APIError keeps the status code, API message, headers, parsed metadata, and up to 8 KiB of the response body, which is usually enough to understand a failed call without reproducing it. A credit-related 402 preserves the plan renewal time and purchased-credit balance when the API supplies them.

There is also a deliberate distinction between failure modes: TransportError wraps network problems, DecodeError reports a successful HTTP response with invalid JSON, and wrapped errors preserve context cancellation. That means a canceled request does not get misclassified as a server failure in your metrics.

Retrying blindly is how you turn a rate limit into an outage. The SDK retries eligible GETs on transient network errors and HTTP 429, 500, 502, 503, or 504, and it picks the delay in a sensible order: Retry-After first, then RateLimit-Reset, then exponential backoff with jitter. Computed backoff is capped, and the overall call deadline still wins.

Just as important is what it does not retry: POST chat requests, x402 payments, other 4xx errors, decoding failures, and failed body reads. Those are exactly the cases where an automatic retry can duplicate work or spend money twice. If you add your own retry loop on top, you are multiplying attempts — the README says so plainly, which is refreshing.

Configuration stays out of the way until you need it:

The defaults are reasonable: 30 seconds per call, three total GET attempts, 250 ms initial backoff with a 5-second cap. WithHTTPClient lets you inject your own proxy, TLS settings, or instrumentation. The client is immutable after construction and safe for concurrent use across goroutines, which is the behavior a shared client in an HTTP server needs.

One security detail worth calling out: the SDK blocks cross-origin redirects so an API key or a signed payment header cannot leak to another host. It is a small thing that many clients forget.

The Nebula Agent is stateless: your application owns the conversation and sends the full message history with each request. For a chat UI, StreamChatCompletion returns a ChatStream that behaves like a Go channel rather than a callback maze:

Two details make this usable in real applications. First, a closed events channel does not mean the answer completed — you must check Err() afterward, because malformed events, API error frames, cancellation, and an unexpected end before [DONE] all surface there. Second, the configured timeout covers the entire stream, so a long answer needs a longer WithTimeout; the default 30 seconds is not enough for a thoughtful essay. Keep the defer stream.Close() even when you expect to drain the stream, since it also releases resources on an early return.

The Agent request itself is OpenAI-compatible, with roles for system, developer, user, and assistant, and an optional thinking mode for deeper answers. Billing is usage-based, with a 10-credit minimum in the pinned contract, so Usage is worth inspecting when it is present.

Two features deserve their own examples because they are where market intelligence stops being a dashboard and starts being a tool.

Forecasts are requested per asset, and a successful HTTP response can still say the asset is not forecastable. The SDK makes that state explicit instead of forcing you to guess from an empty array:

Both mindshare and sentiment forecasts expose Status, Reason, and IsForecastable(). Refresh: BoolPtr(true) asks for recomputation and can cost more credits; the pinned contract describes roughly five seconds for a refresh with a cached fallback after twenty, so the SDK's timeout defaults are worth revisiting if you enable it.

Prediction markets follow a similar "carry the identifier forward" pattern. Search with Predictions.ListMarkets, open the canonical market with Predictions.Market, then use the listing ID and outcome ID from that response to fetch history. The IDs refer to different objects, so each one has to come from its own field. The SDK keeps those types distinct, which prevents the classic bug of passing a market ID where an outcome ID belongs.

Not every project wants an account and a credit balance. Nebula supports x402, an HTTP-native payment protocol, for eligible read operations: you pay per request in USDC on Base mainnet and skip the API key entirely. Thirty-seven of the 41 operations are eligible GETs; account details, the two forecast-generation endpoints, and Agent chat are not.

The x402 package is opt-in and deliberately paranoid. You can inspect an offer without a wallet or private key:

Preview mode does not establish trust — it shows what the server is asking for. To actually pay, you supply your own signer and an explicit SpendPolicy with a per-payment cap and a nonempty recipient allowlist. The adapter checks the x402 version, the exact scheme, the Base network, the USDC asset, the recipient, the amount, and the resource URL before anything is signed. Production resources must use HTTPS, and signed GETs disable both SDK retries and the standard transport's implicit replay.

The README is refreshingly blunt about the risk: x402 can irreversibly spend real USDC, the cap applies per payment rather than in total, and a lost response after signing returns ErrPaymentUncertain, which you must reconcile before authorizing another payment. This is the right posture for a payment feature. It is also a good reason to start with API-key mode and add x402 only when pay-per-request genuinely fits your product.

The most interesting engineering choice in this repository is not an API method. It is the pipeline behind the API methods.

The SDK is generated from a vendored OpenAPI 3.0.3 document pinned at info.version 1.0.2. go generate ./... rebuilds request structs, typed responses, enums, service methods, query validation rules, and x402 eligibility from that contract. The generator is offline: it does not download the spec or call Nebula, so regeneration works in CI and on a plane. A -check mode reports missing, edited, or obsolete generated files without writing anything, which makes drift a build failure instead of a slow surprise.

Naming choices that cannot be inferred from OpenAPI live in compat.json, and business rules that span several parameters live in handwritten request_validation.go. Generated code stays generated; human decisions stay human. That separation is why the project can claim a complete API surface without pretending every rule fits in a schema.

The test strategy follows the same principle. The suite runs without a Nebula key or a wallet, using local HTTP servers, an in-memory transport, and fixtures. A coverage guard ties all 41 operations to service calls, documentation, fixtures, and x402 eligibility. Contract tests exercise all 173 query parameters and all 750 response properties, including nullable fields, empty collections, large int64 values above 2^53, fractional timestamps, and unknown upstream fields retained in Raw. CI runs the race detector, go vet, staticcheck, govulncheck, CodeQL, formatting checks, and a generated-output check on both Go 1.24 and the current stable release.

That is a lot of ceremony for a young SDK, and it is the main reason to take the project seriously. Contract tests do not prove live API compatibility — the README says that too — but they do make silent regressions much less likely.

Hand-rolling an API client is not wrong. Sometimes it is the right call: you need one endpoint, you want zero dependencies, or your organization has a standard HTTP stack. Here is an honest comparison.

The trade-off is familiar: less code to own, more behavior to learn. For a service that talks to Nebula regularly, the SDK is the shorter path. For a one-off script, curl and encoding/json may still win.

The SDK fits a few concrete shapes of work:

Research dashboards. Show sentiment, mindshare, and prediction-market odds next to price history without building an ingestion pipeline.

Monitoring and alerting jobs. Watch for momentum shifts or sentiment regime changes and notify a team when thresholds are crossed.

AI assistants and tool-using agents. Give an LLM typed access to market intelligence, with streamed answers when a human is reading.

Internal analyst tools. Let analysts search assets, compare communities, and pull forecasts without writing HTTP code.

Quant-adjacent research. Treat sentiment and attention as features alongside prices, with the usual caveat that correlation is not causation.

It is less suitable if you need a synchronous trading connection, ultra-low-latency market data, or an API surface that Nebula does not expose. This is an intelligence API, not an exchange feed.

Is nebula-go free to use? The SDK is MIT-licensed, so you can use, modify, and ship it freely. The Nebula API itself is a commercial service: account mode consumes credits, and x402 mode pays per request in USDC.

Which Go version do I need? Go 1.24 or newer. That minimum comes from the module's dependency graph, including the optional x402 adapter.

Does it support streaming responses? Yes. Agent.StreamChatCompletion returns a ChatStream backed by server-sent events. Read chunks from Events(), then check Err() to distinguish a completed answer from a truncated one.

Can I use it without an API key? For the 37 x402-eligible GET operations, yes — with a wallet and a configured spend policy. Account details, forecast generation, and Agent chat require an API key.

How is it tested without hitting the live API? The suite uses httptest servers, an in-memory transport, and saved fixtures. Contract tests compare the SDK against the pinned OpenAPI document, so go test ./... works offline and without a wallet.

Is it production-ready? It is a v0.x project, so pin a version and review the changelog before upgrading. The test discipline, CI coverage, and release cadence are stronger than the version number suggests.

nebula-go is a focused piece of engineering: one API, 41 operations, and a lot of attention to the parts of client code that usually get skipped. Typed responses make the data legible. The error taxonomy makes failures actionable. The retry policy respects the server. The generator keeps the SDK honest against its contract. And the x402 adapter treats payments with the caution they deserve.

If you are building anything in Go that touches market sentiment, prediction markets, or AI-generated market analysis, it is worth a look — and worth a star if you want the project to keep moving.
