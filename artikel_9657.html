AI in Development: What Actually Ships Faster (and What Doesn't)

Tanggal: 2026-11-16

Every week someone announces that AI "replaced" a chunk of software engineering. Every week someone else points out that the resulting code doesn't compile, the tests don't exist, and the PR is 4,000 lines with no reviewer who understands it.

Both are describing the same thing from opposite ends. AI changes how we build software, but not in the way the headlines imply. The skill that matters is no longer writing code faster — it's specifying, verifying, and reviewing code faster. The teams that get a real return on AI tooling are the ones that got good at those three things first.

A team of five used to spend its week in the editor: writing the endpoint, wiring the config, writing the migration, updating the mock. That work was slow, predictable, and largely mechanical. It was also the part of the job nobody wanted.

So if your process breaks when you paste in generated code, the problem isn't the model. It's that your process assumes code is expensive to produce and cheap to verify. AI inverts that ratio, and most teams' tooling and habits are still built for the old world.

Config loaders, Pydantic models, API clients, type-safe wrappers around a third-party SDK, test fixtures. Not glamorous, but this is where hours disappear. Give the model the actual dependency versions and the actual field names and it will produce something you'd have written anyway, just faster.

The underrated use case. A 300-line module from a service you don't own? Ask for a walkthrough. Ask "what happens if this input is None?" The first answer is often wrong, but the second and third — where you push back with specifics — are frequently better than reading the file line by line.

Generated tests are a starting point, not a deliverable. But "here's the module, write the edge cases" produces a checklist you would probably have missed anyway: empty inputs, unicode, timezone boundaries, the 5000-element array.

This is where careful teams get the most value. Paste the diff, ask "what breaks if this input is empty?" or "what's the race condition here?" An LLM reviewing a diff is not a substitute for a human reviewer, but it's a remarkably good first pass — and it costs seconds.

"Design a schema for a multi-tenant RBAC system" → a first draft of the tables, the enums, the permission matrix. The value isn't the code, it's the visualisation of a decision you'd otherwise make entirely in your head.

Hallucinated APIs. Models write plausible library calls that don't exist, with confident-looking import paths. The classic: passing a parameter that was never in that version. Mitigation: pin exact versions in the prompt, and — this is the important part — make the compiler and type checker non-optional.

Silent over-engineering. Ask for a function, get a class hierarchy with a factory, a strategy pattern, and an abstract base class. Generated code tends toward ceremony because ceremony is statistically common in training data. Say explicitly: "Keep it to a plain function, no classes."

Security-shaped code that isn't secure. Generated auth code tends to look right. Missing: constant-time comparisons, actual scope enforcement, proper token expiry, authorization checks on the object you're fetching rather than the route. Audit it like it was written by a stranger, because it was.

Confident wrong answers about your own system. The model doesn't know your schema, your edge cases, or the migration you ran last Tuesday. It will still answer as if it does.

Here's the setup that works for most teams, and it's less exotic than it sounds:

1. Write the spec before the code. Write a short markdown doc: the endpoint, the inputs, the outputs, the error cases, the invariants. Half of the value is that it forces you to think. The other half is that a spec is the cheapest possible input for the model — it's what makes the output consistent instead of random.

2. Generate a small slice. Not the whole feature. One function, one endpoint, one migration. Smaller slices mean smaller diffs, which means review stays possible.

3. Verify mechanically, not by reading. This is the non-negotiable part. If your loop is "generate → skim → commit", you're shipping a liability. If it's "generate → run the tests → run the linter → run the type checker → read the diff", the machine catches what your eyes will miss. Most of the value of AI coding tools is not in the generation; it's in how much cheaper it makes iteration after generation. That's an argument for fast, deterministic feedback loops — which, not coincidentally, is also good engineering practice independent of AI.

4. Review like it's someone else's code. Because it is. Ask the model to explain its own diff, then ask it to attack its own diff. Take the second pass seriously — that's where it finds its own bugs.

5. Keep the boring parts boring. Configuration, migrations, and error handling are where AI-generated code drifts most. If you have templates, linters, and strict schemas in those places, the generated code lands in a cage instead of in production.

Most AI coding tools are, at their core, orchestrators: they pull your repo context, call a model, apply the diff, and run your commands. The model quality matters, but it's the context and the feedback loop that determine whether you get useful output or confident noise.

The same applies to API-driven features. Every platform you integrate has its own authentication, its own rate limits, and its own opinions about what a valid payload looks like. Treat each one as a separate contract with its own error handling, and never let one failure silently swallow the others — the user needs to know exactly what succeeded and what didn't.

The uncomfortable truth is that AI raises the floor and lowers the ceiling. The weakest developer on your team now ships code that looks like the strongest developer's. The strongest developer on your team has to level up too, because their value is no longer in typing speed.

If your team's differentiation is "we can write more code per week", you're in trouble. If it's "we ship the right thing reliably", AI is a gift.

None of those are new skills. They were always the hard part of software engineering. AI just made them impossible to hide behind.

One concrete experiment: pick a ticket on your board that's small and boring — a new endpoint, a config flag, a migration. Write a proper spec doc first. Have the model implement only that ticket. Run your full CI loop. Review the diff as if it came from a stranger, and write down every spot where you had to intervene.

That write-up is worth more than any benchmark. It tells you exactly where your team's real friction is — and whether the next hour of your time belongs to the model, or to your build pipeline, or to your review process.

That last possibility is the one most teams never check. It is usually the answer.
