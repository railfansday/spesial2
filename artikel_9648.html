How I built 2,300 static pages of calculators in 8 languages without a framework

Tanggal: 2026-11-15

I work in operations at a factory in Bangladesh. In my spare time I built LifeEasyTools, a site with 515 free calculators and everyday tools in 8 languages. It has no framework and no database for the tools: one Node.js script turns plain JavaScript objects into 2,359 static pages.

Here is how it works, what went wrong, and what I would do again.

Most of my users are on low-cost Android phones and slow mobile data. A calculator should show up instantly and never wait for a server to do maths that the phone can do itself.

So every page is plain HTML. Calculations run in the browser, and the PDF and image tools process files locally, so nothing is uploaded. A typical tool page is about 50 KB of HTML (13 KB gzipped), plus one shared stylesheet and one shared script.

seg, num and row are tiny helpers that return form HTML. DN is a small shared runtime (about 25 KB gzipped) that reads the form, formats numbers for the visitor's locale, and draws the result card, tables and charts.

The build script loops over every tool and writes the page with its title, description, breadcrumbs, JSON-LD (WebApplication, FAQPage, BreadcrumbList), hreflang links and a sitemap entry. A full build of all 2,359 pages takes about 35 seconds.

Each language has a translation file per tool: title, description, intro, content and a ui map of the English strings used in the form and the script.

The build translates the form HTML text nodes and every single-quoted string in the tool's script through that map. When a sentence is built from pieces ('in ' + days + ' days'), a small jsFix list replaces that expression with a properly ordered one, because word order differs between languages.

The catch: it is easy to leave English behind. So a test runs every translated tool in headless Chromium, clicks Calculate, and lists any English phrase left in the visible result. That test found things I would never have spotted by hand, such as holiday names in English on Bangla pages, or a chart legend that still said "Part / Rest".

For a calculator site, a wrong answer is the worst bug. I keep a "golden" test file: 36 real cases, each with a reference value computed independently from the published formula, not copied from the tool's code.

Playwright fills each form, runs it, and checks the result contains the expected number. When a test failed the first time, it was usually my test input that was wrong (a mortgage down payment is a percentage, not an amount), which is a good reason to write the reference values independently.

Chrome's layout-shift measurement showed 0.077 on the PDF tools on phones. The file drop zone gets extra buttons (link, camera, paste, Drive, Dropbox) from JavaScript after the first paint, and on narrow screens they wrapped onto two lines and pushed everything down.

The fix was two parts: show the extra sources as one row of fixed-height tiles on phones, and reserve their height in CSS until the script marks the zone as ready:

Layout shift went to 0 on every page I measured.

Plain objects plus a build script were enough for 500 tools. The two things that paid off most were the golden tests and the "find leftover English" test. Both caught real problems before users did.

If you want to try a tool or tell me what is missing, the site is lifeeasytools.com. I am happy to answer questions about the build in the comments.
