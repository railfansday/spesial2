Your LLM Wiki Compiles Away Your Permissions. Design for It Before the Team Uses It.

Tanggal: 2026-11-16

A short thread on X last week put the LLM wiki vs. RAG debate better than most long posts do: a wiki compiles knowledge when a source arrives; RAG retrieves at question time, so per-user permissions and citations stay intact. That line matters most to people taking the trending personal second-brain setups to their team.

And right now a lot of people are. Karpathy's LLM Wiki idea file, Garry Tan's open-sourced gbrain, and the Claude Code + Obsidian vault repos are being cloned by the thousand. They work well for one person, because one person has one permission level: everything. The trouble starts when the same pattern is pointed at a shared drive with HR folders, customer escalations, and board notes in it.

This post is about that one gap. It's not a case against LLM wikis. I think they are the right shape for a lot of team knowledge. But the compile step quietly erases your access model unless you design for it.

In the LLM wiki pattern, raw sources stay immutable and an agent writes a linked set of markdown pages that summarize, cross-reference, and update as new sources land. You get answers that are already synthesized, instead of re-deriving them from chunks on every query.

The agent does what it was asked and writes a good page: "Acme: renewal at risk; dispute over SLA credits; legal involved since October." That page now holds facts from the most restricted source, and it sits in a folder whose permissions were set for the least restricted one.

Citations don't fix this. Even if the page links back to a source the reader can't open, the reader has already read the sentence. A derived fact inherits the sensitivity of its most sensitive input, and a compiled page is made of derived facts.

RAG with permission-aware retrieval doesn't have this failure mode, because it filters source passages per user before generation. What it gives up is the compounding synthesis that makes a wiki useful.

You don't have to pick one. You do have to decide, page by page, where the access check happens.

The simplest rule that holds up: the agent may only write a page into a scope that every source used for that page is visible to. In set terms, the page's allowed readers are the intersection of each source's allowed readers.

Split it: a sales-scoped summary that leaves out the escalation, and a legal-scoped page that adds it. Agents are good at writing two versions. They are bad at guessing which version you meant.

Run this check in the agent's write path, not as a nightly lint. By the time a nightly job runs, the page has already been indexed, quoted, and pasted into Slack.

None of these rules depend on a specific product. But two properties make them much easier.

Permissions should live on the documents themselves, in the same system the agent reads from and writes to. If the agent compiles from a file dump and writes to a folder of markdown, you are rebuilding an access model by hand on top of a filesystem that never had one. A workspace-based knowledge base software setup, where docs, roles, and sharing settings sit together, gives Rule 1 something real to intersect. AFFiNE's write-up on AI workspace permissions walks through the role and data-access checks worth running, and it lines up closely with the leak test above.

The compile step should run where your data already lives. Compiling means the model reads everything, including the restricted sources, in order to decide what not to write. If that model is a third-party API, your most sensitive documents are leaving the building on every compile, no matter how careful the output is. Running the compile on self-hosted AI infrastructure keeps that step inside your own boundary.

This is the main reason I'd pick an AI knowledge base software stack you can self-host for team use, over a personal vault plus a cloud agent. Something in the open source Notion alternative category gives you docs, permissions, and a deployment you control in one place, so the agent's reads and writes stay inside the same access model your people already use.

The LLM wiki pattern took off because it treats knowledge as something you build once and keep current, not something you rediscover on every query. That is still the right instinct for teams. Just remember that when you compile the knowledge, you compile the access decisions too, so make the agent write them down.
