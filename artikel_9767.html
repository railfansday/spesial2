Our Looping Factory Cut DEV Page Load Time by 75% and Counting

Tanggal: 2026-11-09

A month ago, an average web request on DEV took about 70 milliseconds inside Rails, with P99 response time coming in at over 1s much of the time. Today, across roughly 300,000 sampled requests a day in Better Stack, that number sits at 16 milliseconds.

Database time per request dropped from 39ms to under 12ms. View rendering fell from 12ms to 2.6ms. Redis time went from 7ms to 1.3ms. Over the last 30 days, we merged 475 pull requests into Forem. This is the type of work that is critical to scale and user experience, but always difficult to prioritize in the face of other progress that needs to happen.

These gains have been massive for user experience. No more intermittent slow downs, or trouble keeping up with high traffic peak times. This has been a solve for a decade's worth of pain.

We have been able to prioritize these performance improvements by designing a feedback loop and stepping away from the day-to-day on this project.

We accomplished this by spinning up a software factory and stepping out of the loop.

There is a trap in the first phase of agentic development that almost everyone hits. You stop typing syntax, which feels like leverage, only to discover you have promoted yourself to human middleware. You become the clipboard between dashboards and a terminal: nudging prompts, babysitting CI flakes, and rubber-stamping diffs all afternoon. You aren’t coding by hand, but you aren’t doing deep engineering either. You are an API endpoint with a pulse.

Getting out of that trap took weeks of building and reconfiguring autonomous loops on top of OpenHands and the Agent Client Protocol (ACP). The goal wasn’t just to make DEV faster. It was to separate systematic maintenance from the creative, bespoke projects that deserve human taste.

In Design for Churn, I argued that codebases are starting to look less like buildings and more like gardens. When writing code was expensive, durability was how you got your money’s worth. When rewriting is cheap, your investment goes into what doesn’t turn over: the soil, the beds, and the irrigation. Put strong contracts, schemas, and tests at the edges, and the code inside can churn continuously without disturbing the roots.

In early October, I did that gardening interactively with agents, shipping 31 PRs that brought average latency from 70ms down to 50ms. The wins were real, but every query audit still required me to start a session, paste context, and shepherd the branch home.

On October 19, we stood up a persistent self-hosted OpenHands hub and turned those habits into closed-loop systems. Since then, 444 pull requests have merged into Forem: 351 from autonomous loops (172 performance PRs, 93 test-suite speedups, 32 Rust native rewrites, 29 dependency upgrades, 20 production error fixes, and 5 issue-to-PRs) alongside 93 bespoke PRs that I drove directly.

You don’t get a working software factory from a cron job that says "make the app faster." We went through half a dozen configurations, each born from watching an earlier version fail.

From one model to a cross-family router. We started pinned to Claude Opus 5.5 (claude-acp), syncing OAuth tokens from macOS Keychain. After hitting quota ceilings and token-refresh collisions, we built a three-provider router across Claude Opus 5.5, OpenAI’s codex-acp (GPT-6.1 Sol), and Google’s Gemini 4 Argon via the Antigravity CLI (agy), first tunneled over a reverse WebSocket to my Mac and then installed natively in Linux at Medium reasoning. Each loop rotates round-robin with an 8-hour cooldown cap, switching model families whenever a PR repair fails.

From shared checkouts to isolated worktrees. Running eight loops in parallel in one container exposed every sharp edge in Git and Linux. Parallel fetches triggered git gc collisions, a crashed boot left a stale .gitconfig.lock, and zombie processes piled up until we added tini as PID 1. We moved every run into a detached-HEAD git worktree with self-healing lock cleanup, and put deterministic Python gates in front of every cron so full queues exit in two seconds with zero tokens spent.

The real payoff isn’t the 475 PR count, or even the 16ms response time. It’s what happened to those other 93 pull requests.

Because I wasn’t spending mornings hunting sequential scans or routing stack traces between tabs, I had headspace for deeper work. While the loops compacted queries and specs, I spent interactive sessions redesigning how our home feed evolves (adding targeting buckets, age diversity weights, and sticky repeat-visit configs), modernizing JavaScript delivery across four phases to shrink application.js by 71% and base.js by 55%, building an L1 local Redis cache, and crafting observability extensions to watch the whole system work.

Tending to this system and working on the high-leverage margins finally feels like a step past the awkward in-between of AI-supported software development as a meat router. The appropriate interplay between brownfield and greenfield projects and the tools for a more productive and creative day at work are here.
