Oracle AI Database 26ai(23.26.4): Streaming Windowing Table Functions

Tanggal: 2026-11-17

Analyzing time-based data is a common requirement in modern database applications. Oracle AI Database 26ai(RU 23.26.4) introduces four SQL streaming windowing table functions that simplify this type of analysis by dividing table rows into time-based windows.

Each function accepts a datetime column and interval parameters to determine how rows are assigned to windows. The returned result includes two additional columns, WINDOW_START and WINDOW_END, which identify the time boundaries of each window.

In this article, we will explore how these four functions work and demonstrate their practical applications using customer activity data.

Before exploring the individual functions, it is useful to understand how Oracle assigns records to time windows.

A windowing function takes a table, a datetime column, and interval values to divide records into time periods.

The result contains the original columns from the input table, together with two additional columns:

WINDOW_START: The timestamp representing the beginning of the window. WINDOW_END: The timestamp representing the end of the window. These two columns allow us to identify the time range associated with each record.

An important detail is how Oracle handles the beginning and ending points of a window. The starting time is included, but the ending time is not.

For example, with one-hour windows, a record timestamped at 11:00 belongs to the 11:00–12:00 window rather than the 10:00–11:00 window.

This boundary rule ensures that records occurring exactly between two consecutive windows are assigned consistently.

Although the four functions share the same general purpose, their behavior can produce significantly different results.

The previous functions use predefined time intervals to organize records. However, some business requirements are based on user behavior rather than fixed clock periods.

Consider a website where a customer performs several actions. We may want to consider consecutive actions part of the same session as long as the customer does not remain inactive for too long.

Instead of relying on a fixed window size, it examines the timestamps of consecutive records. A configured inactivity gap determines whether a record continues an existing session or starts a new one.

For example, if the maximum gap is 10 minutes, activities separated by 3 or 5 minutes can remain in the same session. However, when the interval between consecutive activities exceeds 10 minutes, a new session begins.

Another useful feature is PARTITION BY. It allows us to separate records according to one or more column values before identifying sessions.
