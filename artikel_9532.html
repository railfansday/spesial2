Callbacks are powerful and a little dangerous: they run "invisibly". Use them for small, predictable housekeeping like this, and be careful once they start sending emails or touching other records. We'll meet that in Part 8.

validate (singular) takes the name of your own method. If the method adds something to errors, the record is invalid. Here, a topic can't have two sessions running at once. errors.add(:base, ...) attaches the message to the whole record instead of one field.

A scope gives a name to a query you'll use again:

The patch :complete, on: :member line adds a custom action on one specific session: PATCH /study_sessions/:id/complete, with the helper complete_study_session_path(session). Use member for "an action on one record" and collection for "an action on the whole list" (you'll see that one in Part 7).

Why resources :topics and not nested inside plans? It keeps URLs and helpers short: edit_topic_path(topic). The one place we need the parent is when creating, and we pass it as a parameter: new_topic_path(study_plan_id: plan.id). (Nested routes like /study_plans/1/topics are a valid alternative, so use whichever you find clearer.)

See how the scope pays off: topic.study_sessions.active.empty? reads like English. We only show the "Start" link when nothing is running, and the model validation guarantees it even if someone forges the request.

Look at the chain: of_user(...).active.includes(...). Three small scopes combine into a precise question.

What does includes do? In the view we print study_session.topic.study_plan.name for each session. Without includes, Rails runs one query for the sessions, then one more query per session for its topic, and another for its plan. Ten sessions means 21 queries. That's the N+1 problem. With includes(topic: :study_plan), Rails loads all the topics in one query and all the plans in another: 3 queries total, however many sessions you have.

Use Date.current rather than Date.today. current respects Rails' configured time zone. We'll make that per-user in Part 10.

Run bin/dev and try it: create a plan, add topics, start a session, end it, and watch it move from "Active" to "Completed Today".

The second and third controller tests are the point of this post's security rule, and they will catch you if anyone ever "simplifies" Current.user.topics.find to Topic.find.

Our "only one active session per topic" rule is checked in Ruby. If two requests arrive at the exact same moment, both can pass the check and both save. A validation can't prevent that, only the database can. In Part 14 we'll add a unique index for it. Until then, remember: validations are for friendly messages, constraints are for guarantees.

Right now, every click reloads the whole page. In Part 5 we add Hotwire: Turbo Frames and Turbo Streams, so adding a topic or finishing a session updates just the part of the page that changed.
