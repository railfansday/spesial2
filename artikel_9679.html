Claude Code forgets everything when a session ends. Close the terminal and the decisions, the dead ends and the "never do that again" lessons go with it. The next session starts from zero, and you pay for it in re-explaining.

I run my agency and side projects from one Claude Code workspace, and most of this year has gone into fixing that one problem. The fix isn't a plugin or an MCP server. It's three layers of plain files, plus four small Python hooks that move context in and out at the right moments.

This post is the code. Everything below runs on my machine today: an Obsidian vault of just over 1,500 notes, 170 memory files, 186 skills, and about 30 hook commands across 10 Claude Code events. This post covers the four hooks that handle memory.

Three layers, each answering a different question:

What I know: strategy, SOPs, people, decisions, diary

How to work with me: corrections, gotchas, preferences

Session state: last handoff, learned failures, skill hints

One rule sits under all of it: inject pointers, not content. Nothing loads the whole vault. The hooks add a few hundred tokens at most, and everything else is fetched with grep when the task needs it.

Obsidian is markdown files in a folder. Put that folder inside the workspace Claude Code runs in and the integration is done. Claude reads, greps and edits notes with the same tools it uses on code. No API, no auth, no rate limit.

What makes it work is a CLAUDE.md at the vault root that acts as a router. Mine is mostly two tables, one for where to look and one for where to save. Trimmed:

Two Claude Code behaviours keep this cheap.

Nested CLAUDE.md files load lazily. The root file loads at startup. A CLAUDE.md inside a subfolder only loads when Claude reads a file in that subfolder. The vault's router costs nothing during a coding session and appears the moment Claude opens a note. Every project folder in the workspace works the same way.

The "Where to SAVE" table is the half most setups skip. Without it, Claude reads the vault and never feeds it. With it, the end of a task routinely includes writing a decision, a CRM line or a lesson back to the right folder. The vault grows from use. Hooks are commands Claude Code runs on lifecycle events. Each one receives the event as JSON on stdin. For SessionStart and UserPromptSubmit, anything a hook prints to stdout on exit code 0 is added to Claude's context. That is the entire mechanism for injecting memory.

When a session stops, one script writes a snapshot: modified files, commits from the last two hours, the tail of a scratchpad file and the current branch. At the next session start, the same script prints it back if it's under 48 hours old.

The flag --no-optional-locks came from a painful bug. A plain git status takes .git/index.lock while it refreshes the index. My hook ran it with a 5-second timeout. When the timeout killed git mid-write, the lock file stayed behind and blocked every commit in the workspace, once for 31 hours before I found it. A read-only status check should never take a lock, and with that flag it doesn't.

With 186 skills I can't remember which one exists for what. Letting Claude auto-fire them on fuzzy matches was worse, because a wrong skill costs more than no skill. So a UserPromptSubmit hook suggests up to three and leaves the decision to Claude.

It runs before every prompt, so it has to be fast and dependency-free. No embeddings, no model download, no API call. It's a TF-IDF retriever over each skill's name and description, standard library only:

The IDF weighting does the useful work. A distinctive word like "carousel" appears in one or two skill descriptions and scores high. Generic words like "create" or "content" appear in dozens and score close to zero, and the stopword list removes the rest ("please", "thanks", "continue").

A hook that hangs or crashes stalls every prompt, so each one carries a hard timeout and swallows its own errors:

daemon = True is there because of a real bug. Without it, the timer thread kept the interpreter alive until it fired, so every run took at least 3 seconds even after the hook's work was done. Every prompt paid that delay.

On Windows, every Python hook flashed a console window on screen. Each command in my settings.json actually runs through a small Node wrapper:

It spawns the real command with windowsHide: true and passes stdin, stdout and the exit code straight through, so the hook contract is unchanged. It also resolves bare python to a real interpreter. Claude Code can spawn hooks with a reduced PATH where the only python on it is the Microsoft Store redirector, which prints an install prompt and exits with code 9009.

Skip the TF-IDF hook until you have enough skills to forget which ones you have.
