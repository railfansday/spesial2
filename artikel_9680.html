This article explains how I built a Git repository of Chile's entire legal code: more than 300,000 laws, decrees and resolutions in a corpus that reaches back to 1810, with one commit per legislative publication, so the text of any law can be read as it stood on any date. It covers scraping the Biblioteca del Congreso Nacional (BCN) and LeyChile, building the history with git fast-import, the limits of Git and GitHub that the repository hit, and the web UI, API and MCP server built on top of it. The repository is pisanvs/ley-chile, and you can browse it at leyes.pisanvs.cl.

I think most programmers would agree that working—in a team—without a version control system like Git, is as horrifying as ripping your nails out with bare hands. Git has become a ubiquitous tool in the software industry, not because it’s amazing, but because it’s undoubtedly necessary.

As coders and hackers, we tend to believe in the delusion that we can fix others’ problems by working our fingers against the keyboard. This is partly (mostly) the reason why one of my obsessions is making other fields of work more efficient.

One of these fields of work is law. You see, the lawyers I know religiously use either Google Docs’ or MS Word’s implementations of version control systems. This doesn’t look like a bad idea or use-case at first glance, but upon further examination we can see the shortcomings of this approach.

🚧 (“blame” doesn’t exist, you must rely on version history)

❌ “versions” are just point-in-time objects

✅ Can stage specific hunks, write commit messages, explain changes.

Now, we programmers use these features regularly, but other fields of work don’t. They don’t have the tools and they have to find increasingly complex workarounds.

A good place to start the Git crusade, in my opinion, is the law.

There are some projects around the world that have tried doing this to varying levels of success.

nickvido’s us-code repository on GitHub has one substantial shortcoming: it only has 16 commits.

How many bills have been passed to modify laws in the US Code? Thousands. At least a few hundred per two-year congressional term. But this doesn’t check out. Why? Because this repo is built from the point-in-time snapshots from the Library of Congress, instead of having its history built per bill.

In my humble opinion, although this repo is accurate, it does not provide a value-add over what the Library of Congress snapshots already provide.

Legalize is probably the most complete solution that has scaled this up to multiple countries. But sadly, their Chilean repo is a bit behind: it only has 3k laws and reforms in it, compared to the more than 300k norms in the complete Chilean corpus.

I really appreciate the work Legalize has done. If I had been aware of their existence before I started this project, I probably would’ve made a fork instead of starting from scratch.

Apart from being mostly unaware of other solutions, the reason I built this project this way was because I had some very particular requirements and constraints. No good engineering challenge has few constraints, after all!

Some of these requirements are considered (rightfully so) a bit outrageous by some friends of mine. I would agree for the most part!

The main purpose of these requirements is to have an easily clone-able, replicable and iterable source for the data and the scraper/generator alike. This enables some benefits of distribution and accessibility, which the traditional sources don’t have.

A fourth bonus requirement was to have the pipeline run alongside the repo. The default option for this was of course GitHub Actions. Having a self-contained GitHub repository for the whole “ecosystem” makes it easy for anyone to clone, modify, and distribute as needed.

Now, having this pipeline run completely within GitHub actions generates its own set of weird constraints. Contrary to popular belief, it has actually brought on some benefits, especially related to the fact that public facing IPs on each job tend to be distinct, and thus lets you circumvent some rate limiters by spreading your work across IPs.

Lucky for the Chilean folk, our National Library of Congress keeps in-depth, updated, accurate and densely linked data on the legal history of the country. They’ve got laws spanning from the country’s first provisional government in 1810 to the present day. The founding act of the First Government Junta is dated 18 September 1810, the day Chile now celebrates as its national day. The Acta de la Instalación de la Primera Junta de Gobierno is one example from the beginning of the corpus.

Another early entry shows how broad the words “legal code” are in the Library. They file “Medidas contra la sífilis” as a decree, but it’s really a letter from the government to a marquis, dated 13 January 1813. Providence, they say, put the cure to syphilis in the hot springs on the marquis’ estate, and the government would like the sick to be able to reach them. So it asks him what road work is needed between Rancagua and the baths, and how it could be paid for. It is an early example of a government text with practical force, even though it might look like it’s very informal.

The Chilean Library of Congress, BCN from now on, exposes multiple APIs, to the point where it’s not possible to have a single source that trumps the rest.

The first two APIs are used and each serves a specific purpose in this project. The only API that is not being used is the API-key-restricted one.

datos.bcn.cl, the SPARQL endpoint, is the fastest way to get the list of everything that exists on the server. With one query we can get every norm's leychileCode, type and publication date. Unfortunately, the server times out on deep OFFSETs, so the script pages with a keyset cursor asking for 500 sequential codes at a time.

This query is from our first stage of the process, which is building the catalog.

nuevo.leychile.cl, the norm JSON, gives me all data corresponding to one norm, and the text of any version of it. The same endpoint serves both the metadata and the versioned text. The difference is one parameter:

The response is an HTML-like tree with law fragments plus a list of the dated versions the norm has had. Inside the HTML are callouts with links to the norms that modified it, and that's where I get the edges of the graph (more on that in the next section).

The third API, bcn.cl/leychile/api/v1, I never used. It needs an API key, and the quota is 500 requests per day per key. At 358,000 norms, one pass would take about two years of quota, before counting any versions. This is a separate issue, but when scraping doesn’t affect in a negative way the infrastructure of a service, and the second best way to get the data is actively harmful for performance or results, it’s probably a symptom of a system that isn’t really open, independent of how much the orgs publicize the “open data” aspect of it.

Ingesting all of this data is an interesting task. It is weirdly shaped, not always complete, or accurate, or standardized.

The scraper is, in essence, four idempotent scripts that run in order.

A note on counts, since they appear throughout: in the main branch’s builder, the catalog contained about 358,000 norms. Roughly 19,000 lacked a usable publication date or had only sentinel dates, leaving about 339,000 that this builder could place in history. Those are pipeline figures, not a count of what the deployed site can show; its Railway deployment uses a different path. The search index in a later section was loaded when it stood at 333,026 norms.

Now, trying to scrape data means that it’s probably going to fight back the whole way. Some of these examples are the following.

Because every stage can be resumed, the work gets spread across GitHub Action runs. The pipeline runs every 3 hours in three phases. A first job refreshes the catalog and graph when they're more than a day old. Then the version fetch runs on 8 parallel runners to avoid IP rate-limiting, since each runner gets a different IP. The last job merges the eight shard branches back into pipeline-cache, rebuilds historial, and pushes it. A concurrency group makes sure only one run can write historial at a time.

An average library, with 10,000 books, should store around 20 GB of just text. There’s a reason why we have a Library of Congress.

The ley-chile repo stores almost 20 GB of pure normative text.

At this scale, some things start to break.

To some extent, the ley-chile repo has broken two of these limits: the size of its tree objects and the width of its directories.

This is the uncompressed size of the repo. Note that the on-disk value is much smaller:

What this means is that if you were to count every version of every file ever committed, you would have around 17 GiB of data in total (blobs). You can see that the trees take up the most space. Why is this?

Git never edits objects in place. When you change one file, Git writes a new blob for it. Then it writes a new tree for every directory on the path from that file up to the root, because each parent's listing now holds a new hash.

For a normal repo that costs little. Here, directories like cache/versions/ or leyes/ list thousands of entries each. Every commit that touches even one law rewrites those huge listings in full. Thousands of commits * multi-MB listings = 375 GiB uncompressed.

Which leads us to the second limit broken: directory width. The three biggest folders in the repo are all inside the pipeline-cache branch (an orphan branch that holds the downloaded data; the rebuilt history of the laws lives in a second orphan branch, historial, described below). They all have more than 357k entries.

In the history branch, with the “rendered” repository, you will see the biggest folder by entries is etc/res with all of the resolutions from different state organisms.

A few more things that broke or had me bang my head against a wall along the way:

The useful unit of history is a publication, not a law or an edit within a single file. A new Chilean norm can amend several older ones at once, so I made each publication a single commit containing the new norm and every change it caused. Open that commit and you can see the legal change as one event.

I wrote about the mechanics of generating those commits with git fast-import in my previous article. Here, that commit model matters because it powers the diffs and historical lookups below.

I also tried the alternatives for the dates, as I described in my previous article. Mercurial accepts 1901 through 2038, which is a bit wider than Git for the past but closes the future sooner. Fossil stores dates as Julian day numbers in SQLite, so it took every date in the corpus, including early nineteenth-century dates.

For our users to actually make good use of the data, we needed to expose it in a more familiar interface. Given Git’s and GitHub’s constraints, the fact that the existing GitHub UI wasn’t made for exploring data of this shape, and the hard limits around datetimes, metadata, linking, etc, I decided to go forward building a Web UI for the project. This was probably the best decision I made.

The web UI makes it easy for lawyers and regular users to take advantage of Git’s utility, while not necessarily having to interact with it. Common interactions are implemented, with Git-specific functionality available for power users who are willing to clone the repo.

A counterpart of the Web UI is an API and an MCP server. These can get quick access to the corpus with the main functionality being search. Search is a big challenge, especially when storing not only the latest versions but also the full history.

The directory structure of ley-chile only serves quick lookup when the user previously knows the text’s type and id. For any semantic search, another layer is needed. Just grep-ing over the whole directory is an immensely slow operation. The challenge then becomes building a search engine over the corpus.

The site started with two search tiers. Meilisearch stored the top ~8% of laws that people actually read, 28,730 of 333,026, and Postgres held the rest. This was supposed to be an 80/20 solution to the search problem, but it actually became very expensive!

Postgres full-text index on articles (articulo_tsv_idx)

That is about sixteen times the disk for under a tenth of the content. There was a second cost in memory. Meilisearch memory-maps its index, so its resident memory climbs to cover the working set and never comes back down, and Railway bills observed memory, so the mapped index was a continuous charge. A premium price to pay even with no usage being registered.

What settled it was an outage. On 2026-09-07 Meilisearch didn't come back from a Railway region migration. Search returned nothing for every query, including a bare law number that Postgres could have answered, because the code awaited the Meilisearch tier unconditionally and swallowed the error. A dependency serving under a tenth of the corpus took down 100% of search, and did it with a 200 response and an empty list.

The old query took 21 seconds because Postgres chose the wrong index and removed 524,720 rows by filter while never touching the full-text index at all. Making one query shape the default would have made common words 38 times slower, this justifies the logical overhead.

This was the point when I removed the Meilisearch client and its volume. It's not perfect. When a common word has thousands of matches, the fast shape picks which 20 laws to show by lowest ID, not by relevance. This probably justifies the decision to build a different engine at some point, but with an LLM in front of the search, as with the MCP server, it works well enough most of the time.

The fact that we had to build all of this separate infrastructure on top goes to show how Git really isn’t the best format to store this type of data. But alas, it is very useful for a specific purpose.

There's also a /llms.txt with instructions written for agents. This is how most users discover this project, and is probably the most useful use case that impacts efficiency.

You should, if you care about the text of the law being traceable. A Git history gives you something a PDF can't: every version has a hash, every change has a cause, and "the law as of date X" is a command instead of a research project. Lawyers don't need better word processors for this. They need blame, diff and log, which they have never had.

You shouldn't expect Git to be the product. My lawyer friends will keep using Word. What made the project usable for them was the web UI on top, so Git ended up as the engine and not the interface. And it's not even a good database: search needed Postgres, and my first search engine (Meilisearch) cost about 16 times the disk for under a tenth of the corpus and took search down with it when it went offline. In the final design Git is the single source of truth, and everything else (Postgres, the search tables) is derived and can be thrown away and rebuilt. Right now, the MCP seems to be the biggest product.

You should check the limits before you start. GitHub caps blobs at 100 MB, rejects pushes with big packs, and runs fsck on everything you send it. Read the repository limits first. I learned most of them from rejected pushes.
