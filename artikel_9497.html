1 GB VPS Indie Dev Stack: Gitea, Uptime Kuma, and Miniflux Behind Caddy 2

Tanggal: 2026-11-24

Posted on Nov 24 • Originally published at vpsfolio.com

Per-container RAM: gitea 196.8 MB · uptime-kuma 181.3 MB · miniflux 34.2 MB · miniflux-db 28.9 MB · caddy 9.9 MB (sandbox verified 2026-11-24)

View the interactive benchmark plate and full VPS sizing comparison or compare all measured stacks on VPSFolio Benchmarks.

This stack packs three self-hosted staples onto a single 1 GB VPS: Gitea for private Git hosting, Uptime Kuma for uptime monitoring, and Miniflux for RSS reading. All three sit behind one Caddy 2 reverse proxy that routes by hostname. Backend HTTP ports stay internal; only Caddy publishes a host port (bound to loopback for sandbox safety). Gitea SSH is exposed on a separate loopback port so you can push over SSH without opening the HTTP backends.

To keep memory in check we use SQLite for Gitea (no separate Postgres for Git) and a dedicated Postgres 16 instance for Miniflux. Uptime Kuma keeps its state in SQLite inside its data volume. The whole 5-container stack idled at 451.1 MB in our sandbox run — well under 550 MB, leaving headroom for spikes and the OS.

Caddy handles host-based routing with a tiny inline Caddyfile. In sandbox mode we disable automatic HTTPS and serve plain HTTP on port 80 inside the container, published to 127.0.0.1:18080 on the host. That lets you verify with curl -H "Host: git.local" http://127.0.0.1:18080/ without touching DNS or certificates. Production cutover is a small diff: remove auto_https off, switch to real domain names, and publish 80/443.

Sizing notes: in our disposable sandbox run, the 5-container stack measured 451.1 MB total idle RAM (gitea 196.8 MB, uptime-kuma 181.3 MB, miniflux 34.2 MB, miniflux-db 28.9 MB, caddy 9.9 MB). That matches the 448.2 MB sum of our individual guides closely and leaves over 500 MB of OS/burst headroom on a 1 GB VPS (still add 1–2 GB of swap for Git pushes or monitor spikes).

For remote backups, add a cron job or systemd timer that runs docker compose exec -T miniflux-db pg_dump -U miniflux miniflux > /backups/miniflux-$(date +%F).sql and similar for Gitea's SQLite file (copy from the volume) and Uptime Kuma's data directory. Store backups off-box (e.g., rclone to S3-compatible storage).

Backups. Gitea with SQLite stores everything in the gitea_data volume. Back it up by stopping Gitea briefly and copying /data/gitea/gitea.db and /data/git/repositories. For Miniflux, use pg_dump as above. Uptime Kuma's SQLite database lives in the uptime-kuma volume; copy /app/data/kuma.db. Automate with a small script and test restores periodically.

Upgrades. Pin image tags (e.g., gitea/gitea:1.22, louislam/uptime-kuma:2, miniflux/miniflux:latest). For Miniflux, latest is convenient but consider pinning a specific version for reproducibility. Upgrade one service at a time: docker compose pull gitea && docker compose up -d gitea. Check logs and health before moving on. Gitea and Miniflux run migrations automatically; back up first.

Monitoring the monitor. Uptime Kuma can't alert you if the whole VPS is down. Use an external ping service (e.g., Healthchecks.io) to watch Uptime Kuma's /api/status-page/heartbeat endpoint or simply ping the Caddy status host. Keep an eye on docker compose ps and system logs.

With this stack you get a capable indie dev environment on a 1 GB VPS: private Git, uptime monitoring, and RSS reading, all behind one proxy, with room to grow.
