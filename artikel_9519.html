npm audit Found 69 Vulnerabilities in My Two SaaS Apps. Most of the Work Was Sorting Them.

Tanggal: 2026-11-25

Posted on Nov 25 • Originally published at nullstud.io

At Null Studio I write maintenance guides for clients. One of them, on what software costs after launch, splits upkeep into four kinds: corrective, adaptive, preventive and security. It ends with seven questions to settle before launch. The first one is "Who receives deprecation and security notices from each platform and service we use?"

I had never asked that about my own products. So this week I ran npm audit against the production branches of the two SaaS apps I run myself: VoiceDash (white-label client portals for Retell voice agents, Next.js + Prisma + Postgres) and Upwork Scout (AI-matched Upwork job alerts, Next.js + Firestore).

69 advisories across two apps. Here is how I sorted them, what the tool got wrong, and the boring answer to the "who gets notified" question.

My local VoiceDash checkout was 37 commits behind main, so auditing it would have told me about code nobody runs. I pulled the deployed package.json and package-lock.json straight from the branch into a scratch folder and audited the lockfile alone, with no install:

--package-lock-only is the useful flag here. It audits the exact tree Vercel installs, it is fast, and it does not run anyone's postinstall script on my machine.

The obvious next move is --omit=dev, because a vulnerable ESLint plugin is not reachable from an HTTP request.

That looked like progress until I mapped every remaining advisory back to the direct dependency that pulls it in. I wrote a small script that walks packages in the lockfile from each entry in dependencies and records which roots reach each vulnerable package. For VoiceDash:

Fifteen of the 27 "production" advisories come through the Prisma CLI: hono, @hono/node-server, mysql2, chevrotain, lodash, effect and friends. My app does not serve requests with Hono and does not talk to MySQL. Those packages are there because the CLI ships a local dev server and schema tooling.

So why did --omit=dev keep them? Because prisma sits in dependencies, not devDependencies, in my own package.json. The scripts are "postinstall": "prisma generate" and "build": "prisma generate && next build", so the CLI has to be installed at build time, and at some point I put it in the production list. Vercel installs dev dependencies during the build anyway, so it could move. The audit filter trusts my package.json, and my package.json was wrong.

That does not make those 15 advisories irrelevant. Build tooling runs on a machine that holds my environment variables. It does mean they are a different risk from a bug in the request path, and they should not be ranked by npm's severity label alone.

Upwork Scout split cleanly by comparison: 11 of its 18 come through firebase-admin (gRPC, Google Cloud clients, fast-xml-parser, @fastify/busboy), 6 through next, and 1, zod, arrives only through the Anthropic SDK. The app itself does not import zod.

npm audit attaches a proposed fix to each advisory. Two of them would have hurt.

The firebase-admin "fix" is a downgrade. Upwork Scout runs firebase-admin 13.10.0. The advisory range is 11.0.0 - 14.3.0, and npm's suggested fix was:

12.1.0 was published in April 2024. The current release is 14.5.1, which sits outside the vulnerable range. npm audit fix --force would have moved my app back two years and across a major boundary in the wrong direction. The real fix is a forward major upgrade that I need to test against my Firestore code, which is exactly the kind of adaptive work the client guide says to budget for.

prisma@latest is a release candidate. VoiceDash runs Prisma 7.5.0. The vulnerable range ends at 7.10.0, and 7.10.1 is the newest stable 7.x. But the latest dist-tag on npm currently points to 8.0.0-rc.35. If I had typed npm i prisma@latest to clear the warning, I would have shipped a release candidate of my ORM to production. The fix I want is prisma@7.10.1 and @prisma/client@7.10.1, pinned together.

The other two big ones were simpler. Both apps pin next to an exact version, which is the create-next-app default, so npm update never touches it. The patched release is in the same major. The auth library in VoiceDash is a beta release, and the patched build is a later beta of the same line. Those are the first two bumps, because they sit in front of every request.

I have not shipped any of this yet. This post is the audit, not the victory lap.

Same response for Upwork Scout. Neither repo has a dependabot.yml or a Renovate config, and neither has a CI workflow that runs an audit. VoiceDash's only workflow pings Supabase so the free tier does not pause, and Upwork Scout's only workflow pings the scan endpoint every 15 minutes.

The git history tells the same story. Upwork Scout's package-lock.json last changed on July 7, two days after the first commit. VoiceDash's last changed on October 5, when I added a feature that needed it. Every dependency change in either repo happened because I was building something, never because I was maintaining something. In the guide's terms, I have been doing corrective work and zero preventive or security work, and the only reason I know is that I finally ran the command.

That pattern is familiar. I already wrote about a cron job that returns 200 when every fetch fails and about a model setting nobody re-checks. A missing notification channel is the same bug in a different place: the system is quiet, so it looks healthy.

npm audit is a good smoke detector and a bad triage nurse. The raw count told me almost nothing. The useful information came from three questions the tool does not ask: does this package run in the request path, does the fix move me forward or backward, and who would have found out if I never ran the command?

How do you handle this on small products? Do you let Dependabot or Renovate open PRs automatically, or do you batch dependency work into a regular maintenance day?
