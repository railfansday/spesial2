axe-core found 10 accessibility issues in a health app. Manual testing found 7 more

Tanggal: 2026-11-17

In October I audited OpenMRS O3, an open source electronic health record, against WCAG 2.2 level AA. I ran it locally from the official Docker images, pinned to version 3.7.1, and scanned eight screens with axe-core 4.13.0: login, location picker, the service queues home, patient search, patient registration, the patient chart, the vitals form and appointments.

axe reported ten distinct problems. Then I put the mouse away and went through the same screens with the keyboard, 200% zoom, a 320-pixel viewport and two screen readers. That found seven more failures. axe had not reported any of them, although it had flagged one of the elements for a different reason.

This article is about that gap: what the scanner saw, what it could not see and why, and how I still run axe on every pull request without the suite turning into noise. The full audit, with the raw scan, the evidence screenshots and the source verification, is public in accessibility-audits. The CI code comes from playwright-qa-showcase.

Added up, that is 28 rule hits, which overstates the problem. Nineteen of them involve two global components, the help button and the user menu, which show up on almost every screen. Grouped by cause, they come down to ten findings under five success criteria: 1.3.1, 1.4.1, 1.4.3, 2.5.8 and 4.1.2. A few examples:

All of these are real, and axe found them in seconds. When I checked the findings against the current OpenMRS source, two of the ten were already fixed upstream, including the help button. This is what automated scanning is good at, and it costs nothing to run again after every change.

The third column matters too. axe marks a check as "incomplete" when it cannot decide by itself. On these eight screens, that was 165 checks: 76 for color contrast (mostly text over the colored alert bands in the vitals tables), 87 for ARIA attributes and two others. A scan that passes with 165 undecided checks has not shown that the page is accessible. It has handed you a to-do list.

The manual pass ran in Firefox and Chrome on Linux (keyboard, zoom, responsive mode, DOM inspection), with Orca on Linux and TalkBack on an Android phone as screen readers. I did not test NVDA, JAWS or VoiceOver in this round, and the report says so.

Something had to be announced. In the global patient search, the "N search results" counter updates on every keystroke, but it is a plain

with no role="status" or aria-live anywhere above it. Sighted users see the count. Screen reader users have to leave the field to find out whether the search found anyone. That is 4.1.3 Status Messages, and no static scan can hear what is not announced.

No rule exists for it. Each result in that same search is a link that contains a button ("Active Visit"). Interactive content inside a link is invalid HTML, and screen readers handle it inconsistently.
