Structured Data for Local Schools: A Hands-On Guide to EducationalOrganization, Course and FAQ Schema

Tanggal: 2026-11-28

If you build websites for small, local schools (a trade school, a career program, a community music academy), you will eventually be asked to "add schema." Usually that request comes with a screenshot of a competitor's search result and a vague hope that some markup will produce stars, carousels, or more calls.

Structured data does not work like that, and the education corner of schema.org has a few traps that general tutorials skip. This guide is a practical deep dive for developers: which types to pick, how to connect entities with @id, how to model a course that runs in two languages on different days, what FAQ markup is still good for, how to validate, the mistakes that show up in audits again and again, and why your JSON-LD has to agree with the school's Google Business Profile.

The examples use a local career school as the running case. The organization name and URL are a real one, Brilliant Dental Assisting School in Dallas. Every other value (address, phone, coordinates, IDs) is a placeholder that you should replace with verified data from your own client.

The most useful shift is to stop thinking of structured data as "the schema snippet for this page" and start thinking of it as a small graph of entities that lives across the whole site.

Each entity gets a stable @id, typically a URL with a fragment. Other nodes reference that ID instead of repeating the data. That keeps your markup consistent and means a fix in one place propagates everywhere.

The @id is just an identifier. It does not need to resolve to anything special, but using the canonical homepage URL plus a fragment makes it obvious what it refers to and avoids collisions.

You will see sites multi-type their school as ["EducationalOrganization", "LocalBusiness"]. JSON-LD allows an array for @type, and doing so makes LocalBusiness-specific properties available. Google's local business structured data documentation is written around LocalBusiness and its subtypes.

This is where education markup gets interesting, because schema.org gives you two overlapping tools.

Course is a CreativeWork describing what is taught. CourseInstance describes a specific offering of it: when, where, how, and in what language. One course can have many instances.

That split maps nicely onto a common situation for local schools: the same curriculum taught in different languages on different days. Here is a course with an English instance and a Spanish instance.

For career training, schema.org also has EducationalOccupationalProgram, which describes a program that prepares people for an occupation. It has properties like programType, occupationalCategory, timeToComplete, educationalProgramMode, occupationalCredentialAwarded, and hasCourse.

You can use both: a program node that hasCourse pointing at your Course node. Whether it adds much depends on the site. For a school with one flagship program, a well-described Course may be enough. For a school with several programs that each bundle multiple courses, the program layer models reality better.

If you use occupationalCategory, prefer a recognized classification code and name it explicitly in your documentation. Do not invent codes.

Course and EducationalOccupationalProgram can carry offers, and some tutorials push you to fill them in. Only do that if the price is clearly published on the page and you are confident it stays current. A stale price in markup is a liability. If the school does not publish pricing, leave offers out entirely.

Google introduced Course Info structured data in 2023 and then announced in its June 2025 post on simplifying the search results page that it was phasing out several features, Course Info among them. Search Console reporting and Rich Results Test support for those features were later removed.

In practice that means Course markup will not produce a special Google SERP feature today, and the Rich Results Test will not grade it. It is still valid schema.org, other consumers may use it, and it still describes your content in a machine-readable way. Keep it if it is accurate. Just set expectations with clients.

FAQPage is simple to write, which is part of why it was so heavily abused.

In August 2023 Google announced it would show FAQ rich results only for well-known, authoritative government and health websites; check the current FAQ structured data documentation for the latest status. For a local school, assume no FAQ rich result. The markup can still make the page's question-and-answer structure explicit. The better reason to build the FAQ at all is that prospective students genuinely have these questions.

Use more than one tool, because they answer different questions.

It will not replace the validators, but it catches regressions the moment someone edits a template.

1. Claiming a status the school does not have. Words like "accredited," "approved," "licensed," and "certified" mean different things and are not interchangeable. A school approved by a state workforce agency is not automatically accredited by an accrediting body. Do not try to encode these as structured claims unless you are certain of the exact relationship; describe them in visible text using the exact wording the school is entitled to use.

2. Markup that does not match the page. Hours in JSON-LD that differ from the footer, an FAQ in markup that is not on the page, a course description copied from an old brochure. Google's general structured data guidelines are clear that markup must represent the visible content.

3. Duplicate organization nodes with different data. A theme plugin outputs one Organization, an SEO plugin outputs another, and your custom code outputs a third. Each has a slightly different name or phone. Pick one source and disable the rest.

4. Wrong subtype. CollegeOrUniversity for a short career program, or MedicalBusiness because the school trains people for healthcare jobs. Type the entity for what it is.

5. Free-text where a format is expected. "timeRequired": "3 months", "byDay": "Sundays", "opens": "9am". Use ISO 8601 durations, DayOfWeek URLs, and 24-hour HH:MM.

6. Class times in opening hours. Office hours and class schedules are different facts. Keep them apart.

7. sameAs padding. Linking to every directory listing dilutes the property's meaning. Only official profiles.

8. Review markup on your own organization. Self-serving reviews of your own business are not eligible for review rich results under Google's guidelines, and fake ones are a policy problem. If you do not have a genuine third-party review system, skip it.

9. Client-side injection that never renders for crawlers. If JSON-LD is added by a tag manager after load, confirm in URL Inspection that it appears in the rendered HTML. Server rendering is safer.

10. Forgetting the Spanish (or other language) pages. On a bilingual site, the /es course page needs its own Course node with Spanish name and description and inLanguage: "es", referencing the same organization @id.

For a local school, structured data is only one of several places where the organization describes itself. The others include the Google Business Profile, the website footer and contact page, social profiles, and any directory listings. NAP (name, address, phone) consistency is the practice of making those agree.

Google's help article on how Google determines local ranking describes the main factors as relevance, distance, and prominence, and recommends complete, accurate business information. Consistent data across sources is a basic part of being accurate. It also has a very practical benefit: a parent who finds a different phone number on Maps than on the website is likely to give up.

Name. Use the exact name the school operates under, the same on the Business Profile, the site header, and name in JSON-LD. Do not append keywords like "Best Dental School Dallas" to the profile name; Google's Business Profile guidelines prohibit that.

Address. Pick one format and use it everywhere: "Suite" vs "Ste", "Road" vs "Rd". Search engines can reconcile small differences, but there is no reason to make them. Include the suite number if the school has one. Make sure geo coordinates match the map pin.

Phone. Use one primary local number. If the school uses a call-tracking number on the website, the Business Profile can list it as primary with the main number as an additional phone. Whatever you choose, the JSON-LD telephone should match what is visibly on the page.

Hours. Holiday hours and schedule changes should be updated in the Business Profile and on the site at the same time. Stale hours on one of them create the kind of mismatch that makes people distrust both.

Category and description. The Business Profile's primary category should describe what the school is. Keep the description factual and aligned with the site's About page.

Website link. Point the Business Profile's website field to the canonical homepage, with the exact protocol and trailing slash convention your site uses.

The simplest way to keep NAP aligned is to stop typing it in multiple places. Store name, address, phone, hours, and coordinates in one config file or CMS entry. Render the footer, contact page, and JSON-LD from that same object. When the school moves or changes a phone number, update it once in code and once in the Business Profile.

Then add a quarterly reminder to compare the live Business Profile against this file by hand. It takes a few minutes and catches edits made by someone who never touched the codebase.

Good structured data for a local school is mostly discipline: pick accurate types, give every entity a stable @id, model courses the way they actually run, keep FAQ markup honest, validate with more than one tool, and make sure the website and Google Business Profile tell exactly the same story. None of it is flashy. All of it makes the school easier for both machines and people to understand.
