2 GB VPS Automation & Utility Hub: n8n, Actual Budget, Uptime Kuma, and Vaultwarden

Tanggal: 2026-11-24

Posted on Nov 24 • Originally published at vpsfolio.com

Per-container RAM: n8n 400.2 MB · actual 144.3 MB · uptime-kuma 112.0 MB · caddy 14.5 MB · vaultwarden 7.3 MB (sandbox verified 2026-11-24)

View the interactive benchmark plate and full VPS sizing comparison or compare all measured stacks on VPSFolio Benchmarks.

Four small services, one reverse proxy, one Compose file. That is the whole shape. n8n handles workflow automation, Actual Budget tracks money, Uptime Kuma watches endpoints, and Vaultwarden stores credentials. Each one is a separate container on an internal Docker network. Caddy is the only thing that publishes a host port, and it publishes it on loopback only.

The 2 GB tier is the constraint that drives every choice here. In our individual single-app runs (n8n, Actual Budget, Uptime Kuma, and Vaultwarden), the four apps summed to 1000.3 MB; combined in this 5-container sandbox run behind Caddy, total idle RAM measured 678.3 MB (n8n 400.2 MB, actual 144.3 MB, uptime-kuma 112.0 MB, caddy 14.5 MB, vaultwarden 7.3 MB). That leaves roughly 1.3 GB of headroom on a 2 GB VPS for OS buffers and active workflow spikes. If you plan to run heavy n8n jobs, schedule them off-peak or move n8n to Postgres on a larger box later.

Why Caddy instead of nginx or Traefik? Caddy's config is short enough to live inline in compose.yml via the top-level configs: block. No host bind mounts, no separate config file to copy around, no Docker socket exposure. The whole stack is one compose.yml plus a .env. That matters when you are debugging on a VPS at 2 AM.

All four backends stay on the internal network. Caddy terminates HTTP on port 80 inside the container, and the host sees only 127.0.0.1:18080. In production you swap auto_https off for real TLS and publish 80/443. The article covers that diff in the cutover section.

You need Docker Engine 24+ and the Compose v2 plugin. A 2 GB VPS with 2 vCPUs and 40 GB of disk is the target. Swap is not optional at this size — add a 2 GB swapfile so the kernel has somewhere to spill when n8n spikes during a workflow run.

Adjust the volume name to match docker volume ls. Do the same for n8n_data and actual_data. Uptime Kuma's history is nice to have but not critical — back it up weekly instead of nightly.

Upgrades. Pin versions in .env for n8n (N8N_VERSION=1.x.y) and Vaultwarden (vaultwarden/server:1.x.y) once you are stable. stable and latest are fine for the first month, then pin. Upgrade one service at a time:

n8n migrations run on startup and can take a minute on a large database. Do not restart mid-migration.

Backups. The named volumes are the source of truth. A docker run --rm -v :/data alpine tar czf - pattern works for all four. Test a restore into a scratch container before you trust the backup. Vaultwarden's db.sqlite3 is the file that matters; the rest is attachments and config.

Trade-offs. SQLite everywhere keeps the stack simple and the RAM footprint low, but it means no horizontal scaling and no live replication. If you outgrow this, move n8n to Postgres first — it is the noisiest writer. Vaultwarden can stay on SQLite for a long time; its write volume is tiny. Actual Budget is fine on SQLite indefinitely for personal use.

Caddy's automatic HTTPS is the reason this stack fits in one file. If you need mTLS, rate limiting, or complex routing rules, Caddy handles those too, but the inline config gets long fast. At that point, split the Caddyfile into its own file and accept the bind mount — but for four services on a 2 GB VPS, inline is the right call.

One more thing: keep SIGNUPS_ALLOWED=true only until you create your Vaultwarden account, then flip it to false in .env and restart. The same applies to n8n's owner account — create it immediately after first boot, before you expose the hostname publicly.
