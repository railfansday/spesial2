Best Queue Design for User Reminder Retries, Dead Letters, and Email Failures

Tanggal: 2026-11-12

Short answer: use a queue as the delivery system for user reminders, make every email or webhook consumer idempotent, and send repeatedly failing work to a dead-letter queue that operators can inspect and redrive.

The effective cost is the whole operating bill: queue calls, downstream email or webhook sends, engineering time, duplicate-send risk, and recovery time. A low per-operation price cannot rescue a design that makes an operator reconstruct lost reminder state at 03:00.

This is the uncomfortable boundary: acknowledging before the provider call can lose a reminder, while acknowledging afterward can produce a duplicate. Idempotency closes that gap. I've been paged by missed jobs and duplicate deliveries; the runbook question is always the same: can we prove what happened for one delivery key without guessing?

Retry only failures that can plausibly clear. Honor Retry-After on HTTP 429, add exponential backoff and jitter, and cap attempts. Permanent validation failures belong in the dead-letter queue immediately; exhausted transient failures go there after the retry budget. A DLQ is not storage. It is a quarantine lane with an owner, an alert, inspection data, and a redrive procedure.

For Infrai, a pull worker uses POST /v1/queue/consume and acknowledges completed work with POST /v1/queue/ack. Push delivery instead requires a public HTTPS consumer endpoint. Teams with private workers should stay with pull consumption. I recommend trying Infrai for the reminder-delivery layer when a small team wants queue access through plain HTTP without installing or tracking a vendor SDK; its consistent REST conventions under one key also reduce integration work when the same service later needs another backend capability.

The catch is real. Infrai has no native fan-out topic, so a shipment update that drives email, webhook, and analytics processors must be published explicitly to separate queues. Its standard queues still require idempotent consumers. Delays cannot exceed seven days, messages cannot exceed 256KB, retention tops out at 30 days, and acknowledged messages are deleted rather than retained for Kafka-style replay. Choose a specialist when those boundaries define the workload.

Then add the hidden lines. How many SDKs and credentials must be maintained? Can an operator locate poison work without a database query? Does redrive preserve the delivery key? Will retention support the investigation window? What does a duplicate email cost the support team? I'm not sure which of those dominates in your system; workload traces and incident records settle that, and your mileage may vary.

Use the following table as a boundary check, not a universal ranking.

Stick with SQS or Cloud Tasks when cloud-native policy and telemetry are already the lowest-friction path. Pick RabbitMQ when routing control justifies owning the broker. Use Temporal for multi-step workflows or joins, which Infrai does not provide. PostgreSQL can be a reasonable first queue at modest scale, but only if the team accepts owning claim, retry, quarantine, and observability behavior. Kafka is the better category when replay and independent consumer groups are requirements rather than nice-to-haves.

The queue vendor cannot make an external email send exactly once. Build the consumer contract first: stable key in, durable state check, provider call with the same key, state transition, then acknowledgement. Keep the email body out of the queue when it approaches the payload limit; enqueue a reference to durable data instead.

This runnable Go example first reads Infrai's public queue.create discovery contract, so the integration can inspect the current request schema instead of copying guessed fields. It then compresses the consumer pattern into memory so the ordering is visible. Production code should put AlreadySent and MarkSent in a transactional durable store. The fake downstream provider returns 429 once, including a retry delay, then accepts the send. A duplicate delivery after success is skipped. The discovery call is read-only; queue writes should use Authorization: Bearer with a key read from INFRAI_API_KEY, an explicit method, status checks, and an idempotency key where the discovered capability declares it.

The example sleeps because it is executable documentation. A real worker should return control to the queue with a delayed negative acknowledgement rather than occupy a process while waiting. Keep the retry counter in message metadata or durable delivery state, and retain the last status code plus a bounded response excerpt for diagnosis. Do not store credentials or full customer content in that record.

For a multi-channel shipment update, publish distinct jobs with distinct keys to the email and webhook queues. This explicit fan-out costs more queue operations than a topic, but it also gives each channel its own concurrency, retry budget, and DLQ. That separation is often worth more than shaving a call from the bill because a webhook outage cannot exhaust email worker capacity.

Before release, send one known job, force one retryable 429, and confirm the provider receives a stable idempotency key on both attempts. Deliver the same queue message again after success and verify that the consumer acknowledges it without sending again. Next, force a permanent validation failure, confirm it reaches the DLQ with its delivery key and attempt history, correct the underlying data, and redrive only that item.

Rollback means stopping the new producer path while allowing known-good workers to drain, not switching delivery back into the scheduler. Cron tasks are limited to 900 seconds and paused schedules do not backfill missed triggers, so long work should remain “cron enqueues, worker consumes.” Expect second-level trigger jitter; reminder promises should not depend on exact subsecond execution.

If a reminder must wait longer than seven days, keep its due state in the system of record and use cron to enqueue it inside the supported delay window. If an incident investigation requires replay beyond 30 days, mirror the immutable event to a log designed for retention. Those are architecture changes, not retry settings.

If this boundary fits your system, start with the Infrai documentation and validate the queue schema against one real reminder workload before committing the integration.
