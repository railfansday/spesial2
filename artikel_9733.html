Why Is There a Delay When I’m Typing? (I Tested the Bottlenecks So You Don’t Have To)

Tanggal: 2026-11-05

A few weeks ago, I was refactoring an internal dashboard in VS Code when my keystrokes began lagging by what felt like an eternity. I would hit const payload =, lift my hands, and watch the characters crawl onto the editor like a teletype machine from 1974.

When you type at 80+ WPM, human perception notices latency spikes as low as 30ms. Anything above 80ms feels broken; at 150ms, your brain trips over its own motor planning.

Most guides will handwave this away with "restart your PC" or "buy a new keyboard." But as engineers, we know keystroke latency is deterministic. A physical keypress must traverse a multi-tier pipeline: hardware switch mechanics, firmware matrix scanning, connection protocols, OS HID drivers, display compositor queues, and the application's UI thread.

Here is an architectural autopsy of where keystrokes get stalled, how to measure the gap with actual tooling, and the exact levers to pull to eliminate it.

Before blaming an individual app, it helps to understand the physical and software journey of a single letter:

When all systems operate within spec, end-to-end latency sits between 18ms and 35ms—completely fluid. When it feels like wading through wet cement, the bottleneck almost always sits in one of four layers.

Mechanical switches register contact via two thin metal leaves slamming together. Because metal vibrates on contact (contact chatter), the controller sees a rapid burst of highs and lows over the span of 1 to 5 milliseconds:

To prevent a single strike from outputting cccc, keyboard firmware runs a debounce algorithm.

If you are using an office-grade membrane keyboard or older mechanical boards, the matrix scan frequency may run as low as 62.5Hz to 125Hz (sampling once every 8ms–16ms). Modern keyboards running QMK or custom ARM controllers scan at 1000Hz (1ms).

If your keyboard is wireless, this is where packet serialization queues silently explode.

For software engineers, 90% of typing latency isn't physical hardware—it's the event loop in our tools.

Modern developer environments (VS Code, Slack, Notion, Obsidian, Chrome) are built on Chromium and Electron. When an input event hits an Electron process, it doesn't immediately print to screen. It gets queued into the main thread.

In browser environments, synchronous operations bound to the input handler freeze visual feedback. Consider an unthrottled React or vanilla JS search component:

Every keystroke fires an InputEvent. If runHeavyAstFilter hogs the thread for 45ms, and you type 3 characters within 100ms, the browser cannot yield to the compositor. The frame budget (16.6ms at 60Hz) is blown, dropping frame rates and deferring text paints until the task queue drains.

Look for red flags labeled Long Task (>50ms) directly beneath the keydown or input slices. If the total duration from Event: keydown to Composite Layers exceeds 50ms, your JavaScript engine is choking the renderer.

If the lag happens specifically inside your CLI, the culprit is terminal rendering architecture.

Traditional terminal emulators like standard Windows Console Host (conhost.exe) or legacy macOS Terminal render glyphs via CPU-bound rasterization pipelines, redraw whole scrollback viewports sequentially, and rely on blocking synchronous PTY reads.

Switching to a GPU-accelerated terminal engine that decouples PTY parsing from the presentation loop immediately shaves 15ms–30ms off every command line character you type.
