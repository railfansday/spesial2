Controlling a remote Android screen: scrcpy, WebRTC streaming and vendor web consoles compared

Tanggal: 2026-11-27

To control a remote Android device from the browser or a desktop, you need two things: a video stream of the screen and a channel that carries your input back. scrcpy does both with a native client over an adb tunnel. WebRTC tools, like Cuttlefish’s web UI, do it in the browser over UDP. Vendor consoles wrap streaming behind a dashboard, often without documenting how.

The differences show up in setup, in how they handle a bad network and in how many devices you can drive at once. Latency is the number everyone asks about. It’s also the one that means nothing without the setup next to it, so this article states the setup for every figure.

scrcpy runs a small server on the device and a native client on your computer, connected through adb. The server encodes the screen with Android’s own encoder and streams it over a socket. The client decodes it, displays it and sends your keyboard and mouse events back on a separate socket.

The project’s developer docs describe the flow in detail. The client pushes a server file to the device and starts it through app_process. Under the hood, it runs roughly this:

bash adb push scrcpy-server /data/local/tmp/scrcpy-server.jar adb reverse localabstract:scrcpy_ tcp:27183 adb shell CLASSPATH=/data/local/tmp/scrcpy-server.jar \ app_process / com.genymobile.scrcpy.Server [options]

Requirements are light. The device needs Android 5.0 (API 21) or later and USB debugging enabled. Some devices, notably Xiaomi, need an extra “USB debugging (Security Settings)” option before input works. The client runs on Linux, Windows and macOS. Nothing stays installed on the device afterwards.

The README’s own tuning example shows the knobs that matter for remote use:

bash scrcpy --video-codec=h265 --max-size=1920 --max-fps=60 --no-audio

It also notes that reducing resolution with -m1024 can greatly improve performance. Over a slow link, that’s the first flag to reach for.

For remote devices, scrcpy rides on adb. That means you need adb access to the device over TCP/IP, an SSH tunnel, or a provider that exposes ADB. The docs have a dedicated page on tunnels. It works well across the internet if adb does, and it doesn’t run in a browser on its own.

Browser consoles can’t open raw sockets, so they use what browsers offer: WebRTC, or a WebSocket carrying video. WebRTC is the common choice when latency matters, because it can use UDP and drop late packets instead of waiting for them.

The clearest open example is Cuttlefish, Android’s own virtual device. Its docs say WebRTC lets you control a Cuttlefish device from a browser without installing anything on the client. They list more efficient encoding than VNC, in-browser ADB, and an extensible protocol for camera, microphone and sensor data. You start it like this:

Besides TCP 8443, it needs TCP and UDP ports 15550 to 15599 open if you connect from another machine. That port list is a good reminder of WebRTC’s main setup cost: networking.

Pick by where the device is, who needs to reach it and how many you drive at once.

|---|---|---|---| | Client | Native app on Linux, Windows or macOS | Browser | Browser or vendor app | | Transport | TCP sockets through an adb tunnel | UDP via ICE, TCP or TLS fallback via TURN | Often undocumented | | Setup | adb and USB debugging; a tunnel for remote devices | Signalling, ports and often a TURN server | An account and a click | | Multi-device | One window per device | One tab per device | Depends on the dashboard | | Best for | Daily dev work on devices you can reach with adb | Teams sharing virtual devices without installing anything | Real hardware or persistent devices you don't maintain |

Many teams use two: a vendor console for access and scrcpy over ADB for heavy daily work on the same device.

How do I control a remote Android device from the browser? Use a tool that streams over WebRTC or WebSockets, such as Cuttlefish’s web UI for virtual devices, or a vendor console for hosted devices. AWS Device Farm and cloud phone platforms like Multilogin both stream their devices to you this way. For a physical phone you own, you’ll need your own WebRTC stack or a hosted service.

What’s a good scrcpy alternative? It depends on what scrcpy lacks for you. If you need browser access with nothing installed, look at WebRTC-based tools. If you need devices you don’t own, a device farm or cloud phone console fills that gap.

Can scrcpy run in a browser? Not by itself. scrcpy is a native client that talks to the device through adb sockets, which browsers can’t open. Browser access needs a relay that converts the stream to WebRTC or WebSockets.

Does scrcpy work over the internet? Yes, if adb does. Connect over TCP/IP or through an SSH tunnel, as described in scrcpy’s tunnels docs. Lower the resolution and frame rate first, since every frame travels over your link.

How do I tell which protocol a web console uses? Open chrome://webrtc-internals in Chrome while the console streams. A peer connection there means WebRTC. If nothing appears, check the Network tab in DevTools for a WebSocket carrying binary frames.
