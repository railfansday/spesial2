NonoDB in practice #1: expiring invite tokens without Redis or cron

Tanggal: 2026-11-18

Every small product eventually grows the same little subsystem: one-time invite links.

A teammate clicks "Invite", we generate a token, send a URL, and the link must work exactly once and stop working after seven days. It also has to be auditable — "who invited whom, and when was the link used?" — because support will ask.

That is a cache, a database, and a scheduler for a feature that stores maybe a few thousand rows. On a 1 GB VM it is also three more things that can page you at 2 a.m.

This post rebuilds the feature with one process: NonoDB, a single Rust daemon that owns LMDB files and speaks HTTP/JSON. The whole thing fits in the same mental model as SQLite, but with document semantics, TTL, and per-document history built in.

Before choosing anything, I wrote the actual contract:

The important line is number four. Expiry is not authorization. A TTL is a garbage collector, not a lock. If two requests arrive at the same time, "is it expired?" followed by "mark it used" is a race unless the check and the write happen in one transaction.

NonoDB publishes Linux amd64/arm64 images. Pin an exact version in production; latest should be a deliberate choice, not an accident.

The daemon runs as an unprivileged user. TCP requires the auth registry; the Unix socket is the trusted local channel. For a single-host app, mounting the socket into the app container is even simpler, and there is no bearer token to rotate.

NonoDB collections can carry a default TTL and a history retention setting. Both are opt-in.

There is no cron entry and no cleanup container.

The default is seven days, but the support workflow needs one hour. The reserved top-level _ttl field overrides the collection default for that document:

_ttl is metadata: it is stored outside the document and is not returned by reads. An update that does not mention _ttl preserves the current expiry, so "resend invite" can extend or shorten the window explicitly:

This is where the Redis-plus-Postgres version needed a transaction or a Lua script. In NonoDB, find_and_modify selects one document, applies the update, and returns the image — all inside the single writer transaction.

Two concurrent requests cannot both receive the invite. The second one matches nothing, because the first transaction already set used: true. There is no read-modify-write gap in application code, and no distributed lock.

The Python client passes the Extended JSON object through unchanged. Over raw HTTP, NonoDB also accepts numeric milliseconds and RFC 3339 strings with Z or a numeric offset; naive local times are rejected as ambiguous.

This deserves its own section because it is the most common design mistake with any TTL feature, including Redis.

NonoDB TTL is eventual. A document stays readable until the background maintenance worker sweeps it, normally within a few seconds of expiry. That is perfect for garbage collection and terrible as the only check for "is this link still valid?"

So the application contract has two checks, and the find_and_modify filter above already carries both:

The TTL setting exists so that the collection does not grow forever, and so that support does not see year-old invites in the GUI. It is not SETNX.

If a document somehow survives long past its deadline, the expires_at filter still rejects it. TTL remains the janitor, not the bouncer.

Because history is enabled on the collection, the insert and the consume are recorded as revisions in the same LMDB transaction as the current document. There is no second write path to forget.

rev is a global monotonic revision ID. For one document, revisions are ordered but not necessarily consecutive — another document's write can take a number in between. get_version(token_hash, rev) returns one exact revision, or None if retention has pruned it.

The retention setting caps revisions per document at 20. For invites that is plenty: created, maybe extended once, consumed, expired.

A real audit export can then be a single aggregation over the collection or a batch of reads, without joining two databases.

No separate analytics store, no nightly rollup.

On a small VM the idle daemon is in the single-digit-megabyte range, which is the main reason I reached for it instead of adding another service. Backups are a single LMDB directory, and the daemon supports native or restic backups with encryption if the data ever leaves the box.

For the actual shape of this problem — a few thousand short-lived records, one small VM, one process, atomic consumption, and an audit trail — one binary is easier to reason about than three services.

The full API surface used here — create_collection, _ttl, find_and_modify, history, aggregate — is in the NonoDB docs. If you want the next article in this series, it will take the same daemon and build a job queue with leases and retries, again without Redis.
